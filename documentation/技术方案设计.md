## 1. 设计目标与范围

### 1.1 目标

| 维度 | 目标 |
|------|------|
| 通用性 | 能力来自**可插拔插件**（Skill/Tool/Knowledge/Model/Memory），Agent = Runtime + 插件组合配置；新增能力 = 新增插件，不改框架 |
| 可靠性 | 生产级高可用，任务可重试、可断点续跑、可人工介入 |
| 可观测 | 全链路 Trace / Metric / Log，Agent 决策过程可审计、可回溯 |
| 可评估 | 支持离线评测与在线评测闭环，Agent 迭代有量化依据 |
| 安全合规 | 多租户隔离、工具权限管控、数据脱敏、审计留痕 |

### 1.2 非目标（首期不做）

- 不做自有 LLM 训练 / 微调（通过统一网关接入外部/自托管模型）
- 不做复杂的多智能体分布式协同编排（先支持单 Agent + 子 Agent 调用）
- 不承担业务系统本身的重构

### 1.3 关键约束

- 模型多厂商接入，需屏蔽各家 API 差异，支持 fallback 与成本路由
- 生产级部署：多副本、水平扩展、无单点
- 数据安全：企业内网可用，敏感数据可私有化存储

## 2. 技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 语言 | **Python 3.11+** | Agent 生态最成熟 |
| Web 框架 | **FastAPI** | 异步高性能、原生 OpenAPI、类型校验 |
| Agent 编排 | **LangGraph** | 有状态图编排，原生支持 Plan/Decide/Execute/Observe 循环、checkpoint（HITL/Resume 基础） |
| LLM 统一网关 | **LiteLLM** | 统一 100+ 厂商接口，支持路由、fallback、限流、成本统计（即「统一多厂商网关」落地） |
| 关系存储 | **PostgreSQL 16** | 元数据、配置、评测结果、审计 |
| 缓存/会话 | **Redis 7** | 短期记忆、会话态、限流、分布式锁、异步队列 |
| 向量存储 | **pgvector / Milvus** | RAG 检索；小规模用 pgvector，规模化切 Milvus |
| 图存储 | **Neo4j** | 知识图谱 KG（首期可选，降级为关系表模拟） |
| 消息队列 | **Redis Streams / Celery** | 异步任务、长任务执行 |
| 对象存储 | **MinIO / S3** | 文件、工件、embedding 缓存 |
| LLM 可观测 | **Langfuse / LangSmith** | Prompt、Token、成本、Trace 追踪 |
| 系统可观测 | **OpenTelemetry + Prometheus + Grafana + Loki** | 指标、日志、链路 |
| 可视化前端 | **React + Ant Design + ECharts + AntV X6 / React Flow** | 控制台、执行 DAG、仪表盘 |
| 部署 | **Kubernetes + Helm** | 生产级编排、HPA、滚动发布 |

> 备选说明：若未来多智能体协同诉求增强，可平滑迁移到 LangGraph 的多图嵌套或引入 CrewAI/AutoGen 作为上层调度。

## 3. 总体架构

```
                        ┌─────────────────────┐
                        │        User         │
                        └──────────┬──────────┘
                                   ↓
                 ┌───────────────────────────────────────┐
                 │            Agent Gateway              │
                 │  认证鉴权 / 租户隔离 / 上下文装配        │
                 │  限流 / 协议适配(HTTP·SSE·WebSocket)   │
                 └──────────────┬────────────────────────┘
                                ↓
                 ┌───────────────────────────────────────┐
                 │            Agent Runtime              │
                 │    Plan → Decide → Execute → Observe  │
                 │          (LangGraph 状态机)           │
                 └───────┬──────────┬──────────┬─────────┘
                         │          │          │
             ┌───────────┼──────────┼──────────┼─────────────┐
             ↓           ↓          ↓          ↓             ↓
         Brain       Skill Mgr   Tool Mgr   Knowledge    Workflow Engine
        ┌─────────┐  ┌──────┐   ┌──────┐   ┌─────────┐  ┌──────────────┐
        │Working  │  │Skill │   │Tool  │   │RAG │KG  │  │Retry│HITL│Resume│
        │Cognitive│  │Regist│   │Regist│   └──┬──┴────┘  └──────────────┘
        └─────────┘  └──────┘   └──────┘      │
             └───────────┼──────────┼──────────┘
                         ↓          ↓
                ┌───────────────────────────┐
                │   LLM Gateway (LiteLLM)   │──→ 多家 LLM 厂商
                └───────────────────────────┘
                ┌───────────────────────────┐
                │       Observability       │  (Trace/Metric/Log)
                └───────────────────────────┘
                ┌───────────────────────────┐
                │        Evaluation         │  (离线/在线)
                └───────────────────────────┘
                ┌───────────────────────────┐
                │      Agent Console        │  (监测/跟踪/控制/测试 · UI)
                └───────────────────────────┘
```

**核心分层原则**：Runtime 只关心「思考循环」，其余一切能力——Brain（认知记忆）、Skill、Tool、Knowledge（外挂知识）、Model、Memory 后端——都是**可插拔插件（Plugin）**，通过统一 Plugin 接口接入。**Agent = Runtime + 插件组合的配置**，新增能力 = 新增插件，不触碰核心循环（详见 4.12）。

### 3.1 工程分层：业务层与 Agent 框架层分离

**核心原则**：平台拆成两个可独立发布、可单独演进的项目——**业务无关的 Agent 框架层（smartagent-core）** 与 **业务层（SmartAgent App）**，采用 **Ports & Adapters（六边形架构）** 解耦：**业务依赖框架，框架不依赖业务**。

```
┌─────────────────────────────────────────────────────┐
│  业务层（smartagent-app）                             │
│  api · domain · persistence · auth · adapters        │
│    · 认证鉴权、租户隔离、Agent/Tool/Skill 的 CRUD       │
│    · adapters 实现框架定义的端口：                      │
│      DbPluginLoader · DbPermissionContext            │
│      RunRecorder · SubagentRunner · PgVectorMemory   │
└──────────────────────────┬──────────────────────────┘
                           │  依赖（import）
                           ▼
┌─────────────────────────────────────────────────────┐
│  Agent 框架层（smartagent-core）—— 独立项目            │
│  runtime(AgentRuntime) · core(graph/nodes)           │
│  ports(能力协议) · plugins · skills · tools · memory   │
│  events(事件模型) · default(LiteLLM/Redis/HashEmbed)  │
└─────────────────────────────────────────────────────┘
```

**框架层定义的能力端口（Ports）**——业务层注入实现（Adapters），框架只依赖协议与纯数据，不感知 DB / HTTP / 多租户：

| 端口 | 职责 | 对应现有模块 |
|------|------|-------------|
| `LLMGateway` | LLM 统一调用抽象 | `llm/base.py` |
| `Embedder` | 向量化抽象 | `llm/embedder.py` |
| `Plugin` | 能力单元统一协议 | `plugins/base.py` |
| `PermissionChecker` | 运行时授权判定（纯逻辑） | `iam/permission_manager.py` 的 `check()` |
| `SubagentRunner` | 子 Agent 调度回调 | `skills/agent_skill.py` 的 `run_subagent` |
| `FlowRunner` | 多步流程执行回调 | `skills/flow_skill.py` 的 `run_flow` |
| `WorkingMemory` | 短期工作记忆 | `memory/working.py` |
| `LongTermMemory` | 长期语义记忆 | `memory/vector.py` |
| `EventSink` | 步骤/事件回调 | `events/sse.py`（框架出事件模型，HTTP/SSE 传输在业务层） |

**编排入口**：`AgentRuntime.run(definition, task, context, *, deps)` —— 接收 `AgentDefinition`（模型/系统提示/插件引用/运行时配置）+ `RunContext`（tenant/user/session/深度）+ `RuntimeDeps`（上述端口实现的集合），内部执行 Plan→Decide→Execute→Observe 循环，仅在关键节点（execute 前授权、步骤完成、子 Agent 调度）回调注入的端口。

**依赖方向（单向，禁止反向 import）**：

```
业务层(api/domain/persistence/adapters) ──► Agent 框架层(runtime/core/ports/plugins/skills/tools/memory)
```

**与各模块的映射**：4.1 Gateway、4.11 IAM 的「数据加载与身份解析」、DB 落库、限流/审计 → **业务层**；4.2 Runtime、4.3 Brain 的「记忆机制」、4.4/4.5 Skill/Tool 的「执行」、4.12 插件协议 → **框架层**。业务层把 Agent 配置解析成标准 `AgentDefinition`、把权限加载成 `PermissionContext`、把事件持久化为 `runs/run_steps`，再交给框架执行。

> 分层的两册详细设计见 **《Agent框架层详细设计.md》** 与 **《业务层详细设计.md》**。

## 4. 模块详细设计

### 4.1 Agent Gateway

**职责**：统一入口，屏蔽内部复杂度，负责横切关注点。

| 关注点 | 设计 |
|--------|------|
| 认证鉴权 | OIDC / OAuth2 + JWT；内部服务间 mTLS |
| 租户隔离 | 所有资源带 `tenant_id`，通过请求头/中间件注入，底层存储行级隔离 |
| 上下文装配 | 从 Session/Memory 装配 user profile、历史上下文，注入 Runtime 初始 state |
| 协议适配 | HTTP REST（同步）、SSE / WebSocket（流式）、异步回调（长任务） |
| 限流熔断 | 令牌桶（Redis）按租户/用户/模型维度限流；上游异常熔断降级 |
| 模型路由 | 委托 LiteLLM：按 `成本/延迟/能力/配额` 策略选择厂商，失败自动 fallback |

**接口形态**（详见第 6 节）：
- `POST /v1/agents/{agent_id}/runs` —— 创建运行
- `GET  /v1/runs/{run_id}` —— 查询状态（SSE 流式推送事件）
- `POST /v1/runs/{run_id}/actions` —— HITL 提交人工决策

**中间件链**：`Auth → Tenant → RateLimit → Trace(注入 TraceID) → Audit → Route`。

### 4.2 Agent Runtime

**核心：LangGraph 状态机，实现「Plan → Decide → Execute → Observe」主循环。**

```
        ┌─────────────────────────────────────────────┐
        │                 Agent State                  │
        │  task / plan / memory_ctx / history / result │
        └─────────────────────────────────────────────┘
                            ↓
   ┌──────── Plan ────────┐
   │ 任务拆解 / 生成步骤    │
   └──────────┬───────────┘
              ↓
   ┌──────── Decide ───────┐    无可用工具/已达成目标
   │ 选择 Tool/Skill/SubAgent│ ────────────────────────→ End
   └──────────┬───────────┘
              ↓
   ┌─────── Execute ───────┐
   │ 调用 Tool/Skill/SubAgent│
   └──────────┬───────────┘
              ↓
   ┌─────── Observe ───────┐
   │ 结果回填 + 反思 / 判断   │── 需继续 → 回到 Decide
   └────────────────────────┘
```

**设计要点**：

1. **State 定义**：`AgentState` 为强类型（Pydantic），包含 `task`、`plan`、`messages`、`memory_ctx`、`artifacts`、`iteration`、`status`。所有节点读写此状态。
2. **循环控制**：
   - `max_iterations`（默认 20）硬限制，防死循环
   - `timeout` 全局超时
   - `cost_budget` 成本上限，超限自动降级模型或终止
3. **可中断执行**：LangGraph `checkpointer`（Redis/Postgres 后端）持久化每个节点的中间状态，天然支持：
   - **Resume**：崩溃/中断后从 checkpoint 恢复
   - **HITL**：在 `interrupt` 节点挂起，等待人工决策后 `resume`
4. **SubAgent 调用**：Decide 节点可选择「派生子 Agent」（复用同一 Runtime 的图定义），通过父 Agent 的 Tool 形态暴露，实现简单的多智能体嵌套。
5. **模型无关**：所有 LLM 调用统一走 `LLMGateway` 抽象，不直接依赖具体 SDK。

### 4.3 Brain（认知记忆系统）

将「记忆」抽象为 Agent 的**大脑**，模拟人类认知记忆结构，并与「外挂知识库 Knowledge」（4.6）严格区分：

- **Brain（内生记忆）**：Agent 自己的经历与习得——个性化、随时间累积、只属于「这个 Agent/这个用户」。
- **Knowledge（外挂知识）**：外部知识——文档、事实、关系，相对稳定、可跨租户共享。

> 一句话区分：**Brain 回答「关于这个用户 / 这次任务，我积累了什么经验」；Knowledge 回答「关于这个世界 / 这个业务，有哪些事实」。**

#### 4.3.1 Brain 结构（二分）

Brain 由 **Memory Manager** 统一管理，内部拆分为两部分：**Working Brain（工作记忆）** 与 **Cognitive Brain（认知记忆）**，二者通过「固化」衔接。

```
                 Brain
                   │
            Memory Manager（统一门面：写入 / 固化 / 召回 / 遗忘）
                   │
        ┌──────────┴──────────┐
        │                     │
  Working Brain        Cognitive Brain
   （工作记忆）          （认知记忆 / 长期）
        │                ┌──────────┴──────────┐
      Redis             │                     │
        │          Memory Graph          Vector Memory
     Session       （记忆图谱）           （向量记忆）
                Concept Relation        语义向量索引
```

**① Working Brain（工作记忆）**

| 项 | 说明 |
|----|------|
| 存储 | Redis |
| 范围 | Session 级（单次会话/任务） |
| 内容 | 当前任务、中间推理、临时变量、注意力焦点 |
| 特征 | 快、易失、全量注入、TTL 释放 |

**② Cognitive Brain（认知记忆 / 长期）**

由两个互补索引构成，回答不同类型的「记得什么」：

| 索引 | 职责 | 存储 | 适合回答 |
|------|------|------|----------|
| **Memory Graph（记忆图谱）** | 结构化记忆：`Concept（概念/实体）— Relation（关系）`，如「用户 A — 偏好 — 简洁回答」 | 图库（Neo4j）或 PG 邻接表 | 精确关系、多跳推理、「A 和 B 什么关系」 |
| **Vector Memory（向量记忆）** | 非结构化语义记忆：记忆片段 embedding | pgvector / Milvus | 模糊语义、泛化、「和这个类似的事」 |

> 二者互补：Memory Graph 管「精确关系与结构」，Vector Memory 管「模糊语义与泛化」。程序记忆（Skill，见 4.4）与 Persona 属于 Brain 上层的「配置/注册层」，不是记忆存储本身。
>
> 细化结构图（分层 + 数据流 + 存储映射 + 生命周期 + 知识回退）见 **《核心设计图.md》第一部分**。

#### 4.3.2 统一接口

`IMemory` 抽象，Runtime 不感知底层存储：

```python
class IMemory(Protocol):
    def write(self, entry: MemoryEntry) -> None: ...                 # 写入
    def consolidate(self, session_id: str) -> None: ...              # 会话结束后固化
    def query(self, q, types: list[str], filters) -> list[MemoryEntry]: ...  # 召回
    def sufficiency(self, results) -> float: ...                     # 召回充分度（不足则触发 Knowledge 回退）
    def forget(self, entry_id: str) -> None: ...                     # 删除（合规/遗忘）
    def reflect(self, entry: MemoryEntry) -> float: ...              # 重要性/反思评分
```

#### 4.3.3 关键机制

**1) 记忆固化 Consolidation（类睡眠巩固）**

会话/任务结束后异步执行（Celery），模拟「海马体 → 皮层」的沉淀，Working Brain → Cognitive Brain：

```
Working Brain ──结构化抽取──► Memory Graph（新增/更新 Concept 与 Relation）
              ──语义 embedding──► Vector Memory（记忆片段向量化落库）
```

- **分级固化**：`reflect()` 对片段评分，高价值（成功经验、用户偏好、纠错）优先固化，低价值丢弃
- **去重合并**：与已有记忆做相似度比对，重复/冲突的合并或覆盖
- **防污染**：一次性临时信息、噪音不进入长期记忆

**2) 遗忘 Forgetting（类 Ebbinghaus 遗忘曲线）**

- **时间衰减**：`score = importance × e^(-Δt/τ)`，τ 按记忆类型设定（Vector 慢衰减、Graph 边权重衰减）
- **访问加权**：经常被召回的片段提升权重（LRU 思想）
- **重要性标记**：`reflect()` 打分 + 显式标记（用户点赞/纠错）
- **冲突消解**：Memory Graph 新关系覆盖旧关系、Vector 新事实覆盖旧事实，维护一致性
- **显式删除**：合规「被遗忘权」，级联清理向量、图节点与摘要

**3) 检索 Retrieval（装配认知上下文）**

Runtime 在 Plan 阶段并行检索两部分 Brain，装配「认知上下文」注入：

| 来源 | 策略 |
|------|------|
| Working Brain | 当前会话 state 全量注入 |
| Memory Graph | 图查询：精确关系 + 多跳推理（「A 偏好什么」「B 与 C 什么关系」） |
| Vector Memory | 语义向量 top-k 召回（「和这次类似的历史经验」） |
| Persona | 每次必注入（稳定身份） |

**4) 元记忆 Meta-memory**

「记忆的记忆」——为每条记忆记录 `来源、时间戳、访问次数、最后访问、置信度、重要性`：

- 检索排序：高置信 + 高访问优先
- 冲突消解：新旧事实按可信来源与时间裁决
- 审计：记忆的来龙去脉可回溯

**5) 安全与合规**

- 敏感字段（姓名/手机号/密钥）脱敏后才落库
- PII 检测，命中即阻断写入长期记忆
- 所有记忆操作进审计日志

#### 4.3.4 知识回退：Brain 不全 → Knowledge 补全

当 Brain 检索到的知识**不全或置信度不足**时，自动回退到 Knowledge 系统（4.6）补全：

```
Runtime 需要某类知识
        │
        ▼
① 检索 Brain（Working + Memory Graph + Vector Memory）
        │
        ▼
② 充分度评估 ──充分──► 直接用 Brain 记忆
        │ 不全 / 低置信
        ▼
③ 检索 Knowledge（RAG + KG）
        │
        ▼
④ 命中且补齐 ──► 补充进上下文（附引用来源）
        │
        └──（可选）沉淀回 Brain：补全的知识固化进 Memory Graph /
             Vector Memory，形成学习闭环
```

**判定「不全」的依据**（可配置阈值）：
- Vector Memory 召回相似度低于阈值（无高相似片段）
- Memory Graph 图查询无匹配关系（缺概念/关系）
- Reflection 节点自评「信息不足以回答」（low-confidence）
- 命中记忆时间过旧（超过时效阈值）

**回退与沉淀策略**：
- **回退**：仅当 Brain 不足时才查 Knowledge，避免每次都打外挂知识库（省时省 token）
- **沉淀**：补全的知识若被确认有效（用户采纳/任务成功），固化回 Brain，下次不再依赖外挂

---

### 4.4 Skill Manager

**Skill = 可复用、可声明式组合的能力单元**（参考 MCP / Claude Code Skill 思路）。

**Skill 形态（四选一或组合）**：
- `prompt-skill`：纯提示词模板（角色、SOP、few-shot）
- `function-skill`：一段可执行逻辑（Python 函数 / 脚本）
- `flow-skill`：一个预定义 LangGraph 子图（复杂多步流程）
- `agent-skill`：一个可调用的子 Agent

**Skill Registry**：
- 元数据表：`skill_id / name / version / description / tags / owner / tenant`
- 版本管理：语义化版本，Agent 绑定 `skill@version`，支持灰度
- 权限：按租户/角色控制可见性与调用权
- 加载：懒加载（首次调用加载）、热更新（版本切换不重启服务）

**与 Tool 的关系**：Skill 更「重」——封装了上下文与流程；Tool 更「轻」——原子能力。Skill 内部可调用多个 Tool。

**业务接入范式**：业务方「注册 Skill + 配置 Agent 组合」即可上线新场景，不改框架核心。

---

### 4.5 Tool Manager

**Tool = 原子能力（原子动作 / 外部系统调用）。**

| 类别 | 说明 | 示例 |
|------|------|------|
| Builtin | 平台内置 | 计算器、搜索、文件读写 |
| MCP 工具 | 通过 MCP 协议接入外部工具服务器 | 数据库、浏览器、GitHub |
| HTTP 工具 | 通过 OpenAPI 描述注册的 REST 接口 | 业务系统 API |
| 自定义函数 | 业务方上传/注册的 Python 函数 | 内部 RPC |

**Tool Registry**：
- Schema 声明：统一用 **JSON Schema** 描述入参/出参（MCP 与 OpenAI function calling 天然兼容）
- 沙箱执行：外部/自定义工具在隔离环境（容器 / subprocess + 资源限制）运行
- **权限管控**：每个 Tool 声明所需权限（读/写/网络/密钥），执行前走 `PermissionManager` 校验；高危操作触发 HITL 确认
- 观测埋点：每次调用记录 `tool_name / 入参 / 出参 / 耗时 / 是否成功`

**安全红线**：工具必须「最小权限 + 可审计 + 高危人工确认」三原则（权限模型详见 4.11）。

### 4.6 Knowledge（外挂知识库 · RAG + KG）

**职责**：为 Agent 提供「外挂知识」与「结构化关系」，解决 LLM 知识过时与幻觉。
**定位**：区别于 Brain（4.3 的内生记忆），Knowledge 是**外部、相对稳定、可共享**的知识。

```
              Knowledge Manager
        ┌──────────────┬──────────────┐
        │     RAG      │      KG      │
        │ 向量检索 + 重排│   实体关系图  │
        └──────┬───────┴──────┬───────┘
               ↓              ↓
        混合检索（Hybrid Retrieval）
               ↓
        上下文注入 Runtime
```

**RAG 流水线**：
1. **摄取**：文档解析（PDF/Word/网页）→ 清洗 → 分块（语义切分）→ embedding（多模型可配）→ 入库（向量 + 原文）
2. **检索**：向量召回 top-k → Rerank（BGE-Reranker / LLM）→ 去重压缩
3. **生成**：检索结果注入上下文，附引用来源（降低幻觉、可溯源）

**KG（知识图谱）**：
- 从文档/数据抽取 `实体-关系-实体` 三元组（LLM 抽取 + 规则）
- 存储 Neo4j，支持多跳查询、关系推理
- 与 RAG 融合：实体相关事实用图查询补充，向量负责语义泛化

**混合检索**：`向量语义 + 关键词(BM25) + 图关系` 三路召回，加权融合，Rerank 精排。

**与 Brain 的协同（知识回退，详见 4.3.4）**：
1. 默认先查 Brain（Memory Graph + Vector Memory）→ 用户偏好、经验
2. Brain 不足/低置信时，回退查 Knowledge（RAG/KG）→ 补全事实依据
3. 补全的知识可选沉淀回 Brain，形成学习闭环
4. 按上下文窗口预算合并截断，附引用来源

---

### 4.7 Workflow Engine（Retry / Pause-Resume / HITL）

**职责**：把 Agent 能力编排为可重试、可暂停恢复、可人工介入、可断点续跑的可靠流程。

| 能力 | 设计 |
|------|------|
| **Retry** | 节点级重试（指数退避 + 抖动）；工具/模型调用失败自动重试；整体失败走补偿策略；熔断器防雪崩 |
| **Pause/Resume（暂停/恢复）** | 外部（控制台/API）主动暂停 → 当前节点边界打 checkpoint → 状态 `paused` → 收到恢复指令后从 checkpoint 续跑；与 HITL 共用中断-恢复机制，区别在无人工决策输入 |
| **HITL** | LangGraph `interrupt` 挂起节点 → 任务进入 `awaiting_human` 状态 → 通过 Gateway 通知人工 → 人工提交决策 → `resume` 继续 |
| **Resume** | 基于 checkpoint 的持久化执行：任意节点崩溃后从最近 checkpoint 恢复，幂等重放（副作用操作需幂等设计） |

**典型工作流**：

```
Start → Plan → [工具1] → [人工审批节点(HITL)] → [工具2] → Observe → End
                        ↑ 等待人工          │ 批准/驳回
```

**长任务执行模型**：
- 同步任务：短任务直接同步返回
- 异步任务：入队（Redis Streams）→ Celery Worker 执行 → 状态可查 + 事件流推送

**幂等设计**：外部副作用操作（下单、发消息）要求业务方提供幂等键，Resume 时靠幂等键避免重复执行。

### 4.8 Observability

**三层可观测，全链路打通。**

| 层 | 工具 | 采集内容 |
|----|------|----------|
| LLM 追踪 | Langfuse | 每次 LLM 调用的 prompt/token/成本/耗时/模型 |
| 链路追踪 | OpenTelemetry + Jaeger/Tempo | Runtime 节点间 span、Tool/Skill 调用链路 |
| 指标 | Prometheus + Grafana | QPS、延迟 P95、错误率、队列深度、token 消耗、成本 |
| 日志 | Loki + 结构化日志 | 业务日志、审计日志、错误堆栈 |

**关键设计**：
1. **TraceID 贯穿全链路**：Gateway 生成 `trace_id`，透传 Runtime/Tool/LLM/Storage，一条运行记录全链路可回溯。
2. **决策可审计**：记录 Plan/Decide 的完整「思考过程」（prompt、模型输出、选用的工具及理由）。
3. **成本看板**：按租户/Agent/模型维度聚合 token 与成本，支撑降本决策。
4. **告警**：错误率、队列堆积、成本异常、延迟超阈自动告警。

> 以上 Telemetry 数据的**可视化消费端**见 4.10 Agent Console（监测看板 + 执行流程跟踪）。

### 4.9 Evaluation

**评测闭环：离线保证质量，在线反馈迭代。**

```
  离线评测（发布前）                    在线评测（运行中）
┌──────────────────────┐        ┌──────────────────────┐
│ Golden Dataset        │        │ 用户反馈 / 结果采样    │
│ LLM-as-Judge          │        │ A/B 对比              │
│ 工具调用成功率         │        │ 隐式指标(留存/重试率)  │
└──────────┬───────────┘        └──────────┬───────────┘
           └────────── 指标汇总 → 回灌优化 ──────────┘
```

**核心指标**：
- **任务成功率**：端到端目标达成率
- **工具调用正确率**：选对工具 + 入参正确
- **回答质量**：LLM-as-Judge 打分（相关性、忠实度、帮助性）
- **幻觉率**：引用是否可溯源
- **效率**：平均步数、延迟、成本/任务

**评测机制**：
1. 离线：版本发布前跑 Golden Set 回归，质量劣化则阻断发布
2. 在线：抽样运行结果 + 用户点赞点踩，异步回灌标注
3. 实验：同场景多版本 A/B，指标显著提升才全量

### 4.10 Agent Console（可视化控制台与任务控制）

**定位**：Agent 平台的统一控制台，覆盖「监测 → 跟踪 → 控制 → 测试」四大能力，让 Agent 从「黑盒」变成**可观测、可干预、可调试**的白盒。

```
┌──────────────────────── Agent Console ────────────────────────┐
│                                                               │
│  ① 实时监测        ② 执行跟踪        ③ 任务控制     ④ 任务测试  │
│  Dashboard        Trace 图         暂停/恢复/取消    Playground │
│  指标/告警/成本    节点图/时间线     人工介入         回归/对比  │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

#### 4.10.1 实时监测（Monitoring Dashboard）

| 看板 | 内容 |
|------|------|
| 运行概览 | 当前运行数、成功率、平均耗时、QPS、错误率 |
| 队列看板 | 任务队列深度、Worker 数、堆积告警 |
| 成本看板 | 按租户/Agent/模型维度的 token 与成本趋势 |
| 资源看板 | CPU/内存/GPU 利用率（自托管模型场景） |
| 告警中心 | 阈值告警、事件流、告警订阅 |

#### 4.10.2 执行流程跟踪可视化（Trace 图）

把一次 Run 的完整执行过程可视化，支持逐节点下钻：

- **节点图（DAG）**：图形化展示 Plan → Decide → Execute → Observe 循环路径，每个节点标注状态（成功/失败/进行中/暂停/等待人工）
- **时间线（Timeline）**：按时间轴展示每步耗时、token、模型、工具调用
- **节点详情下钻**：点击任意节点查看入参/出参、prompt、模型输出、工具调用结果、报错堆栈
- **回放（Replay）**：按事件流回放一次运行，复现决策过程

> 数据来源：4.8 的 Trace/事件（以 `trace_id` 关联），控制台仅是消费端。
>
> 细化交互稿（布局线框 + 节点类型/状态配色 + 交互规范 + 时间线 + 控制闭环）见 **《核心设计图.md》第二部分**。

#### 4.10.3 任务控制（暂停 / 恢复 / 取消 / 人工介入）

| 控制 | 语义 | 实现 |
|------|------|------|
| **暂停 Pause** | 外部主动挂起当前执行 | 当前节点边界打 checkpoint，状态置 `paused`，等待恢复指令 |
| **恢复 Resume** | 从暂停点继续 | 从 checkpoint 恢复，继续执行 |
| **取消 Cancel** | 终止运行 | 标记取消，停止后续节点，回收资源 |
| **人工介入 HITL** | 需人工决策时挂起 | interrupt 节点，等人工 approve/reject/edit 后 resume |

**交互闭环**：

```
控制台点「暂停」→ Gateway 下发指令 → Runtime 当前节点完成后挂起
        → 状态经 SSE 推送控制台 → 用户点「恢复」→ 从 checkpoint 续跑
```

- 暂停/恢复与 HITL 共用 checkpoint 中断-恢复机制，区别：暂停由外部主动触发、无决策输入
- 所有控制动作进审计日志（谁在何时暂停/恢复了哪个 Run）

#### 4.10.4 任务测试台（Playground / Testing）

沙箱化的任务测试能力，供开发者上线前验证、调试 Agent：

- **Playground**：可视化配置输入（Agent + 版本 + 输入 + 模型/参数），即时运行并查看完整执行轨迹与输出，**不落正式业务数据**
- **回归测试**：导入 Golden Set（4.9），批量跑测试，生成通过率报告，阻断质量劣化版本
- **版本对比**：同输入多版本并排对比（输出、轨迹、token、成本、指标），支持 A/B
- **单步调试**：断点/单步执行、手动注入工具结果、模拟异常场景（工具失败、超时）

#### 4.10.5 可视化技术栈与安全

| 层 | 选型 |
|----|------|
| 前端框架 | React 18 + TypeScript（或 Vue3） |
| UI 组件 | Ant Design / Element Plus |
| 图表 | ECharts（指标/成本） |
| 图可视化 | AntV X6 / React Flow（执行 DAG、节点图） |
| 实时推送 | SSE / WebSocket（事件流、状态变更） |

**安全**：控制台所有查询与操作走 Gateway 鉴权，租户隔离；控制动作（暂停/恢复/取消）二次确认 + 审计留痕。

### 4.11 权限管理（IAM · RBAC + 资源授权）

**定位**：回答「谁（用户）能对什么（资源）做什么（动作）」。与 4.1 认证分工：**认证确认身份（你是谁），授权确认权限（你能干什么）**。属横切能力，Tool/Skill/Agent/Knowledge/Console 调用前统一走 `PermissionManager` 校验。

**对应两个需求**：
1. 不同用户不同权限 → **RBAC（功能权限）**
2. 不同 Skill/Tool 给不同用户授权 → **资源级 Grant（数据权限）**

```
         维度一：功能权限（RBAC）
  User ──m2m── Role ──m2m── Permission（资源:动作）

         维度二：资源授权（Grant）
  User / Role ── Grant（principal × resource × action）
```

#### 4.11.1 实体与关系

| 实体 | 说明 |
|------|------|
| User | 平台用户，归属 tenant |
| Role | 内置（admin/developer/operator/viewer）+ 自定义 |
| Permission | 功能权限点，形如 `agent:create`、`tool:register`、`run:execute`、`console:view` |
| Grant | 资源级授权：把某个具体 Skill/Tool/Agent/Knowledge 授权给某用户或某角色 |

**关系**：`User —m2m— Role`　`Role —m2m— Permission`　`Grant(principal, resource, action)`

#### 4.11.2 内置角色

| 角色 | 功能权限 | 典型场景 |
|------|----------|----------|
| admin | 全部（含用户/角色/授权管理） | 平台管理员 |
| developer | agent:create/edit、tool:register、skill:register、测试 | 业务方开发者 |
| operator | run:execute、console:view、run:pause/resume | 运营/客服 |
| viewer | 只读：agent/view、run/view、console/view | 审计/旁观 |

#### 4.11.3 资源级授权（你提的第 2 点）

把「谁能用哪个 Tool/Skill」落成 Grant，支持三种粒度：

| 粒度 | 示例 |
|------|------|
| 全量授权 | `grant(tool:calculator → 所有用户)` |
| 按角色授权 | `grant(tool:db_query → role:数据分析组)` |
| 按用户授权 | `grant(skill:refund → user:张三)` |

**Tool/Skill 默认门槛**（`permission` 声明）：`read`（人人可用）/ `write`（需授权）/ `admin`（高危，需授权 + HITL）。

#### 4.11.4 校验流程（调用 Tool/Skill 时）

```
Runtime 准备调用 Tool/Skill
   → PermissionManager.check(user, action, resource)
        ├─ ① 功能权限：user 的角色是否含该 action 的 Permission
        ├─ ② 资源授权：该 resource 是否有匹配的 Grant（user 或其角色）
        ├─ ③ 高危判定：permission=write/admin 或 requires_approval=true → 触发 HITL
        └─ 默认拒绝（default-deny）
   → 允许 / 拒绝(403) / 需人工确认
   → 审计留痕
```

**关键原则**：
- **默认拒绝**：未授权即拒绝，避免越权
- **拒绝优先**：deny 覆盖 allow（有任一拒绝规则即拒）
- **租户边界**：所有授权在 tenant 内生效，跨租户默认隔离
- **高危 HITL**：write/admin 级工具执行前人工确认（衔接 4.7）
- **全审计**：每次授权决策留痕（谁、何时、对什么、结果）

#### 4.11.5 数据模型

见 5.1 的 User / Role / Permission / UserRole / RolePermission / Grant 六张表。

#### 4.11.6 接口

见 6.1「权限管理（IAM）」端点。

### 4.12 插件体系（Plugin System · 能力可插拔）

**核心理念**：智能体的「通用性」不来自写死的能力，而来自**可插拔插件 + 配置组装**。平台只提供运行时 + 插件框架；具体某个 Agent（知识问答 / 短视频生成 / …）就是**一组插件的配置**。

```
          Agent = Runtime（思考循环）+ 插件组合（配置声明）

  ┌────────────────────────────────────────────────┐
  │                Agent 配置                       │
  │   system_prompt + 插件引用 + 参数 + 绑定关系       │
  └───────────────────────┬────────────────────────┘
                          │ 装配（运行时加载插件）
  ┌───────────────────────▼────────────────────────┐
  │          Plugin Runtime（插件框架）              │
  │  统一加载 · 生命周期 · 权限 · 观测 · 热插拔        │
  └──┬───────────┬───────────┬──────────┬──────────┘
     ▼           ▼           ▼          ▼
  Tool 插件   Skill 插件  Knowledge 插件  Model/Memory 插件
  （原子能力） （复合能力）  （知识源）    （模型/记忆后端）
```

#### 4.12.1 统一插件接口（Plugin Protocol）

```python
class Plugin(Protocol):
    kind: str                # tool | skill | knowledge | model | memory | node
    name: str
    version: str
    manifest: dict           # 元数据：描述 / 参数 / 权限 / 依赖
    async def setup(self, config: dict) -> None: ...          # 初始化
    async def invoke(self, ctx: InvokeContext, **kw) -> Any: ...  # 调用
    async def teardown(self) -> None: ...                     # 卸载
```

**插件清单（Manifest）关键字段**：`name / version / kind / description / parameters(JSON Schema) / permission / dependencies / requires_approval`

#### 4.12.2 插件类型 → 现有模块映射

| 插件类型 | 对应模块 | 例子 |
|----------|----------|------|
| Tool 插件 | 4.5 Tool Manager | calculator、http、数据库查询 |
| Skill 插件 | 4.4 Skill Manager | 退款流程、报告生成 |
| Knowledge 插件 | 4.6 Knowledge | 文档 RAG、KG、数据库知识源 |
| Model 插件 | LLM Gateway | 各家模型接入 |
| Memory 插件 | 4.3 Brain 存储后端 | Redis / 向量库 / 图库 |
| Node 插件 | 4.2 Runtime 自定义节点 | 自定义决策/反思逻辑 |

#### 4.12.3 插件生命周期

`注册 → 安装 → 配置 → 启用 → （运行）→ 停用 → 升级/卸载`，支持**热插拔**（版本切换不重启服务）。

#### 4.12.4 插件 SDK 与生态

第三方开发者按 Plugin Protocol 实现插件，通过 manifest 声明能力与权限，注册进 Registry 即被 Agent 引用；后续可扩展「插件市场」。

#### 4.12.5 示例：两个 Agent 的插件配置

**示例一：知识问答 Agent**

```jsonc
{
  "name": "知识问答助手",
  "system_prompt": "你是内部知识助手，基于知识库回答，附引用来源。",
  "plugins": [
    {"type": "model",     "ref": "model:deepseek-chat"},
    {"type": "knowledge", "ref": "knowledge:docs_rag", "config": {"top_k": 5}},
    {"type": "tool",      "ref": "tool:search"}
  ]
}
```

**示例二：短视频生成 Agent**

```jsonc
{
  "name": "短视频生成助手",
  "system_prompt": "你根据用户主题撰写脚本并生成短视频。",
  "plugins": [
    {"type": "model", "ref": "model:deepseek-chat"},
    {"type": "skill", "ref": "skill:script_writer"},                  // 脚本撰写
    {"type": "skill", "ref": "skill:video_render", "config": {"resolution": "1080p"}}, // 视频渲染
    {"type": "tool",  "ref": "tool:image_gen"},                      // 素材生成
    {"type": "tool",  "ref": "tool:tts"}                             // 配音
  ]
}
```

> 同一个平台、不同插件组合 = 不同的 Agent。这就是「通用智能体」的含义：**能力边界由插件定义，Agent 只是配置。**

## 5. 数据模型与存储

### 5.1 核心实体（ER 概览）

| 实体 | 关键字段 | 存储 |
|------|----------|------|
| Tenant | id、name、配额、配置 | PG |
| User | id、tenant_id、name、status | PG |
| Role | id、tenant_id、name、is_builtin | PG |
| Permission | id、code（如 agent:create）、description | PG |
| UserRole | user_id、role_id | PG |
| RolePermission | role_id、permission_id | PG |
| Grant（资源授权） | id、tenant_id、principal_type(user/role)、principal_id、resource_type、resource_id、action、approve | PG |
| Agent | id、name、system_prompt、runtime_config、skill/tool 绑定关系、版本 | PG |
| Skill | id、name、version、type、schema、manifest、owner | PG + 对象存储 |
| Tool | id、name、type、json_schema、权限声明、endpoint | PG |
| Run（运行实例） | id、agent_id、state、status、trace_id、cost、start/end | PG + checkpoint |
| Run Step（执行步骤） | id、run_id、node、action、input/output、tool、token、latency、status、seq | PG（时序分区） |
| Test Run（测试运行） | id、agent_id、version、input、expect、result、metrics、passed | PG |
| Vector Memory Entry（Brain） | id、tenant/user、content、embedding、importance、confidence、access_count、last_access、ttl | 向量库（pgvector/Milvus） |
| Memory Graph Node（Concept） | id、tenant/user、type、name、attributes | 图库（Neo4j）/ PG 邻接表 |
| Memory Graph Edge（Relation） | id、source、target、relation_type、weight | 图库 / PG 邻接表 |
| Persona | id、agent_id、role_profile、style、goals、constraints、version | PG |
| Knowledge Doc / Chunk | id、source、chunk_text、embedding、metadata | PG + 向量库 |
| Evaluation Record | id、agent_version、dataset、metrics、judge_result | PG |
| Audit Log | id、trace_id、actor、action、target、timestamp、detail | PG（分区） |

### 5.2 存储选型与规模策略

- **PG**：一切元数据与业务数据的「真相源」，开启审计分区表
- **Redis**：短期记忆、会话态、限流、队列、分布式锁、模型配额计数
- **向量库**：起步 `pgvector`（与 PG 同库，运维简单），数据量超千万级切 Milvus
- **对象存储**：文档原文、工件、embedding 缓存、日志冷备
- **图库**：KG 首期可用 PG 邻接表模拟，规模化后切 Neo4j

## 6. 接口设计

### 6.1 核心 API

```
# 运行管理
POST   /v1/agents/{agent_id}/runs          创建运行（同步/异步）
GET    /v1/runs/{run_id}                    查询运行详情
GET    /v1/runs/{run_id}/stream              SSE 流式事件
POST   /v1/runs/{run_id}/pause              暂停运行
POST   /v1/runs/{run_id}/resume             恢复运行（从 checkpoint 续跑）
POST   /v1/runs/{run_id}/cancel             取消运行
POST   /v1/runs/{run_id}/actions             HITL 提交决策（approve/reject/edit）
GET    /v1/runs/{run_id}/trace              执行流程（节点图 / 时间线 / 事件流）

# 测试 / 调试（Playground）
POST   /v1/agents/{agent_id}/test           单次测试运行（沙箱，不落正式数据）
POST   /v1/tests/{test_id}/compare          多版本对比测试
GET    /v1/tests/{test_id}                  查询测试结果

# Agent / Skill / Tool 管理
POST   /v1/agents                           创建 Agent（CRUD 略）
POST   /v1/skills                           注册 Skill（含版本）
POST   /v1/tools                            注册 Tool

# 权限管理（IAM）
POST   /v1/roles                             创建角色
POST   /v1/roles/{id}/permissions            给角色绑定权限
POST   /v1/grants                            资源授权（给用户/角色授权 Skill/Tool/Agent/Knowledge）
GET    /v1/grants?principal=u_1              查询某主体的授权列表
DELETE /v1/grants/{id}                       撤销授权
GET    /v1/users/{id}/permissions            查询用户最终权限（角色 + 授权展开）

# 知识
POST   /v1/knowledge/documents              上传文档（触发摄取）
POST   /v1/knowledge/query                  检索（供调试/评估用）

# 评测
POST   /v1/evaluations/runs                 触发离线评测
GET    /v1/evaluations/runs/{id}            查询评测结果
```

### 6.2 事件协议（SSE 流式）

运行过程中的事件统一推送给客户端，事件类型：

```
run.started / plan.created / tool.call_started / tool.call_completed
run.awaiting_human / run.resumed / token.stream / run.completed / run.failed
```

每条事件带 `run_id + trace_id + timestamp`，客户端据此渲染进度与流式输出。

### 6.3 错误码约定

| 类别 | 码段 | 示例 |
|------|------|------|
| 参数错误 | 4xx 业务码 | INVALID_ARGUMENT、RESOURCE_NOT_FOUND |
| 权限/配额 | 403/429 | PERMISSION_DENIED、RATE_LIMITED、QUOTA_EXCEEDED |
| 运行时 | 5xx | MODEL_UNAVAILABLE、TOOL_EXECUTION_FAILED、TIMEOUT |

## 7. 部署架构

```
                    ┌──────────────────────────────┐
                    │   Ingress (Nginx / APISIX)    │
                    └──────────────┬───────────────┘
                                   ↓
                    ┌──────────────────────────────┐
                    │   API Gateway (Kong/APISIX)  │
                    └──────────────┬───────────────┘
            ┌──────────────────────┼───────────────────────┐
            ↓                      ↓                       ↓
   ┌────────────────┐     ┌────────────────┐      ┌────────────────┐
   │ Agent Gateway  │     │ Runtime (副本×N)│      │ 知识摄取服务   │
   │ (副本×N)       │     │ HPA 自动扩缩    │      │ (Worker)      │
   └───────┬────────┘     └───────┬────────┘      └────────────────┘
           └──────────────────────┼───────────────────────┘
                                  ↓
        ┌──────────┬──────────┬──────────┬──────────┬──────────┐
        │ Postgres │  Redis   │ Milvus/  │  Neo4j   │ MinIO    │
        │ (主从)    │ (哨兵/集群)│ pgvector │  (可选)  │ /S3      │
        └──────────┴──────────┴──────────┴──────────┴──────────┘
        ┌──────────┬──────────┬──────────┐
        │ LiteLLM  │ Prometheus│ Langfuse │
        │ Gateway  │ + Grafana │ 追踪     │
        └──────────┴──────────┴──────────┘
```

**要点**：
- **无状态服务**：Gateway / Runtime 无状态，会话与状态放 Redis / checkpoint，支持任意横向扩展
- **HPA 指标**：CPU、队列深度（Celery 队列长度驱动 Worker 扩缩）
- **异步执行**：长任务走 Redis Streams + Celery，避免阻塞 API
- **灰度发布**：Agent/Skill 按版本灰度，新版本先小流量
- **容灾**：PG 主从 + 定期备份；Redis 哨兵；跨可用区冗余

## 8. 安全与合规

| 面 | 措施 |
|----|------|
| 身份与访问 | 认证 OIDC/OAuth2 + JWT；授权 RBAC + 资源级授权（详见 4.11）+ 租户隔离；服务间 mTLS |
| 数据安全 | 传输 TLS 1.3、存储加密；敏感字段脱敏（姓名/手机号/密钥）；PII 检测后拒绝落库 |
| 工具安全 | 最小权限 + 沙箱执行 + 高危操作 HITL 确认 + 全量审计 |
| Prompt 安全 | 注入攻击（Prompt Injection）防护：系统提示与工具输出隔离、指令优先级、越权工具调用拦截 |
| 模型合规 | 支持数据不出域（自托管模型路由）；模型输入输出审计留痕 |
| 密钥管理 | 统一 Secret 管理（Vault），密钥不进代码、不进日志 |

## 9. 性能与扩展性

| 指标 | 目标 |
|------|------|
| API 首字延迟（TTFT） | 流式 < 1s（云模型） |
| 端到端任务 P95 | 简单任务 < 5s，复杂任务按 SLA |
| 并发 | 单 Runtime 副本支撑数百并发会话（异步 IO） |
| 扩展 | Gateway / Runtime / Worker 均水平扩展；存储按数据规模分库分表/切分布式 |

**扩展路径**：
- 短期记忆压力 → Redis 集群 + 分级缓存
- 向量规模 → pgvector 迁 Milvus（分片）
- 多智能体协同 → LangGraph 多图嵌套 / 引入调度层
- 成本优化 → LiteLLM 路由策略（简单任务小模型、复杂任务大模型）+ 缓存命中复用
