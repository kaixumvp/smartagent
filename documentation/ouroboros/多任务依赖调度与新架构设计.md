# Ouroboros 多任务依赖调度与新架构设计

> 文档状态：目标架构提案，尚未实现。
> 基线：Ouroboros 2.0.0。当前实现以 [架构总结](./架构总结.md) 和代码为准；本文描述问题、目标及建议的后续改动，不代表现有功能已经具备。

## 1. 目标与结论

本文整理 Ouroboros 的现有框架结构，并设计一条从单 Agent 运行时演进到“可控任务图调度”的路径，重点回答：

- Agent 怎样区分必须按顺序执行的任务和可以独立执行的任务？
- 哪些任务可以并行，哪些即使没有数据依赖也必须串行？
- 多个任务的输出如何可靠地合并？
- 如何在保留当前轻量 Agent Runtime 的前提下加入 DAG 和多 Agent 能力？

**结论：保留 `AgentRuntime` 和现有 Plan → Decide → Execute → Observe 循环，新增可选的任务图编排层。**模型负责提出结构化任务和依赖关系；框架负责校验依赖、调度、收集结果和报告状态；宿主继续负责 Agent 配置解析、持久化、租户权限和外部任务投递。

调度不能只根据任务描述中的“先、再、同时”等自然语言词语判断，也不能将 LLM 返回多个工具调用直接视为安全并行。依赖由显式 DAG 表达；并行还必须满足执行器或宿主的安全策略。

## 2. 当前框架架构

### 2.1 分层与边界

```text
宿主（PlatformAgent 等）
  ├─ 解析 Agent、插件、权限及租户配置
  ├─ 实现持久化、记忆、知识、事件和 checkpoint 等适配器
  └─ 通过 ouroboros.ports 注入能力
          │
          ▼
Ouroboros AgentRuntime.run / resume
  ├─ Plan → Decide → Execute → Observe 状态机
  ├─ PluginRegistry → Tool / Skill / Knowledge
  └─ 横切机制：重试、熔断、超时、预算、审批、事件、追踪
          │
          ▼
LLM / Tools / Skills / Memory / Knowledge / Checkpointer
```

Ouroboros 不依赖 PlatformAgent 的 HTTP、数据库、租户模型或配置。跨层契约集中在 `ouroboros.ports`；宿主可替换端口实现。

### 2.2 单 Agent 运行流程

```text
AgentRuntime.run()
  → 初始化上下文、记忆和 AgentState
  → plan：LLM 生成描述型步骤清单
  → decide：LLM 根据消息、计划和可用工具选择动作
  → execute：授权并调用插件
  → observe：写回工具结果
  → decide / execute / observe 循环
  → completed / failed / awaiting_human
```

当前状态机由 `core/runtime.py` 手动驱动，而非由 LangGraph 执行。Plan 当前是 `description` 和 `status` 构成的步骤数组，供 Decide 参考；它不是可执行任务图，也不承担调度职责。

### 2.3 扩展与宿主契约

| 当前部分 | 职责 |
|---|---|
| `AgentRuntime` | 单个 Agent 的运行、暂停与恢复 |
| `AgentState` | 单次 Agent 运行的内部共享状态，不是宿主数据库 schema |
| `PluginRegistry` | 注册和调用统一的 Plugin；Tool、Skill、Knowledge 通过此处接入 |
| `RuntimeDeps` / `ports.py` | 注入 LLM、权限、记忆、知识、事件、指标、checkpoint 等能力 |
| `AgentSkill` / `SubagentRunner` | 父 Agent 委派到子 Agent；当前子 Agent 结果以字符串返回 |
| `EventSink` / `Tracer` | 产出运行事件和追踪信息；事件传输、持久化由宿主实现 |
| `Checkpointer` | 当前用于审批暂停后的恢复；生产存储由宿主实现 |

### 2.4 当前已有的并发与恢复边界

- `execute.py` 会并发执行同一轮 LLM 返回的多个 tool calls。这是调用轮次级并行，不会分析计划步骤之间的数据依赖。
- `plan.py` 不输出 `depends_on`、输入输出类型或任务状态转移；运行时没有 DAG 校验器或就绪队列。
- `AgentSkill` 的子 Agent 调用是父子委派，不是团队级任务分解、共享状态或结果聚合。
- `RunResult` 和子 Agent 结果以自然语言/字符串为主，缺少任务图需要的稳定结果结构。
- `step.completed` 记录的是运行时节点级信息，不是有完整关联 ID 的 task/tool 生命周期。
- 当前 checkpoint 主要服务于审批：恢复时会从被阻塞的 execute 前重跑该步骤。它不等于任意任务图的崩溃恢复；有副作用的重跑必须另行解决幂等问题。

## 3. 已识别的缺点与风险

### 3.1 任务规划没有依赖语义

自然语言子步骤无法明确表示“任务 B 使用任务 A 的结果”。模型可能漏掉依赖、推断错误，或仅凭措辞把本可并行的任务排成串行。

### 3.2 执行计划与运行状态没有闭环

当前计划没有 `ready/running/done/failed/blocked` 的调度状态，也没有任务级结果仓库。因此无法可靠地调度“所有依赖完成后启动”的任务、只重试失败分支，或在界面展示任务图。

### 3.3 同轮工具调用并发缺少副作用策略

`asyncio.gather` 并发执行多工具调用，但“同一轮返回”不保证这些调用互相独立，也不保证外部写操作可并发或可重试。尤其是支付、发信、写数据库等操作，重复执行可能产生真实副作用。

### 3.4 输出与合并没有契约

多个 Agent 的自由文本结果可能字段缺失、格式不一致或互相冲突。直接拼接字符串不能证明汇总完整，也不适合作为下游任务的稳定输入。

### 3.5 子 Agent 的结果语义不足

当前子 Agent 端口以字符串返回，父运行难以区分成功、部分成功、审批暂停、失败、可重试错误或结构化输出；总预算和取消信号也不构成明确的树级契约。

### 3.6 可观测与持久化无法覆盖 DAG 生命周期

目前没有标准的 task queued/started/retried/blocked/completed 事件和 task ID 关联；现有 checkpoint 不能保证任务图在进程中断后安全续跑。

### 3.7 模型规划不能取代运行时校验

LLM 适合提出依赖图，不应被当作依赖图正确性、权限或并发安全的最终裁判。图结构错误、资源冲突和越权必须由确定性代码拒绝或处理。

## 4. 目标架构

### 4.1 分层原则

```text
Host API / Service
  ├─ 读取并授权 Agent、工具和数据
  ├─ 提供 TaskExecutor、持久化和事件适配器
  └─ 负责部署级 queue / worker（如确有需要）
          │
          ▼
Optional TaskGraphRuntime（新增，可选）
  ├─ Plan：生成 TaskGraph
  ├─ Validate：校验 ID、依赖、环、输出引用和策略
  ├─ Schedule：选出 ready 且允许并行的任务
  ├─ Execute：经 TaskExecutor 执行任务
  ├─ Collect：按 task_id 收集 TaskResult
  └─ Aggregate：校验/汇总结果，形成图级结果
          │
          ├── Agent task → 现有 AgentRuntime.run()
          ├── Tool task  → 宿主提供的执行器 / 现有 Plugin 能力
          └── Code task  → 可选的确定性纯函数节点
```

`AgentRuntime` 继续负责单个 Agent 内部的对话和工具循环。`TaskGraphRuntime` 管“任务之间”的依赖和调度，不把现有单 Agent 状态机改造成必选图框架。

### 4.2 核心数据结构（目标）

```json
{
  "id": "compare_products",
  "description": "比较两个产品并提出建议",
  "depends_on": ["research_a", "research_b"],
  "input_from": {
    "product_a": "research_a",
    "product_b": "research_b"
  },
  "output_schema": {
    "type": "object",
    "required": ["summary", "recommendation"],
    "properties": {
      "summary": {"type": "string"},
      "recommendation": {"type": "string"}
    }
  },
  "executor": {"kind": "agent", "ref": "analyst"}
}
```

建议的核心类型：

| 类型 | 作用 |
|---|---|
| `TaskSpec` | 稳定的 task ID、描述、显式依赖、输入映射、输出 schema、执行器引用 |
| `TaskGraph` | 任务集合、入口参数和图级汇总配置 |
| `TaskResult` | task ID、状态、结构化输出、错误、用量、耗时、关联 run ID |
| `TaskGraphResult` | 图级状态、各任务结果、最终聚合输出及失败/阻塞清单 |

状态至少区分 `pending`、`ready`、`running`、`completed`、`failed`、`blocked`、`canceled`。这些是目标数据契约，不是当前 `PlanStep` 已支持的状态。

### 4.3 依赖识别与并行判定

1. Planner 先将用户请求拆成有明确输入、输出和执行目标的任务。
2. Planner 为每个任务输出 `depends_on`：只有当任务确实需要另一个任务的输出、或存在明确的先后约束时才建立边。
3. `TaskGraphValidator` 确认所有依赖都存在、ID 唯一、无自依赖、无环，且输入引用与依赖相符。
4. 调度器从未完成任务中选择所有依赖均已完成的任务，形成 ready 集合。
5. ready 不代表一定并行：还需经过执行策略检查。执行器/宿主没有明确声明可并行时，按串行执行。
6. 如果模型无法确定依赖，先向模型发起一次有边界的修正，或把有歧义的任务串行化；不能通过隐式猜测放宽安全策略。

示例：

```text
research_a ─┐
            ├─► compare ─► recommend
research_b ─┘
```

`research_a` 与 `research_b` 可同时进入 ready 集合；`compare` 必须等两者结果可用；`recommend` 必须等 compare 完成。DAG 依赖决定“何时可运行”，策略决定“是否允许并发”。

### 4.4 安全并发策略

- 初期只并行明确声明为并行安全的任务；策略缺失时默认串行。
- 在 Plugin/TaskExecutor 层提供执行元数据，例如 `parallel_safe`、`idempotent` 和资源/副作用类别。Planner 自己声明“只读”不能作为可信依据。
- 配置最大并发数、每任务超时、图级超时及总 token/成本预算。
- 有写入或外部副作用的节点默认串行；若允许重试，执行端必须提供幂等保障或去重键。
- 同一并行批次中任何任务失败时，保留已经完成的结果；只重试符合策略的失败任务；其下游任务标记 `blocked`，无关分支可继续或按图级策略终止。

### 4.5 结果传递与合并

1. 每个结果按 `task_id` 保存，不依赖完成先后顺序。
2. 下游输入按 `input_from` 从已完成 `TaskResult.output` 构造，并对照 schema 校验。
3. 聚合前进行字段校验、来源追踪和冲突检测；确定性数据由代码合并，开放式文字结论才交由汇总 Agent。
4. 汇总输出保留来源 task ID 和失败/缺失项。不得将失败伪装成空字符串或“成功”。
5. 若结果 schema 校验失败，优先报告具体任务和字段；只有明确可修复的格式错误才允许有限次修复，不重跑已产生副作用的任务。

### 4.6 事件、恢复和取消

任务图增加稳定事件：`task.queued`、`task.started`、`task.retrying`、`task.completed`、`task.failed`、`task.blocked`、`task.canceled`、`task_graph.completed/failed`。事件至少包含 `graph_run_id`、`task_id`、父子 `run_id`、`trace_id`、时间和脱敏后的数据。

若要支持进程中断恢复，checkpoint 必须持久化图定义版本、各任务状态、成功输出、尝试次数和可重放信息。恢复时只调度尚未完成且可安全执行的任务；不能默认重跑所有 Agent/Tool 节点。持久化和跨进程任务队列仍由宿主提供。

取消应从图级上下文传递到正在运行的子任务；取消父图后，停止继续派发新任务，并按执行器能力取消在途任务。

## 5. 建议的改动点

### 5.1 Ouroboros 框架层

| 改动 | 建议位置 | 目的 |
|---|---|---|
| 新增任务图类型和校验 | `ouroboros/tasks/`（建议新目录） | 定义 `TaskSpec`、`TaskGraph`、结果类型、拓扑与输入引用校验 |
| 新增可选图执行入口 | `ouroboros/tasks/runtime.py` 或同等模块 | 实现 ready-set 调度、并发上限、失败传播和取消 |
| 新增任务执行端口 | `ouroboros/ports.py` | 用结构化结果调用宿主执行器，避免框架依赖业务 Agent 存储 |
| 调整 Planner | `core/nodes/plan.py` 或新的 task planner | 从自然语言步骤扩展为结构化图计划；LLM 失败不得生成无效 DAG |
| 明确并发安全元数据 | `PluginManifest` 或执行器策略 | 不依赖 LLM 对副作用和并发安全的自我判断 |
| 补足事件模型 | `events/events.py` | 支持 task 生命周期、重试、父子 run 关联和图级结束事件 |
| 扩充预算/取消上下文 | `RuntimeConfig`、`RunContext` 或图级 context | 约束总耗时、成本、并发和整棵运行树的取消 |
| 保持向后兼容 | 现有 `AgentRuntime`、`AgentSkill`、`RunResult` | 现有单 Agent 调用默认行为不变；新图能力作为显式 opt-in |

具体类型名称、字段和新目录应在实现前通过 API 兼容性评审确定；表格中的名称是建议，不是已冻结接口。

### 5.2 PlatformAgent 宿主层

- 为图执行提供 TaskExecutor：将 task 的 Agent 引用解析成租户内可用的 AgentDefinition，并通过现有 Runtime 启动子运行。
- 将 `TaskResult` 状态、结构化输出、用量、错误和父子关系持久化；保持现有多租户过滤。
- 实现并发/副作用安全策略、幂等键以及持久化 checkpoint；框架只定义协议，不读取业务数据库。
- 更新 Skill 配置 UI：选择 Agent 并写入运行时实际读取的 `agent_ref`，而不是仅保存通用 definition。
- 前端展示任务 DAG、就绪/运行/阻塞/失败状态、各节点输入输出、重试记录和最终合并结果。

### 5.3 测试与文档

- 图校验：不存在的依赖、自依赖、循环、重复 ID、无效输入引用。
- 调度：独立任务并行、依赖任务等待、并发上限、默认串行策略。
- 故障：部分失败、下游 blocked、只重试失败节点、取消传播、超预算停止。
- 合并：按 task ID 稳定收集、schema 错误、缺失结果、冲突和来源保留。
- 恢复：成功节点不重复执行；副作用节点没有幂等保障时不自动重放。
- 集成：单 Agent `run()`、`resume()`、现有 AgentSkill 和宿主父子 run 关联继续工作。

## 6. 分阶段实施建议

### 阶段 0：现状基线与契约

- 确认任务图与单 Agent Runtime 的责任边界。
- 定义 task/result/event 数据结构和版本兼容策略。
- 明确首批并行安全执行器及“未知即串行”的默认规则。

### 阶段 1：纯框架 DAG 最小闭环

- 先实现结构化 `TaskGraph`、静态校验、内存态有界调度和结构化 `TaskGraphResult`。
- 使用 fake executor 做并行、依赖、合并和失败测试，不引入队列或数据库。
- 初版只覆盖明确安全的只读 Agent 任务和确定性汇总；单 Agent 原入口保持不变。

### 阶段 2：宿主接入与 UI

- PlatformAgent 实现 TaskExecutor、权限检查、持久化及父子 run 关联。
- 补齐 Agent Skill 的 Agent 选择与 `agent_ref` 配置。
- UI 显示 DAG 执行时间线、输入输出、失败原因和结果汇总。

### 阶段 3：可靠恢复与更复杂协调

- 增加图级持久化恢复、幂等和副作用策略。
- 引入失败分支重试、受控 re-plan、树级取消和总预算传播。
- 再评估顺序流水线、并行专家、协调者汇总等 Team 模式。

每阶段都应先满足可观测、可控和可测试，再扩大 Agent 自主权。暂不建议直接实现开放式 Agent 间讨论、无限重规划或自动执行任意写操作。

## 7. 不做的事与架构决策

- **不替换现有 AgentRuntime**：它继续作为轻量单 Agent 执行器。
- **不默认引入 LangGraph**：当前可用显式 DAG 调度满足需求；只有当需要通用状态图、分支循环、子图和成熟持久化时，再基于实测评估引入。
- **不把任务规划交给模型独占**：模型输出需要确定性验证，非法计划不得执行。
- **不把“无依赖”误解为“安全并行”**：数据依赖与资源/副作用约束是两类判断。
- **不把整套队列系统放进框架包**：跨进程调度、重试队列和部署运维属于宿主或专用执行平台。
- **不把自然语言拼接当作聚合**：下游依赖必须使用带 schema 的任务结果。

## 8. 验收标准（目标）

1. 给定两个无依赖且显式允许并行的任务和一个依赖两者的任务，两个前置任务可并行启动，汇总任务只能在两者完成后运行。
2. 任意环、缺失依赖或无效输入引用在执行前被拒绝，并提供可定位的错误。
3. 未声明并行安全的任务不会因 LLM 输出多个调用而自动并发。
4. 结果按 task ID 稳定保存并通过 schema 校验；失败、阻塞和部分成功均可区分。
5. 图级预算、并发上限和取消可限制子任务；事件能关联到对应图、任务和子运行。
6. 现有单 Agent API、HITL `resume()` 和父子 AgentSkill 调用保持兼容。
