# Ouroboros 上下文管理设计方案

> 文档状态：设计提案，尚未实现。
> 适用基线：Ouroboros 2.0.0。当前实现以代码和[架构总结](./架构总结.md)为准。

## 1. 背景与目标

Agent 每次请求模型时，实际输入不只是聊天记录，还包含系统提示、当前任务、计划、工具 schema、工具调用历史、工具返回结果和记忆。随着任务持续运行，这些内容可能不断累积，造成：

- 请求超出模型上下文窗口，或者留给模型输出的空间不足；
- 工具 schema 和重复历史占用大量输入 token，增加成本和延迟；
- 大型 MCP/API 响应挤掉用户目标和关键任务状态；
- 为压缩上下文而随意删除消息，破坏 tool call 协议关系、来源追踪或任务正确性；
- 日志无法解释某次请求究竟被哪些上下文内容占满。

本方案目标是为每次模型调用构造**有预算、可追溯、符合消息协议的上下文视图**，同时保留完整运行记录供宿主审计和排错。

设计边界：

1. 完整对话/运行记录与“本次发送给模型的输入”分离。
2. token 预算在请求发出前检查，而不是只在收到模型 usage 后累计。
3. 先保护系统规则、当前用户目标和未完成任务状态，再裁剪低优先级内容。
4. 历史压缩、记忆选择、工具 schema 和工具输出使用统一预算。
5. 不静默丢弃内容；裁剪、摘要、截断和预算不足均有明确状态。
6. 框架负责纯逻辑组装与预算控制；数据库、文件/对象存储和完整运行记录由宿主实现。

## 2. 当前实现基线与问题

### 2.1 当前请求如何组装

- `AgentRuntime.run()` 将输入 `history` 放入 `AgentState.messages`；如果 `history` 非空，当前实现不会自动把本次 `task` 再追加进去。因此宿主传入的历史必须已经包含当前用户轮次，避免本轮任务遗漏或重复注入。[runtime.py](../../application/ouroboros/ouroboros/core/runtime.py)
- `decide` 每轮构造系统提示、当前计划和完整 `state.messages`，再把所有注册插件转成的工具 schema 传给 LLM。[decide.py](../../application/ouroboros/ouroboros/core/nodes/decide.py)
- `observe` 将工具结果追加到消息历史；下一轮 Decide 会再次发送这些消息。[observe.py](../../application/ouroboros/ouroboros/core/nodes/observe.py)
- Tool schema 来自 `PluginRegistry.to_openai_schema()`；Runtime 当前构建完整 schema 列表，没有本轮上下文预算或工具候选筛选机制。[registry.py](../../application/ouroboros/ouroboros/plugins/registry.py)
- `RuntimeConfig.max_total_tokens` 根据模型响应返回的 usage 累计。它能限制运行总用量，但不能在调用前保证 prompt 未超过模型窗口。
- MCP 客户端将返回的文本块组合成字符串，没有统一的上下文输出上限或大型结果引用机制。[mcp.py](../../application/ouroboros/ouroboros/tools/mcp.py)
- Working Memory 的会话窗口限制不等于单次 Run 的消息压缩；两者是不同数据路径。[working.py](../../application/ouroboros/ouroboros/memory/working.py)

因此，现有机制有运行轮数、运行总 token 和工作记忆窗口等限制，但**尚无统一的每次 LLM 请求上下文准入、分项预算和压缩策略**。

## 3. 核心概念：三份数据，不混用

```text
完整记录（Transcript / Run Record）
  完整保存用户轮次、assistant/tool 消息、运行步骤与原始结果；
  用于审计、重放、排错，不直接等同于每次模型输入。

运行状态（Execution State）
  当前任务、计划、未完成动作、审批状态、关键结构化结果；
  用于驱动执行，体积应受控，不依赖把所有旧消息塞进 prompt。

上下文视图（Context View）
  针对某次模型调用，从运行状态、最近对话、摘要、记忆和工具 schema
  中选择、压缩、排序后形成的有限输入。
```

完整记录原则上由宿主持久化。框架运行期间可维护消息状态，但 Context Builder 不得为了节省模型 token 而删除或覆盖唯一的原始记录。

## 4. 目标架构

```text
RuntimeState + 当前任务 + History + Memory + Plugin Schemas
                       │
                       ▼
             ContextBuilder.build()
       ├─ 规范化消息及 tool-call/result 配对
       ├─ 确定模型上下文窗口和输出预留
       ├─ 估算各来源 token 并生成预算明细
       ├─ 选择相关记忆和本轮工具 schema
       ├─ 必要时压缩旧历史、限制工具输出
       └─ 超预算时明确拒绝，不静默丢失关键输入
                       │
                       ▼
              LLMGateway.chat(...)
                       │
                       ▼
         用量反馈、裁剪原因和诊断指标
```

Context Builder 作为纯逻辑组件接收明确输入并返回 `ContextBuildResult`；它不自行访问数据库、MCP 服务或宿主 API。

### 4.1 建议数据类型

具体名称和字段需要在实现前审查公共 API 兼容性。以下仅表达设计职责：

| 类型 | 职责 |
|---|---|
| `ContextPolicy` | 模型窗口、回复预留、安全余量、来源预算、工具数量/结果限制和压缩策略 |
| `ContextItem` | 一项候选上下文及其来源、优先级、保护级别、内容和估算 token |
| `ContextUsage` | 按 system、task/state、history、summary、memory、tools、tool_results 分项的 token 估算 |
| `ContextBuildResult` | 最终 messages、tools、预算统计、压缩/截断记录和是否可安全发送 |
| `TokenEstimator` | 按模型或 tokenizer 估算消息与工具 schema token 的端口/协议 |
| `ContextBudgetExceeded` | 必需上下文仍超预算时的明确失败类型，包含预算分项，不含未脱敏正文 |

### 4.2 组件架构与责任

```text
AgentRuntime
  ├─ 维护 canonical run state / 消息记录
  ├─ 在每个 LLM 请求前调用 ContextPipeline
  └─ 只将已构建的请求交给 LLMGateway

ContextPipeline（建议位于 ouroboros/core/context/）
  ├─ ModelProfileResolver：解析模型窗口、输出预留和估算器
  ├─ ToolSelector：从 Agent allowlist 中生成本轮候选工具
  ├─ HistorySelector：按完整消息单元选择近期历史
  ├─ MemorySelector：按相关性和预算选择记忆
  ├─ ContextCompactor：压缩可压缩内容，不改写原始记录
  ├─ TokenEstimator：估算最终 messages + tools 的 token
  └─ ContextDiagnostics：产生分项预算和变更记录

Plugin/Tool 执行结果
  └─ ResultLimiter：限制进入后续模型上下文的结果；可选委托宿主 ArtifactStore

宿主适配器
  ├─ 提供模型 profile / 精确 tokenizer（若框架不内置）
  ├─ 持久化完整 transcript、摘要元数据和大型结果 artifact
  └─ 决定租户范围、Agent allowlist、保留期和敏感数据策略
```

职责边界：

| 组件 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| `ModelProfileResolver` | 模型标识、宿主配置 | 窗口、回复上限、估算器及精度说明 | 猜测未知模型能力 |
| `ToolSelector` | Agent 已授权插件、当前任务、预算 | 本轮候选 schema 和稳定插件 ID 映射 | 扩大 allowlist 或授予权限 |
| `HistorySelector` | canonical messages、运行状态、预算 | 完整消息单元组成的历史视图 | 删除/覆盖原始 transcript |
| `MemorySelector` | 已召回记忆、当前任务、预算 | 有序且限额的记忆项 | 自行查询数据库或改变记忆权限 |
| `ContextCompactor` | 候选上下文和分项预算 | 摘要/裁剪后的候选视图与审计记录 | 把摘要写回原始对话 |
| `TokenEstimator` | provider 格式化前最终请求 | 分项和总量估算 | 将估算伪装成 provider 精确 usage |
| `ResultLimiter` | 插件输出、工具元数据、限制策略 | 有界文本/结构化输出或授权 artifact 引用 | 静默截断或私自持久化业务数据 |
| `ContextPipeline` | 上述候选项、ContextPolicy | 最终 `ContextBuildResult` 或明确失败 | 调用模型、做业务 IO |

`ContextPipeline` 本身应保持确定性、无网络 IO，便于单元测试。若后续需要 LLM 生成摘要，应由显式、预算受限的 `Summarizer` 组件执行；该调用不得递归触发同一上下文压缩流程。第一阶段建议使用确定性保留/截取策略，后续再评估模型摘要的质量、费用和风险。

### 4.3 与现有 Runtime 的请求时序

每次 Plan/Decide 等 LLM 调用都应经过同一请求构建流程；特别是 Decide 的 tools schema 必须参与同一次预算计算。

```text
AgentRuntime._drive
  └─ run node (plan / decide)
      ├─ 收集 canonical state、system prompt、当前 plan
      ├─ ToolSelector 从当前 Agent allowlist 选择候选工具
      ├─ ContextPipeline.build(model, messages, tools, policy)
      │    ├─ 解析 model profile / output reserve
      │    ├─ 按优先级组装受保护内容
      │    ├─ 计算 history / memory / tools / results 分项预算
      │    ├─ 必要时压缩并重新估算
      │    └─ 返回 ContextBuildResult 或 ContextBudgetExceeded
      ├─ LLMGateway.chat(result.messages, result.tools)
      ├─ 记录估算 token、实际 usage 和 compaction 记录
      └─ 继续现有状态机

PluginRegistry.invoke
  └─ Plugin / Tool 执行
      └─ ResultLimiter 在结果进入 state/messages 前限制大小
```

关键接入规则：

- `_build_registry()` 产生的 Agent 插件集合是权限和配置范围，不直接等于每次请求的候选集合。静态模式下候选集合就是显式绑定集合；动态模式下只能取其子集。
- 当前 `run_plan()` 也会调用 LLM，因此不能只在 `decide` 节点做预算；Plan 请求同样需要 ContextPipeline，但它不需要工具 schema。
- `AgentRuntime._drive()` 目前一次性生成 `tool_schemas` 并向所有节点传递。接入后应在每次需要 LLM 的节点调用前构建该次请求，避免计划阶段/工具阶段配置不一致。
- Context 构建失败属于请求准入失败，不应按普通瞬态 LLM 错误重复重试；否则重试会重复相同的超预算请求。
- `RunResult`/step diagnostics 可记录预算摘要和错误码；不应把完整 prompt 或未脱敏工具数据放入事件。

### 4.4 数据流与状态所有权

```text
宿主加载/持久化的 canonical history ─┐
当前 task 与本轮运行状态 ────────────┤
已召回 memory ───────────────────────┤
Agent plugin allowlist ──────────────┤
模型/上下文策略 ─────────────────────┘
                     │
                     ▼
             本次 Context View
             （临时、可丢弃、可重建）
                     │
                     ▼
                 LLM Request

插件原始结果 ──► 有界处理 ──┬─► 小结果：写入 run state / transcript
                            └─► 大结果：宿主 artifact + 有界引用
```

- canonical history 是消息协议和审计的事实来源；Context View 只为单次请求服务，不应反写为完整对话。
- Context View 必须保留原始消息/tool-call ID 的关联；如生成摘要，摘要需记录覆盖的消息范围和来源 ID。
- 大型 MCP 结果是否存入 artifact 由宿主策略决定。若未提供 ArtifactStore，ResultLimiter 只能返回明确标记的有界结果，不能声称完整结果仍可恢复。
- LLM 请求成功后的 assistant/tool 消息仍按既有 runtime 协议更新 canonical state；后续请求再次从最新 canonical state 构造新的视图。

### 4.5 建议的内部调用契约

以下为说明职责的伪代码，非已冻结 API：

```python
request = await context_pipeline.build(
    model=model,
    system_prompt=system_prompt,
    task=state["task"],
    plan=state.get("plan") or [],
    messages=state.get("messages") or [],
    memory=state.get("memory_ctx") or [],
    allowed_plugins=registry.all(),
    output_reserve=policy.max_output_tokens,
    policy=policy,
)

response = await deps.llm.chat(
    messages=request.messages,
    model=model,
    tools=request.tools or None,
)
```

建议契约属性：

- 输入包含模型 ID、provider 请求所需 messages/tools、各类预算、允许压缩范围和稳定来源 ID。
- 输出包含最终 messages/tools、token 估算及其精度、逐来源统计、裁剪/摘要动作、所用插件 ID 和必要的安全提示。
- 预算不足通过明确异常或结果联合类型返回；不得输出一个看似有效但丢掉必需输入的请求。
- 结果中不携带可变的共享列表；单次请求的 Context View 不得污染 Agent 原始 state。
- 压缩策略和 TokenEstimator 可通过明确接口替换；接口版本变更需符合 Ouroboros 公共 API 的 SemVer 承诺。

### 4.6 并发、缓存与一致性

- ContextPipeline 只读取本次 run 的不可变快照；同一 run 不能由多个并发节点同时修改共享消息列表。
- Token 估算可缓存纯输入结果，但缓存键必须涵盖模型/tokenizer 版本、messages、工具 schema、输出预留和格式配置；任何输入变化都必须使缓存失效。
- 不缓存基于模型内容的历史摘要，除非键包含完整来源范围、摘要策略/模型版本和策略版本，且摘要可追溯。
- 动态 ToolSelector 的选中 ID 必须在执行时映射回同一个注册插件；插件被撤销、禁用或权限变化时，执行前再次拒绝。
- 诊断中的估算与实际 usage 关联到同一模型请求 ID，避免把多轮请求的 token 混算。

## 5. 请求预算模型

定义：

```text
模型输入上限 = 模型上下文窗口 - 最大回复预留 - 安全余量
```

Context Builder 对最终请求做 token 估算。估算必须计入：

- system prompt、平台级规则和当前计划；
- 当前用户任务、最近历史和历史摘要；
- 记忆召回内容；
- 工具调用记录和工具结果；
- 本轮传入的工具名称、描述和参数 schema；
- provider 请求格式自身可能增加的开销。

若 provider/model 能提供可信的上下文窗口和 tokenizer，优先使用它们。否则由宿主配置明确的保守模型能力与 estimator；字符数估算只能作为注明精度的回退，不能被当成准确 token 计数。

模型输出预留必须在发送前扣除。若 prompt 估算已经超过输入上限，按压缩策略重建并重新估算；压缩后仍超限则返回明确预算错误，不能继续发送可能必然失败的请求。

`max_total_tokens` 继续承担“运行总量”限制；每请求输入预算是不同控制项，两者并存：

| 控制项 | 目的 | 检查时机 |
|---|---|---|
| 单请求输入预算 | 防止单次 prompt 超模型窗口 | 每次调用模型之前 |
| 最大回复预留 | 为模型输出留空间 | 每次构建上下文时 |
| Run 总 token 预算 | 限制整次运行消耗 | 请求 usage 返回后累计，并在后续请求前阻止继续 |
| 每个来源预算 | 防止 history、memory、tools 或结果占满全部输入 | Context Builder 内 |

## 6. 上下文选择与压缩顺序

### 6.1 保护级别与优先顺序

建议将上下文分为三类，而不是对消息按字符数简单截断：

**必须保留（Protected）**

- 系统提示、安全和权限规则；
- 当前用户目标及当前轮必要的输入；
- 当前执行阶段、待处理审批和未完成任务状态；
- 保证消息协议有效所需的完整 tool call 与对应结果；
- 下游决策依赖的关键结构化结果。

**按相关性选择（Relevant）**

- 与当前目标相关的长期记忆；
- 当前任务仍需引用的旧事实、决策、工具证据；
- 当前 Agent 本轮允许使用的工具定义。

**可压缩或可淘汰（Compressible）**

- 已完成且不再影响后续的早期对话；
- 已完成工具调用的冗长原文（需保留摘要、来源及可追溯引用）；
- 与当前目标弱相关的记忆；
- 非候选工具的完整 schema。

压缩策略不得改变授权结果；工具候选筛选只影响模型看到的工具，不替代执行时权限检查。

### 6.2 每次请求的构建算法

1. 解析并校验输入消息，确认当前任务存在，消息角色及 tool-call/result 关系合法。
2. 加入必须保留内容，计算当前请求预算和输出预留。
3. 基于任务相关性选取记忆，并受总记忆预算限制。
4. 选择本轮可用工具 schema；优先使用 Agent 已绑定的最小工具集，之后才考虑动态发现。
5. 从最近的**完整对话单元**向前加入历史；不得把 assistant tool call 与其结果拆开。
6. 若超预算，依次压缩早期历史、删减低相关记忆、减少工具候选、缩短可压缩结果；每次变更后重新估算。
7. 若仍超预算，返回 `ContextBudgetExceeded` 和分项诊断；不得静默删掉当前任务或系统规则。
8. 输出最终 `ContextBuildResult`，记录估算器类型、预算占用和采取的压缩动作。

### 6.3 历史摘要

- 将旧历史压缩为带时间范围、来源消息 ID 和覆盖范围的摘要；摘要是模型输入视图，不替代完整原始 transcript。
- 保留用户明确目标/约束、已确认事实、未完成项、重要决策、工具结论及其来源、已知不确定性。
- 摘要刷新应有阈值和最大长度，避免每轮都额外调用模型；摘要调用也消耗 token，应纳入 Run 总预算或单独配置的压缩预算。
- 摘要生成失败时显式记录并采用有界历史回退；不能把摘要失败伪装成完整压缩成功。
- 摘要中的用户文本和工具结果仍是不可信输入，需保持现有工具结果边界标注和安全策略。
- 重要事实应保存来源引用，必要时能从宿主记录中重新取回原始证据。

### 6.4 记忆预算

- 记忆召回应同时受相关性、数量和总 token 预算约束，而不只是 `top_k`。
- 先选与当前任务直接相关的条目；无关记忆不因为“已召回”就自动进入 prompt。
- 记忆内容标记来源与时间；与本轮用户要求冲突时，应优先遵循当前明确指令，并让模型知道该条目是历史记忆。
- 将记忆预算纳入整体输入预算，不能与 history、tools 和 tool result 各自独立地无限追加。

### 6.5 工具 schema 与大量 MCP 工具

- **工具总目录不等于 Agent 可用工具集，也不等于本轮模型看到的工具集。**设计上应分开管理：

  ```text
  Capability Registry 的全部工具（平台目录）
      ↓ 管理员/Agent 作者显式绑定
  Agent allowlist（该 Agent 获准可用的工具）
      ↓ 本轮按任务选择（以后可选）
  LLM 候选工具（本次请求实际发送的完整 schema）
  ```

- **最小工具绑定是配置原则，不是盲目设一个固定工具数量。**每个 Agent 只绑定其角色完成任务所需、且已授权的工具；模型不应该看到其他角色或无关业务域的工具。数量和 schema token 预算用于发现异常或保护上下文，不能以“截断工具列表”的方式丢掉完成任务所必需的工具。
- 当前 PlatformAgent 已支持两种绑定范围：`capability_provider` 会展开并绑定 Provider 下全部工具；`capability_tool` 只绑定指定 Tool。因而“绑定整个 Provider”是工具数量膨胀的直接来源之一；当 Provider 含有大量工具时，优先使用逐工具绑定。Capability Registry 中未被 Agent 配置引用的工具，不会自动进入该 Agent registry。
- 当前 Agent 配置表单允许按 Provider 或单个 Tool 勾选；用户可展开 Provider 查看工具并逐项勾选。现有 `addAgentPlugins` 还会避免同一 Provider 全量绑定与其单工具绑定重复。后续 UI 应把“全量绑定 Provider”明确标成批量操作，并提示会展开的工具数和 schema 估算，而不是让它看起来像只绑定一个工具。
- 最小绑定示例（格式沿用当前 `config.plugins`）：

  ```json
  {
    "plugins": [
      {"type": "capability_tool", "ref": "<provider-id>/<search-tool-id>"},
      {"type": "capability_tool", "ref": "<provider-id>/<fetch-tool-id>"},
      {"type": "tool", "ref": "tool:calculator"}
    ]
  }
  ```

  `capability_provider` 只应在 Agent 确实需要该 Provider 的全部工具，或 Provider 本身已被拆分成小而专用的工具集时使用。示例中的 ID 为占位符。

- **按职责拆 Agent，而非给一个 Agent 绑定所有 MCP。**例如 Research Agent 绑定搜索/读取工具，Database Agent 绑定只读查询工具，Report Agent 绑定文档生成工具；主 Agent 只持有有限的委派能力。跨 Agent 委派要遵守租户、权限、预算和深度限制，不能借拆 Agent 绕开授权。
- 第一阶段不做运行时自动发现：加载 Agent 配置时，只加载 allowlist 中明确绑定的工具；生成 schema 时，向模型发送该 allowlist 的完整 schema。每次模型请求都记录可见工具数及 schema token 估算。
- 只有当显式绑定仍然导致目录过大时，才引入动态候选选择。候选选择的边界是 Agent allowlist 的子集，绝不在整个 Capability Registry 或租户目录中任意挑工具。
- 推荐动态模式为两阶段调用：

  1. Context Builder 给模型发送受限的 `search_agent_tools(query)` 目录检索能力，以及 Agent allowlist 中很小的必需工具集；目录项仅含名称、短描述和稳定 ID，不发送完整参数 schema。
  2. 检索器只在当前 Agent allowlist 内按名称、描述和类别检索 top-k 候选；框架再从已授权插件中解析这些 ID，将候选完整 schema 放入**下一次**模型请求。
  3. 如果结果不够，模型可以再次检索，但受检索轮数、候选数量、token 预算和总运行预算限制；否则清楚返回“未找到已绑定的工具”，不能静默扩大范围。
  4. 执行插件时仍按现有 PermissionChecker 再做授权检查；候选检索只控制发现和模型可见性，不发放权限。

- 工具选择应可解释：记录候选 ID、选择来源（静态绑定/检索）、匹配原因和 schema token 估算。检索结果质量不足时，允许在 Agent 的显式 allowlist 内回退，而不是扩大为全部注册工具。
- 工具名必须在 Registry 中全局唯一且可识别来源。当前 capability loader 生成带 provider/tool 标识的名称；继续保留此类命名空间，避免不同 MCP Server 同名工具冲突。
- **不建议默认启用动态检索。**小规模、职责清晰的 Agent 直接静态绑定最可靠；动态检索本身会增加模型调用、延迟、选择错误和调试复杂度。只有工具规模或实测 schema token 达到配置阈值时，才对该 Agent 启用。

#### Agent 工具绑定的操作流程

1. Agent 作者先写清该 Agent 的职责和禁止执行的动作。
2. 在工具管理页按类别/Provider 搜索，逐项勾选完成该职责所需的最小 Tool 集；先不要选“绑定整个 Provider”。
3. UI 展示“已选 N 个工具 / schema 估算 token / Provider 全量展开会增加多少工具”，并对全量绑定要求明确确认。
4. 保存后后端将选中的 Tool 引用写入 Agent `config.plugins`；加载器只解析这些引用。
5. 运行诊断页显示本轮实际传给模型的工具清单和 token 占用；由此判断需不需要动态检索，而不是先上检索再猜效果。
6. 如果一个 Agent 需要跨多个互不相关的工具域，优先拆成职责明确的 Agent/Skill；主 Agent 通过委派调用，再按预算汇总结果。

#### 推荐默认策略

| 场景 | 默认设计 |
|---|---|
| 小型工具集、稳定任务 | 静态逐 Tool 绑定；每轮传已绑定工具 schema |
| Provider 下只有少数同职责工具 | 可以绑定 Provider，但 UI 显示展开后的工具清单 |
| Provider 下工具多或跨多个业务域 | 不全量绑定；按 Tool 选择，或拆分 Agent |
| 已绑定工具仍超过输入预算 | Agent allowlist 内动态检索候选；每轮只传 top-k schema |
| 工具检索无结果/失败 | 只回退到显式配置的安全子集或报清楚错误，不扩大授权范围 |
| 高风险写操作 | 显式绑定、默认不自动并发；保持执行时权限/审批检查 |

### 6.6 Tool/MCP 输出控制

- 在结果进入后续模型消息之前施加按工具类型配置的字节/token 上限。
- 结构化结果优先保留 schema 要求字段；列表/表格优先分页或抽取相关行；长文本使用带明确标记的摘要或片段。
- 被截断或摘要的结果需说明是否完整、保留来源和结果 ID；不能让模型误以为获得完整结果。
- 若宿主有安全的结果存储，可把大结果保存为 artifact，并在上下文中提供摘要和授权后的引用/读取工具。框架不直接保存业务数据库或文件。
- 错误信息和截断提示也有大小限制，防止失败回显本身造成 prompt 膨胀。

## 7. 错误处理与安全

- **无法确定模型窗口或估算质量不足**：使用宿主明确配置的保守值；没有可用配置时应给出警告或拒绝启用硬性保证，不宣称 token 估算绝对准确。
- **必须保留内容超预算**：返回明确错误，说明各分项占用和超额，不返回成功形状的空上下文。
- **摘要/压缩失败**：保留原始记录；按配置使用最近完整消息的有限回退，或明确失败。
- **工具筛选失败**：可回退到 Agent 已绑定的安全子集；不能扩大到全租户/全 Registry 工具集合。
- **截断与外部引用**：明确标注不完整性和引用权限；不允许未经授权读取 artifact。
- **敏感信息**：分项诊断只记录 token 数、项数、动作与 ID；正文继续走 Redactor，避免为了调试而记录未脱敏 prompt。
- **提示注入**：历史摘要和工具输出不能被提升为系统指令；保留来源边界和不可信数据标记。

## 8. 建议配置

具体默认值需要以目标模型、实际 tokenizer、业务任务和延迟/成本测量确定；此处不预设任意固定 token 数：

| 配置项 | 作用 |
|---|---|
| `context_window_tokens` | 当前模型的输入+输出总窗口 |
| `max_output_tokens` | 给模型回复预留的 token |
| `context_safety_margin_tokens` | 估算误差及 provider 格式开销余量 |
| `max_prompt_tokens` | 可选的显式输入上限，不超过扣除回复预留后的窗口 |
| `history_recent_turns` 或 `history_token_budget` | 最近对话保留范围/预算 |
| `summary_token_budget` | 旧历史摘要预算 |
| `memory_token_budget` | 记忆召回总预算 |
| `tool_schema_token_budget` / `max_visible_tools` | 工具定义预算及候选数量 |
| `tool_result_token_budget` / `tool_result_byte_limit` | 单项或单类工具输出上限 |
| `token_estimator` | tokenizer/provider 估算实现及其模型映射 |
| `compaction_mode` | 禁用、历史摘要、工具输出摘要/引用等策略 |

还应支持每个 Agent 或模型覆盖配置，但统一由 Runtime 执行预算校验，避免业务入口各自实现不一致。

## 9. 可观测性与指标

每次 LLM 请求至少记录以下非敏感诊断字段：

- `run_id`、`trace_id`、模型标识和请求序号；
- 估算 prompt token、实际 usage（若 provider 返回）、输出预留和窗口余量；
- system/task、history、summary、memory、tools、tool results 的分项估算；
- 输入消息数、可见工具数、记忆条数、工具结果数；
- 本轮是否摘要、裁剪、截断、外置引用，以及原因；
- 预算拒绝、provider context-length error 的次数。

估算值与模型实际 usage 应分别展示，不混为同一个精确指标。不得在普通日志或 metrics 标签中记录原始 prompt、用户内容、工具结果或秘密。

## 10. 实施步骤

### 阶段一：请求前预算与输出硬限制

- 增加模型能力/TokenEstimator 契约和 ContextPolicy。
- 在每个 LLM 调用前估算完整输入（含工具 schema）并预留输出空间。
- 给 MCP/Tool 返回值加有界处理与显式截断标记。
- 对超限返回结构化错误；增加单位测试覆盖。

### 阶段二：统一 Context Builder

- 将 Decide 的请求组装从节点内迁到统一构建组件。
- 将当前任务、历史、计划、记忆和工具定义作为不同来源输入。
- 加入上下文分项统计、优先级策略和可解释的裁剪记录。
- 保持 `AgentRuntime.run()` 的现有使用方式；新策略通过可选依赖/配置启用并逐步成为默认。

### 阶段三：历史摘要与相关记忆

- 建立摘要模型、来源覆盖范围、刷新阈值和摘要预算。
- 保留完整原始 transcript；摘要失效或缺失时可以从宿主历史重建。
- 记忆选择从固定数量扩展为相关性与 token 预算共同约束。

### 阶段四：大工具目录治理

1. **先收敛静态绑定（第一版，建议默认）**
   - 将 Provider 绑定明确定义为“绑定该 Provider 当前全部工具”的批量操作，不把 Provider 本身误当成单个工具。
   - Agent 作者逐项绑定 `capability_tool` / `capability_api_tool`，并按职责分 Agent；加载器只加载配置中的 allowlist。
   - Agent 编辑 UI 展示展开数量、去重后的实际工具列表、schema token 估算；Provider 全量绑定设置二次确认。
   - 设置每 Agent 的工具数量/schema token 告警阈值；阈值用于告警或要求作者确认，不应静默截去工具。
   - 验收：一个 Agent 只传入配置明确绑定且授权通过的工具；未绑定的 Capability 工具不会进入模型 schema；全量 Provider 绑定能显示并解释展开结果。

2. **再做目录和命名治理**
   - 为工具保存稳定的 `provider_id`、`tool_id`、类别、描述、schema 大小和风险/权限元数据。
   - Registry 内部 ID 使用稳定 namespaced ID；LLM function name 使用可读且唯一的名称，调用映射回稳定 ID。
   - 对相同工具的重复绑定去重；冲突或配置引用已失效的工具要报告明确错误。
   - 验收：多 Provider 同名工具不互相覆盖；Agent 配置变更后运行时 registry 与 UI 展示一致。

3. **最后按指标决定是否动态发现**
   - 先采集静态绑定下每次请求的工具数、schema token、总 prompt token、模型选错率/无效工具调用率、延迟和成本。
   - 仅当特定 Agent 经常受 schema 预算限制时，启用 Agent allowlist 内的 `search_agent_tools` 两阶段发现；不对所有 Agent 全局开启。
   - 对比开启前后的任务成功率、漏检率、无效调用、请求 token、额外检索轮数、延迟和权限拒绝情况；质量不达标时回滚到静态 allowlist。
   - Context Builder 执行最后的总 prompt 预算检查。动态发现是减少候选的优化，不替代预算硬边界。

## 11. 测试与验收标准

1. 在请求 LLM 前估算消息、记忆和工具 schema 总量；超限输入不会发起模型调用。
2. 回复 token 预留和安全余量会从模型上下文窗口扣除。
3. 多轮运行上下文超预算时，只压缩允许压缩的内容，并保留当前用户目标、系统规则和活动任务。
4. 历史压缩不会拆开 assistant tool call 与匹配结果；完整原始历史仍可追踪。
5. MCP/API 超大输出被限制或转为引用，结果明确标记不完整；普通大小结果保持兼容。
6. 记忆、工具 schema、历史和工具结果分别受预算约束，单一来源不能无界挤占其余内容。
7. 压缩失败、预算不足、估算缺失等路径有明确可观测错误，不静默降级成空 prompt。
8. 工具筛选不改变执行时授权检查；筛选失败不会扩大可用工具范围。
9. 诊断可比较估算 token 与实际 usage，但不泄漏原始敏感文本。
10. 现有单 Agent 执行、工具调用、暂停与恢复语义保持兼容。

## 12. 决策摘要

- Context Management 是单 Agent Runtime 的横切能力，不应只作为多 Agent/DAG 功能的一部分实现。
- 最先落地：**请求前预算检查、输出上限、工具 schema 预算、诊断明细**。
- 随后落地：**历史与工具输出压缩、记忆预算、按需工具发现**。
- 完整运行记录永远独立保留；上下文视图可丢弃并重建。
- 在确定性边界内压缩，不能静默丢弃当前任务、权限规则或关键结果。
