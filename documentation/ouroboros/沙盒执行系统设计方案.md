# Ouroboros 沙盒执行系统设计方案

> 文档状态：目标架构提案，尚未实现。
> 适用范围：Ouroboros / PlatformAgent 中按任务策略执行代码或受限计算的沙盒系统；不把普通 Agent 推理和所有 MCP 工具强制搬进沙盒。

## 1. 执行摘要

建议采用**宿主控制面 + 独立 Sandbox Worker 执行面 + 按任务风险选择隔离 Profile**：

- 普通 LLM 推理和常规 MCP/API 工具继续由 Agent Runtime 和宿主工具适配器执行。
- 可信、固定的内部函数可保留普通受限执行模式，但不得称为安全边界。
- 有来源不确定或用户/模型可控的代码，必须交给与业务 API、数据库和 Docker 管理面隔离的 Sandbox Worker。
- 若要开放任意不可信代码，目标隔离级别应是 microVM 或经评估的托管代码执行服务；普通容器只适合受控风险的第一阶段，不能宣称可抵御宿主内核级逃逸。
- LLM 可以提出“需要代码执行”的意图，但不能指定或降低安全 Profile。最终决策由宿主策略引擎根据代码来源、Agent 权限、任务能力和部署策略确定。

当前 Ouroboros 的 `FunctionSkill` 默认在子进程中运行受限 builtins，并有超时；源码明确说明这只是 best-effort，并非安全边界。[FunctionSkill](../../application/ouroboros/ouroboros/skills/function_skill.py) 因此它只适用于可信代码便利执行，不适用于任意用户提交或模型生成代码的安全隔离。

## 2. 范围与威胁模型

### 2.1 纳入范围

- Python/脚本/代码解释器执行；
- 沙盒任务的准入、Profile 选择、调度、资源限额和生命周期；
- 代码读取输入数据、生成输出/文件、超时/取消和错误回传；
- 沙盒与 Agent Runtime、MCP/API、宿主凭据、存储之间的数据边界；
- 审计、监控、隔离测试、上线和应急处理。

### 2.2 不纳入范围

- 将所有 Agent LLM 请求本身放入容器；
- 把 MCP Server 或 API 工具调用等同于代码执行；
- 通过 Python 受限 builtins、AST 检查或提示词规则来保证恶意代码安全；
- 让沙盒直接连接 PlatformAgent 主数据库、Redis、云元数据服务或宿主 Docker socket；
- 把容器本身作为对抗不可信多租户代码的充分安全证明。

### 2.3 保护目标与威胁

需要保护：

- PlatformAgent、Capability Registry、数据库、Redis、宿主机和其他租户；
- API/云凭据、MCP 授权头、签名密钥、环境变量和私有文件；
- 云内网、宿主网络、云元数据服务和未经允许的公网目标；
- 其他沙盒任务的数据、执行状态和产物；
- API 可用性、Worker 容量、LLM/代码执行成本。

威胁包括恶意/失控代码、无限循环、资源耗尽、文件系统探测、网络探测、凭据窃取、跨任务数据访问、输出伪造/注入、重复执行副作用和沙盒运行时漏洞。

本设计假设底层操作系统、云账号和 Worker 管理面受到运维保护；若攻击者已获得 Worker 宿主 root 或云账号控制权，应用级沙盒无法单独挽救系统。

## 3. 按任务选择执行策略

### 3.1 决策原则

“是否需要沙盒”由**执行能力和代码来源**决定，而非只看自然语言任务名称：

1. 纯聊天、规划、总结：不启动代码沙盒。
2. 调用预先注册的 MCP/API/业务 Tool：走宿主的 Tool Broker、权限/审批和出网策略，不直接放入代码沙盒。
3. 运行平台维护、版本固定且来源可信的内部函数：可以使用受限子进程等便利模式；该模式不允许不可信源代码。
4. 运行用户上传或 LLM 生成的代码：视为不可信代码，必须进入强隔离 Profile。
5. 无法证明代码来源可信、任务能力需求不明确或策略服务不可用：拒绝执行或采用部署允许的最强隔离，不得降级到 inline/普通子进程。

“模型说这是安全代码”“Skill 名称是 trusted”“调用者是管理员”都不能单独作为代码可信证明。可信来源需由宿主基于发布者身份、代码版本/哈希、审批状态和签名策略判定。

### 3.2 Execution Intent 与 Policy Resolver

Runtime/宿主将插件调用归一为执行意图：

```text
ExecutionIntent
  kind: llm | registered_tool | trusted_function | untrusted_code
  source_trust: platform_signed | tenant_trusted | user_supplied | model_generated | unknown
  requested_capabilities: cpu | filesystem | network | packages | ...
  data_classification: public | tenant | sensitive
  agent_id / tenant_id / run_id / task_id
```

由宿主 Policy Resolver 决定 `ExecutionProfile`：

- 规则输入应来自 Agent/Skill 元数据、制品签名与哈希、调用者授权、部署策略和任务需求。
- LLM 输出最多只能提出 intent/capability 请求；不能设置 `trusted=true`、选择弱隔离 profile 或授予网络权限。
- 策略决策必须有解释码，例如 `not_code_execution`、`trusted_internal_function`、`untrusted_source_requires_microvm`、`network_not_allowed`。
- Policy Resolver 故障、profile 不可用或要求能力无法满足时，fail closed（拒绝执行），不能回退至较弱隔离。

### 3.3 隔离 Profile

Profile 描述能力和限额，不暴露任意低层运行时参数给 Agent。具体数值应根据负载压测、模型/解释器版本和云资源确定，不能仅凭固定模板推断安全。

| Profile | 适用任务 | 隔离与能力 | 建议使用边界 |
|---|---|---|---|
| `P0_HOST_TOOL` | 普通聊天和注册 MCP/API 工具 | 不运行用户代码；宿主侧按 Tool 权限执行 | 默认路径；每次执行仍鉴权 |
| `P1_TRUSTED_FUNCTION` | 平台发布、审核、签名的固定函数 | 当前受限子进程或受控内部执行；资源/超时限制 | 仅可信代码；明确不是对抗恶意代码的边界 |
| `P2_ISOLATED_CONTAINER` | 受控团队的半可信代码、内部试验 | 独立 Worker 上的短生命周期、非特权隔离容器，默认无网络 | MVP；仅在接受容器共享宿主内核风险时启用 |
| `P3_STRONG_ISOLATION` | 任意用户代码、模型生成代码、多租户不可信代码 | 每任务 microVM 或经安全评估的托管执行环境 | 面向外部用户开放前的目标 Profile |

Profile 可以按部署关闭。例如尚无 P3 时，P3 请求必须明确拒绝/排队等待，不得静默转成 P1/P2。资源上限、网络目的地和挂载内容在 Profile 中由管理员定义。

## 4. 总体架构

```text
PlatformAgent API / Ouroboros Runtime
  ├─ 识别执行意图（不信任模型自选安全级别）
  ├─ Delegation/Permission Policy：校验用户、租户、Agent、Skill
  ├─ Sandbox Policy Resolver：选择 ExecutionProfile
  └─ SandboxRunner Port（仅提交声明式任务）
           │ authenticated, bounded request
           ▼
Sandbox Control Plane（宿主/独立服务）
  ├─ Job API：幂等创建、状态查询、取消
  ├─ Admission Controller：配额、Profile、镜像/制品校验
  ├─ Queue / Scheduler：并发、租户公平性、deadline
  ├─ Credential & Artifact Broker：窄权限、短时凭证
  └─ Audit / Metrics / Event Sink
           │ one task → one isolated execution
           ▼
Sandbox Worker Pool（独立 ECS/节点/托管执行服务）
  ├─ Worker Agent：验证签名任务、准备临时环境
  ├─ Isolation Runtime：P1/P2/P3 Profile
  ├─ Network Guard：默认断网；可选受控 egress proxy
  ├─ Resource Guard：CPU / memory / pids / time / disk / output
  └─ Cleanup Controller：超时/取消/完成后回收整个环境
           │ bounded result / artifact ref
           ▼
PlatformAgent Run / Audit Store
```

控制面和执行面应分离。沙盒 Worker 不能访问 PlatformAgent 的数据库/Redis网络；Sandbox API 不能向公开客户端暴露容器管理能力；业务 API 不应持有可在任意容器中挂载的宿主级 Docker 管理权限。

### 4.1 组件职责

| 组件 | 职责 | 禁止事项 |
|---|---|---|
| `SandboxPolicyResolver` | 基于可信元数据选择允许的 profile/capabilities/limits | 依据 LLM 自报的信任等级放宽策略 |
| `SandboxRunner` Port | 传递声明式请求并返回结构化结果 | 直接执行 `exec` 或连接容器管理 socket |
| Control Plane | 认证、配额、准入、排队、状态、取消、审计 | 接受任意镜像、任意挂载或任意网络参数 |
| Worker Manager | 拉取已批准的镜像/制品，启动并清理任务环境 | 与 API worker 共用权限和宿主目录 |
| Isolation Runtime | 提供容器、microVM 或托管隔离执行 | 通过 Python 层沙盒替代 OS 隔离 |
| Tool Broker | 代表宿主执行明确允许的工具/API 操作 | 将长期 API 密钥放进执行环境 |
| Artifact Broker | 以短时、单任务、窄权限方式读写输入/输出 | 给沙盒共享存储账号或任意路径访问 |
| Result Validator | 校验状态、schema、大小、引用和截断标记 | 把不可信 stdout 当作可信系统指令 |

## 5. 请求、任务与结果协议

### 5.1 SandboxRequest

请求结构应是声明式、可校验并且有版本的。宿主生成任务 ID 和 profile，不接收 Agent 自由设置的容器命令或挂载路径。

```json
{
  "schema_version": "1",
  "job_id": "sbx_job_id",
  "tenant_id": "tenant_id",
  "root_run_id": "run_root",
  "parent_run_id": "run_parent",
  "task_id": "task_id",
  "execution_intent": {
    "kind": "untrusted_code",
    "source_trust": "model_generated",
    "code_digest": "sha256:..."
  },
  "profile": "P3_STRONG_ISOLATION",
  "artifact_inputs": [
    {"artifact_id": "artifact_id", "access": "read"}
  ],
  "input": {"schema": "task-specific-input"},
  "limits": {
    "wall_time_seconds": 0,
    "cpu": "policy-defined",
    "memory_bytes": 0,
    "process_count": 0,
    "disk_bytes": 0,
    "stdout_bytes": 0,
    "stderr_bytes": 0
  },
  "network_policy": {"mode": "none"},
  "idempotency_key": "run/task/attempt"
}
```

`0` 及 `policy-defined` 是字段示意，不是可用配置。最终有效 Profile 和限制由 Control Plane 重新计算/校验；请求中的限制只能收紧不能放宽策略。

安全字段要求：

- 用户/租户身份由已认证服务端上下文确定，不能信任客户端 JSON 中自报的 `tenant_id`。
- 代码包/依赖使用不可变版本和哈希；不允许运行时动态拉取任意代码依赖。
- 镜像只能从管理员批准的镜像集合中选择，并固定 digest。
- 输入通过 artifact ID/受限 JSON 传递，不接受任意宿主路径。
- 每个任务具有 deadline、attempt 和幂等键；重复提交返回同一 Job 或被明确拒绝。
- 网络和资源策略由服务端 Profile 注入；调用方不能通过请求修改全局限制。

### 5.2 SandboxResult

```json
{
  "job_id": "sbx_job_id",
  "status": "completed",
  "exit_code": 0,
  "stdout": "bounded output",
  "stderr": "",
  "truncated": false,
  "duration_ms": 0,
  "resource_usage": {
    "cpu_ms": 0,
    "peak_memory_bytes": 0,
    "disk_bytes": 0
  },
  "artifacts": [],
  "error_code": null,
  "profile": "P3_STRONG_ISOLATION",
  "image_digest": "sha256:..."
}
```

状态至少区分 `queued`、`starting`、`running`、`completed`、`failed`、`timed_out`、`canceled`、`resource_exceeded`、`rejected`。输出、错误和 artifact 数量/体积均受限。stderr 不自动暴露给最终用户；需按安全策略脱敏并转为可理解的错误摘要。

## 6. 任务生命周期

```text
1. Agent 请求代码执行
2. Host 校验 Agent/用户/租户授权、代码来源和任务类型
3. Policy Resolver 选择 profile 与 capabilities
4. Admission Controller 检查配额、镜像、输入大小、deadline 和 Worker 能力
5. 创建幂等 Job 并登记 run/task 关联
6. Scheduler 将任务放入对应隔离级别的队列
7. Worker 验证请求签名、代码/镜像 digest 和策略版本
8. Worker 准备一次性执行环境并限制资源、文件和网络
9. 运行任务；持续采集状态，强制执行 timeout/cancel/output limits
10. Worker 关闭任务、收集受限输出/产物、销毁执行环境
11. Result Validator 验证 schema、状态、大小、artifact 权限
12. Host 将结构化结果写入原 run trace，再交给 Agent 作为不可信工具结果
13. 更新审计/用量并按 retention 清理临时数据
```

若 Worker 失联，应由租约/心跳超时回收任务；任务是否重试由执行类型和幂等策略决定。纯计算任务可以按策略重新运行；具有外部副作用的任务不应盲目自动重试。

## 7. 隔离与权限设计

### 7.1 Worker 与运行时隔离

- Worker 部署在独立的 ECS/节点池或经安全评估的托管环境，与 PlatformAgent、Capability Registry、数据库和 Redis 分离。
- Worker 的宿主操作系统、容器/VM 管理面只由专用服务账号操作；Control Plane 使用窄权限任务 API，不持有任意宿主 shell 能力。
- P2/P3 每个 job 使用独立、短生命周期环境；不跨租户复用可写文件系统、进程命名空间或持久 HOME。
- 容器 Profile 应采取 rootless/非特权、只读基础文件系统、临时工作目录、Linux capabilities 最小化、系统调用/进程/资源限制、无宿主 socket/敏感 mount 等加固。容器共享宿主内核，依然存在内核逃逸风险。
- P3 使用 microVM 或经独立安全评估的托管执行环境；评估启动/销毁边界、宿主共享面、补丁周期、租户隔离、审计接口和供应商数据处理条款。
- 沙盒镜像按 digest 固定，来源签名、依赖 SBOM、漏洞扫描和更新回滚都纳入发布流程；不要使用可变 `latest` 作为生产执行来源。

### 7.2 文件和数据

- 根文件系统只读；每任务提供独立临时工作区，任务完成/失败/取消后回收。
- 输入文件以最小集合、只读方式提供；不挂载整个项目目录、宿主 home、SSH keys、Docker socket、云凭据文件或业务配置。
- 输出通过独立 artifact 通道返回；默认不允许覆盖输入或直接写入业务数据库。
- Artifact 引用需校验 tenant、root_run、task、访问模式和过期时间；跨 Agent/跨 run 共享必须由宿主授权。
- 输入、输出、归档和日志分别设置大小/保留期限；临时目录与磁盘使用也要设硬限额。

### 7.3 网络与工具调用

- 默认完全禁网，包括公网、内网、loopback、云元数据和宿主网段。
- 若任务确实需要网络，必须由管理员批准专用 Network Profile，经受控出网代理访问明确目标；禁止任意 URL 或任意 DNS 解析结果直接放行。
- Network Profile 应考虑域名/IP 解析变化、重定向、代理绕过、DNS 与私网/保留地址拦截；代理规则由宿主控制，沙盒不能自行关闭。
- 沙盒代码不直接访问 MCP Server、数据库、Redis 或 Capability Registry。需要工具能力时，通过宿主 Tool Broker 按 Agent 权限执行，或将经过授权的最小数据作为输入。
- 外部服务凭据由 Broker 在宿主侧持有；绝不把长期密钥写入环境变量、代码、文件或命令行。若确需任务级授权，使用短时、单任务、窄 scope 凭证，并确保 Worker 无法读取其他任务凭证。

### 7.4 资源与滥用治理

- 限制 wall-clock、CPU、内存、进程数、磁盘、打开文件/句柄、stdout/stderr、artifact 数和总输出。
- 按租户、用户、Agent 和 Profile 设置并发、队列长度、每日用量和成本配额；高成本 Profile 默认更严。
- 每个任务都有超时和取消；强制终止进程树/整个 VM，不只结束父进程。
- 避免无限排队；排队超时、Worker 不可用和配额耗尽返回明确状态。
- 对重复提交用 idempotency key 去重；attempt 记录不可覆盖。
- 提供 kill switch：按 tenant、Agent、Profile 或全局暂停新任务，并保留对正在运行任务的安全取消能力。

## 8. 身份认证、审计与可观测

### 8.1 服务身份

- Sandbox API 只允许 PlatformAgent 后端/可信调度器访问，通过服务身份认证和 TLS；不暴露给浏览器或公网匿名调用。
- 每个请求签名或使用短时服务凭证，并校验时间戳、nonce/job ID 和策略版本，防止伪造/重放。
- Worker 通过短时身份向 Control Plane 拉取单个已授权 Job；不能按 tenant 或 run 列举其他任务。
- 服务凭据通过 Secret Manager/宿主安全配置注入到 Control Plane，不进入沙盒。

### 8.2 审计字段

记录但不泄露原始敏感代码/数据：

- job/run/root_run/parent_run/task/tenant/user/agent 关联 ID；
- 代码来源类型、代码 digest、批准状态、Profile、策略版本；
- Worker、镜像 digest、运行时版本、开始/结束时间和最终状态；
- 资源使用、输入/输出大小、网络策略和 artifact ID；
- 重试/取消/拒绝的原因码、调用者和策略决策 ID。

审计正文按敏感级别另行存储和授权；普通日志不写代码原文、API key、用户文件内容和未脱敏 stdout/stderr。审计记录应防篡改并有明确保留期。

### 8.3 运行指标

- 排队时延、启动时延、运行时长、成功/失败/超时/资源超限率；
- CPU/内存峰值、并发数、队列长度、Worker 健康度；
- 各 Profile 的调用量、成本、拒绝数和隔离层版本；
- 输入/输出大小、截断次数、artifact 读写量；
- 用户取消到实际终止的延迟、孤儿 Worker/未清理资源数。

安全事件告警：跨租户访问拒绝、异常网络尝试、重复资源超限、Worker lease 失联、镜像 digest 不符和清理失败。

## 9. 与 Ouroboros / PlatformAgent 的集成

### 9.1 Ouroboros 框架层

建议新增稳定的 `SandboxRunner` Protocol，而不是把 Docker/microVM API 写进框架：

```text
SandboxRunner.submit(request) -> SandboxJob
SandboxRunner.wait(job_id, timeout) -> SandboxResult
SandboxRunner.cancel(job_id) -> CancelResult
```

实际 API 可改为单个异步 `run()`，但应支持状态、取消和明确异常。端口只定义纯数据和生命周期，不依赖 SQLAlchemy、FastAPI、Docker SDK 或云厂商 SDK。

新增 `CodeExecutionSkill`/执行器或扩展 Skill 时：

- manifest 声明需要的能力和输入/输出 schema，不允许 Skill 自己指定低级 sandbox 参数；
- Runtime/宿主在调用前做 policy resolution；
- FunctionSkill 的 `subprocess`/`inline` 只能用于可信任务，未来不可信代码必须配置 `sandbox=external` 或等价策略，且外部 Runner 不可用时拒绝；
- 返回 `SandboxResult` 的受限结果并通过现有工具结果安全边界标注。

### 9.2 PlatformAgent 宿主层

- 新增 Sandbox Adapter/Client：负责认证 Control Plane、任务关联、配额和结果映射。
- 在 Agent/Skill 管理配置中定义允许运行代码、允许 Profile、数据分类和人工审批要求；普通用户不能自行设置 Profile。
- child Agent 继承父级预算上限，但是否允许代码执行由 child Agent 自己策略和宿主 policy 决定。
- 任务完成状态、用量、Profile、执行摘要和 artifact refs 关联 `runs`/`run_steps`，完整沙盒日志存独立审计域。
- 对沙盒输出作为不可信输入处理，经过 schema/大小校验和脱敏后才进入 Agent Context Builder。
- 前端展示“代码来源、Profile、状态、资源用量、输出是否截断”，不默认展示敏感源码或完整 stderr。

### 9.3 建议数据库实体（宿主可选）

```text
sandbox_jobs
  id, tenant_id, root_run_id, parent_run_id, task_id, agent_id
  status, profile, policy_version, code_digest, image_digest
  idempotency_key, attempt, queued_at, started_at, finished_at
  timeout_seconds, resource_usage_json, result_summary, error_code

sandbox_artifacts
  id, job_id, tenant_id, artifact_type, object_key
  size_bytes, checksum, sensitivity, expires_at, created_at
```

数据库不保存长期凭据；对象存储 key 不作为公开可猜路径；访问 artifact 仍经过宿主授权。具体 schema 和 retention 需根据审计要求决定。

## 10. 在阿里云 ECS 的部署建议

当前 PlatformAgent Compose 栈包含 API、PostgreSQL、Redis 和前端，不包含 sandbox worker。沙盒不应简单追加为一个与 API 共用宿主权限的容器，并开放 Docker socket 给后端。

### 10.1 推荐拓扑

```text
公网 / Gateway
      │
PlatformAgent ECS（API + DB/Redis 按现有拓扑）
      │ 仅私网 Sandbox API；服务身份认证
      ▼
Sandbox Control Plane（可独立部署）
      │ 私网任务队列/受限 Job 拉取
      ▼
Sandbox Worker ECS/节点组（无数据库/Redis路由）
      │
一次性容器（P2）或 microVM/托管隔离执行（P3）
```

- Worker 放在独立 ECS/节点组及独立安全组，尽量使用单独的 VPC 子网/网络策略；不开放公网入站。
- Worker 安全组只允许 Control Plane 的必要私网流量；默认拒绝访问数据库、Redis、Capability Registry、宿主管理面、元数据服务及互联网。
- 如果只有一台 ECS，先不要开放外部用户任意代码执行。单机上的 sibling container 隔离不足以形成适合恶意多租户代码的边界。
- Control Plane 可在 MVP 与后端同一受控服务部署，但不得把 Worker 的宿主管理 socket 暴露给公开 API；更严格的部署应将控制面也独立。
- 对 P3，应选可验证的 microVM/托管隔离实现，并实测该环境在所用 ECS/云产品区域的支持性；不要假设普通 ECS Docker Compose 已提供 microVM 安全边界。

### 10.2 阿里云集成点

本方案不预设某个特定阿里云沙盒产品。落地前需核实目标地域的服务能力、VPC 接入、隔离承诺、镜像/依赖限制、网络策略、审计、数据处理与成本。

无论采用 ECS 自建 Worker 还是托管执行服务：

- 使用独立 RAM 身份/实例角色，并按需授权；Worker 不持有 Platform 数据库密码和主服务 API key。
- Secret 放在受控密钥管理中，仅 Control Plane 获取必要配置；任务代码不可读取服务端管理凭据。
- 关闭公网入口；通过私网 endpoint、安全组和应用层认证限制 API/Worker 通信。
- 将日志、指标和审计发往独立受控监控/日志系统，敏感正文默认不采集。
- 预留 Worker 镜像补丁、隔离 runtime 更新、异常任务熔断和快速停用流程。

## 11. 分阶段实施

### 阶段 0：定义风险边界

- 盘点哪些功能真的执行任意代码：FunctionSkill、Notebook/代码工具、用户上传脚本等。
- 明确代码来源信任等级、数据分类、是否允许联网/依赖安装/文件操作和租户模型。
- 将当前 FunctionSkill 明确标为可信代码便利执行；先关闭或限制不可信来源。
- 形成 Profile 白名单、拒绝条件和应急 kill switch。

### 阶段 1：受控内部 MVP（P2）

- 部署与 PlatformAgent 分离的 Worker ECS/节点池。
- 仅运行固定批准镜像和受控任务；每任务一次性隔离容器、默认断网、无秘密、无宿主挂载、硬资源/时间/输出限制。
- PlatformAgent 通过最小 `SandboxRunner` API 提交任务；增加认证、幂等、状态、取消、审计和自动清理。
- 不接受外部用户任意代码；不因 P2 已上线就宣称能承载对抗性多租户。

### 阶段 2：生产加固

- 加入公平调度、租户配额、Worker 自动扩缩、故障恢复、审计保留、镜像签名/扫描和安全告警。
- 验证 worker 网络完全不能到达业务数据库、Redis、云元数据和未授权公网。
- 对 timeout/cancel/crash 做资源泄漏和孤儿任务演练。

### 阶段 3：不可信代码 P3

- 选择 microVM 或完成安全审查的托管隔离服务；不将 P2 自动视为 P3。
- 进行独立威胁评估、供应链审核、隔离穿透测试、租户数据访问测试和应急演练。
- 在 P3 通过验收前，对模型生成/用户提交代码强制拒绝或只允许人工审查后的受信制品。

## 12. 验收标准

### 功能与策略

1. 普通聊天和已授权 MCP 工具调用不会无故启动代码沙盒。
2. 用户/模型生成代码不能进入 inline 或普通 Python 子进程路径。
3. policy/profile 不可用、服务故障或能力不支持时明确拒绝，不静默降级。
4. Agent 只能使用宿主授权的执行能力；不能请求任意镜像、挂载、网络或资源上限。
5. 重复 job 请求具备幂等行为；状态和错误可追踪至 run/task。

### 隔离

1. Worker 无法连接数据库、Redis、Capability Registry、云元数据和未授权私网/公网。
2. 沙盒无法读宿主凭据、环境秘密、其他 job 文件和宿主管理 socket。
3. CPU、内存、进程、磁盘、wall time、输出和 artifact 限额可验证地生效。
4. 超时/取消会终止整个执行环境并清理临时资源。
5. 多租户任务之间文件、网络授权、输出和 artifact 均隔离。
6. P3 隔离实现经过独立安全评估，且供应链、更新和应急响应有负责人。

### 可观测与运维

1. 能查询排队、运行、完成、超时、取消、拒绝和资源超限状态。
2. Worker 崩溃/失联后能检测并回收孤儿任务。
3. 审计记录 profile/策略/镜像/代码 digest 和资源使用，不泄漏秘密正文。
4. 配额、kill switch、告警、日志保留和镜像回滚有演练记录。

## 13. 关键架构决策

1. **按照执行意图路由，不是每个 Agent run 一律启动沙盒。**
2. **信任级别由宿主策略决定；LLM 不能选择弱隔离。**
3. **普通 MCP/API 调用继续由宿主工具层处理；代码沙盒默认断网。**
4. **把执行 Worker 与业务 API/数据库隔离，避免 API 暴露宿主管理权限。**
5. **一次性容器是受控风险 MVP，不是任意恶意代码的强隔离承诺。**
6. **开放不可信代码前必须具备 P3 microVM/托管隔离、独立安全验证和应急机制。**
7. **Ouroboros 定义 SandboxRunner 端口；PlatformAgent/部署适配器负责策略、队列、身份、存储和运行时。**
