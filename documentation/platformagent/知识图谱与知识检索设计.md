# PlatformAgent 0.4.0 · 业务知识图谱与知识检索设计

> 状态：设计提案，尚未实现。适用项目：`application/platformagent/backend/`。
> 本文中的“知识图谱”是**从租户知识库文档中抽取、带来源证据的业务实体关系图**；
> 它不是从用户对话中沉淀偏好、人物和事件的个人记忆图谱。个人记忆图谱不纳入本期。
>
> 现状基线：PlatformAgent 0.3.0 已有 PostgreSQL + pgvector、`VectorMemoryStore` 和
> Ouroboros `Knowledge` / `Retriever` 协议；业务侧尚未建设文档知识库、知识图谱或知识检索适配器。

## 1. 目标与非目标

### 1.1 0.4.0 交付目标

1. 允许租户管理员创建知识库、导入文档并查看索引状态。
2. 将文档切分为可引用的知识片段，建立向量索引。
3. 从片段中抽取实体、关系及原文证据，形成可追溯的图结构。
4. 对 Agent 问题执行受租户、知识库授权和 Agent 配置约束的混合检索。
5. 将检索到的来源传给 Runtime，能够回答“依据哪份文档/哪段原文”。
6. 支持文档替换、删除、重建索引；失败不破坏上一个可用版本。

### 1.2 明确不做

- 不替代 `vector_memories`：对话历史、个人偏好仍属于用户长期记忆。
- 不自动从聊天记录抽取事实，不与用户记忆共享 Entity/Relation 表。
- 不以图数据库作为新基础设施；本期不引入 Neo4j、Milvus、Celery、对象存储。
- 不把大模型抽取结果视为真理：知识断言必须保留原文证据，矛盾来源并存。
- 不做任意 URL 抓取、网页爬虫、PDF/Office 解析、图编辑器和多跳图可视化。
- 不开放 Agent 对知识图谱进行写操作；Agent 只读，导入与删除由授权用户操作。

## 2. 技术决策

| 决策 | 0.4.0 方案 | 原因 |
|---|---|---|
| 图存储 | PostgreSQL 邻接表（Entity + Relation） | 与现有数据库、迁移、事务及测试方式一致；避免新增运维依赖 |
| 片段检索 | PostgreSQL + pgvector，复用现有 Embedder 配置 | 当前已经使用 pgvector；知识片段与 `vector_memories` 分表、分生命周期 |
| 混合检索 | 向量候选 + 图关系候选 + 名称/别名精确匹配；候选合并后排序 | 不依赖未安装的中文分词器；精确实体查询可利用图结构 |
| 图遍历 | 固定最多 2 跳、限制节点与边数 | 支持关系补全，避免无界递归和大响应 |
| 抽取 | 按片段调用结构化 LLM Extractor，校验后写入 | 能复用当前模型网关；抽取成本和模型版本可审计 |
| 文档输入 | 本期只接收 UTF-8 `text/plain` / Markdown 文本 | 仓库无对象存储及文件解析服务；先验证完整知识闭环 |
| 导入作业 | PostgreSQL 持久化 job + 有界 worker + 行锁认领 | 文档 embedding/抽取是慢操作；避免只用进程内 `create_task` 导致重启后任务状态不明 |

**中文检索说明**：初版不把 PostgreSQL 默认 `tsvector` 当中文全文搜索引擎。词条匹配以实体规范名/
别名为主，内容召回以向量为主。若后续确需字面模糊搜索，可评估启用 `pg_trgm` GIN 索引；本期不强依赖
额外 PostgreSQL 扩展。

## 3. 总体架构

```text
管理员/文档提供方
       │ 上传文本、查作业状态
       ▼
PlatformAgent API ──► KnowledgeService ──► PostgreSQL
                           │                   ├─ Knowledge Base / Document / Version
                           │                   ├─ Chunks + pgvector
                           │                   ├─ Entities / Relations / Evidence
                           │                   └─ Ingestion Jobs
                           ▼
                  有界知识摄取 worker
                  parse → chunk → embed
                         → extract → validate
                         → atomically activate

Run 请求
   │
   ├─ 认证 principal / tenant / run permissions
   ├─ 解析 Agent 配置的 knowledge_base_ids
   ├─ 按 tenant + knowledge:read + Agent 配置取交集
   ├─ 现有 VectorMemory 先召回
   │      ├─ 足够：本次不查知识库
   │      └─ 不足：注入本次专属 Knowledge adapter
   ▼
Ouroboros AgentRuntime
   └─ Knowledge.search(query) → 向量 + 实体/关系图 + 原文证据
                                  → KnowledgeEntry + 来源
                                  → 回答上下文 / Run 来源记录
```

Platform 业务层仍是数据隔离和权限决策的权威方；框架只调用本次运行注入的 Knowledge adapter。
用户输入、文档正文、实体和关系描述均视为不可信数据，检索结果是证据而不是可执行指令。

## 4. 数据模型

ID 沿用 `util.new_id` 的 `{prefix}_{uuid4hex}` 风格。以下表均冗余保存 `tenant_id`，便于每次查询显式
加租户过滤、建复合索引和审计。跨租户关联须由数据库约束或 service 校验禁止。

### 4.1 `knowledge_bases`

| 字段 | 说明 |
|---|---|
| `id`, `tenant_id` | 主键与租户归属 |
| `name`, `description` | 租户内名称、说明 |
| `status` | `active` / `archived` |
| `embedding_model`, `embedding_dimension` | 创建时固定的向量模型标识与维度 |
| `created_by`, `created_at`, `updated_at` | 审计字段 |

唯一约束：`(tenant_id, name)`。embedding 维度必须和 pgvector 列定义一致；修改模型/维度需要新建
索引或显式全量重建，禁止静默混用。

### 4.2 `knowledge_documents` 与 `knowledge_document_versions`

Document 是逻辑文档；Version 保存一次不可变内容版本。替换文档先建新 Version，只有新版本完整解析成功后
才切换 `active_version_id`。

核心字段：

- Document：`id`、`tenant_id`、`knowledge_base_id`、`title`、`source_uri`（仅描述来源，不自动抓取）、
  `active_version_id`、`status`、创建/更新时间。
- Version：`id`、`tenant_id`、`knowledge_base_id`、`document_id`、`version_no`、`content_hash`、
  `raw_text`、`mime_type`、`status`、`error`、`extractor_model`、`created_at`、`activated_at`。
- Version 状态：`queued` → `processing` → `ready`；部分图抽取失败可为 `ready_with_warnings`；
  整体失败为 `failed`。

同一文档相同 `content_hash` 的重复上传应返回现有版本或作为幂等重试，不重复计费。对外响应不回显
`raw_text`，除非调用者请求文档内容且具有管理权限。

### 4.3 `knowledge_chunks`

一个 Version 对应多个有序片段：

`id, tenant_id, knowledge_base_id, document_id, document_version_id, chunk_index, content,
embedding, token_count, metadata, created_at`

- 唯一约束：`(document_version_id, chunk_index)`。
- 索引：`(tenant_id, knowledge_base_id, document_version_id)`；向量 HNSW 使用 cosine operator class。
- `metadata` 保存章节标题、来源页码等解析器提供的信息；当前纯文本导入时允许为空。
- 切片建议从 **500–800 tokens、80–120 tokens overlap** 起步，经验收集评估后再调；
  token 估算需与模型限制兼容。

### 4.4 `knowledge_entities`

实体采用知识库内规范化身份，不跨知识库自动合并：

`id, tenant_id, knowledge_base_id, entity_type, canonical_name, normalized_name, properties,
status, created_at, updated_at`

- 初始 `entity_type` 采用小型可扩展集合，例如 `person`、`organization`、`product`、`project`、
  `location`、`concept`；未知类型归 `concept` 或 `other`，不让模型自由制造类型体系。
- `(knowledge_base_id, entity_type, normalized_name)` 建唯一索引。
- `normalized_name` 做 Unicode NFKC、空白和大小写规范化；不做跨语言翻译或激进合并。
- 别名放 `knowledge_entity_aliases`：`tenant_id, knowledge_base_id, entity_id, alias,
  normalized_alias`，对 `(knowledge_base_id, normalized_alias)` 建非唯一检索索引。

若控制迁移规模，也可在 0.4.0 把 aliases 存在 JSONB；但必须有可重复的规范化规则和来源校验。

### 4.5 `knowledge_relations` 与 `knowledge_evidence`

Relation 是图边，Evidence 是支持某个实体或关系的原文片段：

- Relation：`id, tenant_id, knowledge_base_id, subject_entity_id, predicate, object_entity_id,
  properties, status, created_at`
- Evidence：`id, tenant_id, knowledge_base_id, document_id, document_version_id, chunk_id,
  entity_id nullable, relation_id nullable, quote, start_offset, end_offset, confidence,
  extractor_model, created_at`

Evidence 必须且只能指向一个 `entity_id` 或 `relation_id`（数据库 CHECK 约束）。外键限制 entity、
relation、chunk 必须属于同一租户/知识库。关系唯一性先按
`(knowledge_base_id, subject_entity_id, normalized_predicate, object_entity_id)` 合并；
不同文档/版本分别保留 Evidence，不覆盖旧证据。

图查询必须只使用**当前 active document version** 的 Evidence。旧版本事实保留以支持审计/回滚，但不参加
默认召回；清理过期版本可放到后续维护作业。

### 4.6 `knowledge_ingestion_jobs`

`id, tenant_id, knowledge_base_id, document_id, document_version_id, status, attempts,
lease_owner, lease_expires_at, error_code, error_message, created_at, started_at, finished_at`

使用 `SELECT ... FOR UPDATE SKIP LOCKED` 原子认领工作；设置 lease 以便进程崩溃后重新认领。
重试次数、并发数与单文档限制必须有上限。错误消息中不得记录密钥或完整敏感正文。

### 4.7 `run_knowledge_sources`

为每次 Run 记录实际注入模型的来源：

`id, tenant_id, run_id, knowledge_base_id, document_id, document_version_id, chunk_id,
retrieval_method, score, cited_facts, created_at`

唯一约束可设为 `(run_id, chunk_id)`；同一片段同时由向量和图检索命中时，合并 `retrieval_method`
与最高融合分数。该表用于复现、引用回显和审计，不能仅依赖模型自由生成的文件名。

另需记录每次检索尝试（包括无结果/失败）的运行状态，可扩展为 `run_knowledge_searches`：
`tenant_id, run_id, status, error_code, query_hash, result_count, started_at, finished_at`。
这样框架的 best-effort fallback 即使没有返回片段，也不会让知识服务故障在业务侧不可见。

## 5. 文档摄取流程

1. **创建/授权**：管理员在当前 tenant 下创建知识库；创建者获得该库的管理权限，其他主体必须有
   `knowledge:read` 和对应知识库 Grant。
2. **接收与去重**：只接收支持的 UTF-8 文本，校验内容非空、字节大小上限、MIME 类型和租户配额；
   不接收任意远端 URL，避免 SSRF。计算 SHA-256，创建 DocumentVersion 和 Job。
3. **解析与切分**：纯文本/Markdown 规范化；保留标题层级和段落边界，产生有序 chunk 与章节 metadata。
4. **Embedding**：批量调用现有 `Embedder`，确认每个向量维度与 KnowledgeBase 配置一致。
5. **实体关系抽取**：逐 chunk 请求结构化输出。抽取实体、规范名、别名、关系、方向、置信度和
   `evidence_quote`。不让抽取模型自行写数据库。
6. **校验**：Pydantic/schema 校验；实体 key 必须存在；quote 必须是本 chunk 原文的精确子串；
   offsets 与原文一致；confidence 在 `[0,1]`；拒绝空关系、非法类型和超过数量限制的结果。
7. **Upsert**：同一知识库内按规范化身份合并实体和关系，新增 Evidence；写入 chunk 向量。
   每一步以 `(document_version_id, chunk_index)` 幂等，job 重试不重复制造数据。
8. **激活**：只有所有 chunk 均可向量检索且关系结果已提交后，在短事务中切换 Document 的 active version，
   将 Version/job 标记为 `ready`。抽取部分失败时可标记 `ready_with_warnings`，并保留可用的向量片段。
9. **替换/删除**：新版本激活后旧版本自动退出默认检索；删除文档先软删除并停止召回，后台再按外键关系清理
   chunks、evidence 和不再被引用的图边/实体。

### 抽取结果例子

```json
{
  "entities": [
    {"key": "org_a", "type": "organization", "name": "星河科技", "aliases": ["星河"]},
    {"key": "product_b", "type": "product", "name": "云桥平台", "aliases": []}
  ],
  "relations": [
    {
      "subject": "org_a",
      "predicate": "owns",
      "object": "product_b",
      "evidence_quote": "星河科技负责云桥平台的建设与运营。",
      "confidence": 0.93
    }
  ]
}
```

抽取与引用以原文为准。LLM 返回了不存在的原文 quote 时，舍弃该 relation，不可用模型补写的解释替代证据。
重复事实采用“多条来源证据支持同一规范化边”；相反事实也并存，回答时呈现不同来源和时间，不在入库时
自动覆盖或裁决真伪。

## 6. 混合检索与 Graph-RAG

### 6.1 查询流程

1. 从本次运行的 `tenant_id`、Agent `knowledge_base_ids`、调用者授权解析出**允许知识库 ID 集合**；
   结果为空就不查知识库。
2. 查询解析首版使用原问题文本、实体名和 alias；不先调用额外 LLM 做 query rewrite。
3. 并行获取候选：
   - Vector：在允许知识库 + active versions 范围内取 top 20 chunk。
   - Entity：对 canonical name / alias 做规范化精确匹配；后续可加 trigram 模糊匹配。
   - Graph：从命中实体沿 active relation/evidence 向外最多 2 hop；限制每跳节点数、关系数及 predicate。
   - Evidence：每条图关系必须回连至至少一个 active source chunk。
4. 将图路径映射回来源 chunk，按 chunk 去重；合并向量、实体、图路径的候选。
5. 使用 Reciprocal Rank Fusion 起步合并排序；实现时固定默认参数、配置上限并用验收集调参，
   避免不同量纲的相似度/LLM 置信度直接相加。
6. 返回 top-k KnowledgeEntry；每条包含 `content`、稳定 `source`、`similarity` 和 citation metadata。
7. 对检索内容按 token 预算截断；保存最终实际进入上下文的来源到 `run_knowledge_sources`。

### 6.2 图遍历约束

- 只支持有向实体关系，谓词先做小写/空白规范化；关系方向由抽取结果保留。
- 默认 1 跳，复杂问题可在服务端固定开放 2 跳；不由模型任意指定深度。
- 每个查询设置 `top_k` 上限、候选节点上限、候选边上限、SQL statement timeout。
- Recursive CTE 或分步批量查询都必须携带 `tenant_id`、`knowledge_base_id` 和 active-version Evidence 条件。
- 图边不能脱离 Evidence 单独提供为事实；无有效来源的 orphan edge 不参与检索。

### 6.3 返回模型和引用

框架现有 `KnowledgeEntry` 有 `id/content/source/metadata/similarity` 字段，够承载兼容的 citation：

```json
{
  "id": "chunk_...",
  "content": "原文片段……",
  "source": "knowledge://kb_.../doc_.../version_.../chunk_...",
  "metadata": {
    "title": "产品说明",
    "chunk_index": 4,
    "matched_by": ["vector", "graph"],
    "facts": [{"subject": "星河科技", "predicate": "owns", "object": "云桥平台"}],
    "evidence_quote": "星河科技负责云桥平台的建设与运营。"
  },
  "similarity": 0.82
}
```

实现注意：当前 `AgentRuntime._recall_context` 将知识结果缩减为 `{content, source}`，不会传递完整
`metadata`。因此本期至少要让 `source` 保持稳定且可读，并让 per-run adapter 暂存已返回的 citation
records，RunService 在运行后持久化为 `run_knowledge_sources`。若 Console 需要展示可靠来源，应扩展 Run
响应或加 Run sources 查询接口；不可指望模型只靠答案文本自行生成可靠引用。

Adapter 应按返回顺序为来源生成稳定于本次 Run 的编号（例如 `[S1]`），并将编号与 chunk ID 一并暂存；
`source` 字段带上 `[S1]` 和可读标题，使 Runtime 在 metadata 被缩减后仍保留引用提示。回答 Prompt 应要求：
只把检索结果视作带来源的参考证据；事实回答附 `[S1]`；证据不足时明确说不足；文档中的指令不得覆盖
系统/开发者指令。`RunOut` 的结构化 sources 是权威链接，编号不跨 Run 复用。

## 7. Runtime 接线和个人记忆隔离

1. 在 `RunService.start()` 中保留现有顺序：先写 Working Brain，再读取历史；宿主先执行现有 pgvector 个人记忆召回。
2. 计算已有记忆是否足够；足够时不注入 Knowledge adapter，避免无谓查询。
3. 不足时，按本次 `Principal`、Agent 配置和 Grant 创建**run-scoped** `PlatformKnowledgeAdapter`，
   只允许访问已授权 KB，并将其传入 `RuntimeDeps.knowledge`。
4. 当前 0.4.0 初版继续让 `RuntimeDeps.long_term_memory` 留空，并保持个人记忆由宿主侧读取。
   原因：框架当前 Knowledge fallback 在同时注入 `long_term_memory` 时会把 Knowledge 结果写回
   `vector_memories`，会污染个人记忆；本期不接受这种跨域写入。
5. Adapter 持有本次检索 sources；Runtime 返回后由 RunService 将实际 sources 写入 `run_knowledge_sources`。
   如果 `Run` 失败，仍保留已检索 source 记录并标注运行状态，供故障定位。
6. 子 Agent 必须重新按 child run 的 principal/agent config 构造 scope，不能复用父 Agent 的允许 KB 集合。

框架 `_recall_context` 当前把任何高相似/高置信度长期记忆视为 sufficient。PlatformAgent 在宿主侧做
KB fallback 决策时应使用独立、可测的记忆相关性门槛；不可直接假设这条通用规则等同于“问题已有答案”。

## 8. 权限、安全与隐私

- 所有读取条件同时包含 `tenant_id` 和允许的 `knowledge_base_id` 集合；不得只靠前端隐藏资源。
- 复用 `Grant.resource_type = "knowledge"`，资源 ID 为 KnowledgeBase ID；新增 `knowledge:manage`
  管导入/删除，`knowledge:read` 管检索/查看来源。Agent 配置的 KB 还必须与调用者权限求交集。
- 若调用者没有 KB read 权限，Agent 不能通过自动 fallback 读取该 KB；跨租户资源对外返回 404。
- 来源 URI 只用内部 ID，不包含文件系统路径、远端签名 URL 或原始凭据。
- 原文、抽取结构和 LLM 请求要有日志脱敏策略；默认不写完整原文到日志。
- 文档可能包含 prompt injection：检索到的原文需作为引用材料隔离，不能变成系统指令。
- 删除文档须使其立即退出召回，再异步清理 embedding、实体/关系证据和来源缓存。
- 设定每租户 KB 数、文档字节数、单文档 chunk 数、每批 embedding 文本数、LLM 抽取并发和费用上限。

## 9. API 草案

所有接口挂在 `/v1`，由 JWT principal 和现有 permission dependency 保护。下列路径是新设计，不是当前已存在 API。

| Method / Path | 权限 | 行为 |
|---|---|---|
| `POST /knowledge/bases` | `knowledge:manage` | 创建知识库，固定 embedding 配置 |
| `GET /knowledge/bases` | `knowledge:read` | 只列出当前 tenant 且 caller 有权读取的 KB |
| `GET /knowledge/bases/{kb_id}` | `knowledge:read` | 查看 KB 与文档统计 |
| `POST /knowledge/bases/{kb_id}/documents` | `knowledge:manage` | 提交纯文本/Markdown，返回 Document 与 queued Job |
| `GET /knowledge/bases/{kb_id}/documents` | `knowledge:read` | 分页查看文档和活动版本状态 |
| `GET /knowledge/ingestion-jobs/{job_id}` | `knowledge:read` | 查询分阶段状态、错误码与计数 |
| `POST /knowledge/bases/{kb_id}/documents/{doc_id}/reindex` | `knowledge:manage` | 对当前内容重建 embedding/graph |
| `DELETE /knowledge/bases/{kb_id}/documents/{doc_id}` | `knowledge:manage` | 立即 tombstone，再排队清理 |
| `POST /knowledge/query` | `knowledge:read` | 调试混合召回，返回 chunks、图路径与 citations |
| `GET /runs/{run_id}/knowledge-sources` | Run read permission | 返回本次 Agent 实际注入的来源 |

文档导入 body 首版可采用 `title`, `content`, `mime_type`, `source_uri?`, `metadata?`；`source_uri` 仅作
来源描述，不触发服务器网络请求。上传大小和 top-k 上限由配置及 schema 硬性限制。

## 10. 版本拆分与实现顺序

### 0.4.0-A：知识库和可检索文档

- Alembic 增加 KB、Document/Version、Chunk、Ingestion Job 表及 tenant 索引。
- 纯文本/Markdown 入库、hash 去重、chunking、embedding、状态查询、失败可重试。
- 向量检索 + citation；先打通 `Knowledge.search` 和运行时隔离。

### 0.4.0-B：图谱抽取与 Graph-RAG

- 增加 Entity、Alias、Relation、Evidence 模型和索引。
- 结构化抽取、原文 quote 校验、幂等 upsert、证据版本过滤。
- 增加实体命中、受限图遍历、图结果映射回原文 chunk、混合排序。

### 0.4.0-C：授权、审计和验收收口

- 新增 `knowledge:manage` / `knowledge:read` 权限码和 knowledge Grant 流程。
- Agent 配置 KB 范围和请求用户权限做交集，落 `run_knowledge_sources`。
- 评估检索准确性、引用完整率、跨租户隔离、替换/删除与恢复场景。

### 后续版本

- PDF/Office/OCR、对象存储、外部任务队列、多语言词法检索、reranker、人工实体合并/关系审核、
  图谱浏览器和个人 Memory Graph 应另立范围，不作为本 0.4.0 方案的隐含交付。

## 11. 验收标准

### 功能与来源

- 一个 Markdown 文档成功导入后，可查到 Document 状态、chunk 数、实体/关系数及来源 quote。
- 同文档重复提交幂等；替换文档成功前仍能查旧版，激活后检索不再返回旧版证据。
- 每条进入 Graph-RAG 上下文的 relation 都有至少一个 active chunk evidence。
- 通过关系问题能召回实体路径，并至少返回一条对应原文；无证据时不返回“无来源图事实”。
- 对没有足够个人记忆的问题执行知识检索；记忆足够时不产生不必要的 Knowledge query。
- Run 来源可从数据库/API 查回，并能指向知识库、文档版本和 chunk。

### 安全与韧性

- tenant A 不能枚举、检索、通过 Agent 间接访问 tenant B 的 KB/document/entity/chunk。
- 同 tenant 无 `knowledge:read` Grant 的主体不能借用 Agent 配置绕过 ACL。
- 上传无效内容、抽取输出不合法、LLM/embedding 超时均有明确 Job 状态和错误，不把半成品设为活动版本。
- Worker 处理同一 job 并发时至多一个有效 claim；过期 lease 可恢复，重复执行不生成重复证据。
- 文档删除后立即不再出现在 query 结果，异步清理失败可观察、可重试。
- 自动抽取 quote 必须能在源 chunk 中精确定位；不满足校验的 assertion 不进入 active 图。

### 性能基准

用固定小型中文验收集（含实体直查、关系问答、同名实体、相互矛盾来源、无答案问题）验证：

- Recall@5、引用命中率、关系证据精确率分别统计，不只看 LLM 最终答案。
- 首版目标基准在实现前确定；验收报告注明文档数、chunk 数、抽取模型和 embedding 模型。
- 单次 query 有固定 SQL/LLM/embedding 调用上限，图遍历最多 2 跳，不得因为环路或高度节点无限扩展。

## 12. 测试矩阵

- **Unit**：文本规范化、chunk 边界、实体 canonicalization、证据 quote/offset 校验、RRF 排序、
  图遍历深度/上限、版本激活规则。
- **Adapter/DB**：tenant 与 KB filters、向量维度、复合外键/约束、active-version evidence 过滤、
  删除 tombstone 和 orphan 清理。
- **Job**：幂等重试、lease 超时重领、LLM/Embedder 失败、部分抽取失败的 `ready_with_warnings`、
  新版本失败不影响旧活动版本。
- **API**：JWT、permission codes、Grant、404 tenant 隔离、请求体限额、分页和错误响应。
- **Runtime**：memory sufficient 时不搜 KG；memory insufficient 时只搜允许 KB；子 Agent 独立授权；
  citation source 随 Run 可持久化；知识内容不会写进 `vector_memories`。
- **Evaluation**：小型中文 Knowledge Golden Set 对实体检索、关系路径、引用和拒答分别测量。

当前业务层单元测试主要用 FakeSession，不会验证 PostgreSQL 专属的 pgvector、复合约束、
`SKIP LOCKED` 或 Alembic 行为。0.4.0 必须另设可选的真实 PostgreSQL + pgvector 集成测试阶段，
至少跑迁移升级/回滚、索引创建、隔离过滤、并发 job claim 和版本原子切换；不能把 FakeSession 通过当作数据库验收。

## 13. 关键风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 抽取产生幻觉 | 要求原文 quote；精确子串校验；断言保留 confidence 和 extractor 版本；不据此覆盖来源 |
| 中文语义召回效果不稳定 | 固定业务验收集；向量 + 实体 alias + 图候选融合；按数据结果再决定 trigram/reranker |
| 多租户越权 | Adapter 按 run 构造不可变租户/KB scope；所有 SQL 重复 tenant filter；负向隔离集成测试 |
| 模型/维度更改造成索引不兼容 | KB 固定模型/维度；新版本重建并验证后原子切换 |
| 长任务跨请求或服务重启 | Job 表 + lease/重试；版本状态机；不把全量 ingest 放在 API 请求生命周期 |
| 图关系缺少来源或事实冲突 | Evidence 必填；活动版本过滤；保留多来源和时间，不做无证据自动裁决 |
| 检索内容诱导模型越权 | 内容作为不可信引用注入；工具授权仍由 Runtime PermissionChecker 决定 |

## 14. 与当前路线图的关系

本设计把 PlatformAgent 0.4.0 的“Knowledge/Retriever + RAG + KG”具体化为**租户业务知识库**。
现有 `vector_memories` 与未来 Knowledge 数据分别存储、分别授权、分别清理。个人对话 Memory Graph
未纳入本期，若未来要做，应另建个人/会话作用域和删除策略，不能复用本文 KB 图的 ACL/生命周期。
