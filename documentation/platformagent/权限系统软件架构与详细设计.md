# PlatformAgent 权限系统软件架构与详细设计

> 状态：目标架构提案；本地 Tool 执行授权及通用 OIDC 登录/身份绑定首期已落地。
> 已实现：Grant 的 `execute` 动作在运行时按稳定资源 ID 判权；支持用户/角色 Grant、拒绝优先、旧 Grant 兼容以及未授权 Tool 的 Registry 过滤。另支持租户管理员配置通用 OIDC Provider、Authorization Code + PKCE 登录、显式绑定已有本地账号。对暂不能映射到稳定 ID 的旧授权（如内置 Tool 名称、Skill 版本）保留名称回退。
> 尚未实现：SAML、厂商专用 OAuth/通讯录 API、SCIM/部门/组同步、OIDC 自动开户、工具副作用前实时权限重查、多动作（discover/read/manage）ACL 或外部授权变更同步。

## 1. 架构目标

本设计解决以下工程问题：

1. Google、Apple、阿里云企业身份、微信/企业微信、钉钉、字节系身份接入不侵入授权核心。
2. 企业外部组可映射到租户内部角色，但外部身份声明不能直接授予平台权限。
3. 一个用户/角色可按稳定 Tool ID 授权 `discover/read/execute/manage` 等动作。
4. API、资源读取、Agent 调用、子 Agent、后台任务和恢复执行使用一致的授权规则。
5. 权限引擎可单元测试；数据库和第三方 API 被隔离在 Adapter 中。
6. 与现有 RBAC/Grant/JWT/Runtime 渐进兼容，不一次性替换平台身份和所有 API。

非目标：构建通用策略语言、任意 Python 插件加载、一次性实现所有厂商组织同步、将每个模块拆成微服务。

## 2. 约束与关键设计决策

### 2.1 认证和授权是两个独立子系统

认证输出平台内部身份：

```text
ExternalAssertion(provider_id, issuer, subject, verified_claims)
    -> LocalPrincipal(user_id, tenant_id, status)
```

授权只消费 `LocalPrincipal` 和 PlatformAgent 数据：

```text
AuthorizationRequest(subject, action, resource, run_context)
    -> AuthorizationDecision
```

Authorization Service 不调用 Google、微信或企业通讯录 API；Provider Adapter 不返回平台角色或权限。外部组同步走独立 Provisioning 流程。

### 2.2 双阶段 Tool 授权

当前 Ouroboros 在运行初始化时为 Agent 所有插件生成统一 Tool Schema；其 PermissionChecker 是同步接口。设计采用：

1. **Run composition 阶段（snapshot check）**：PlatformAgent 加载用户、租户、角色、Grant、Agent 绑定和 Tool 风险策略，构成不可变 `RunAuthorizationSnapshot`。据此只将调用者有权发现和执行的 Tool 装入模型可见 Registry。
2. **Tool invocation 阶段（live check）**：每个 Tool 被调用时，宿主 Adapter 使用短生命周期数据库会话重新检查用户/租户状态、Agent 绑定、当前 Grant、策略版本、参数限制和审批凭证，再执行外部副作用。

因此，Runtime 的同步 PermissionChecker 作为早期决策/审批提示，不是最终安全边界；最终安全边界必须在 Tool 执行 Adapter 内。若 live check 不可用或策略状态无法读取，写操作、外发和其他敏感动作失败关闭。

### 2.3 默认拒绝且管理角色不绕过风险策略

- 没有明确的功能权限或资源 Grant 时拒绝。
- 任何适用 deny 优先于 allow。
- 显式审批、策略义务、租户隔离不能被普通 `is_admin` bypass。
- 紧急 break-glass 是独立、限时、强认证、强审计的机制，不是静态 admin 布尔值。
- “Agent 绑定了 Tool”仅表示该 Tool 是 Agent 的候选能力，不表示运行发起者有权调用。

## 4. Core contracts

The following Python-like declarations are design-level contracts. Exact types should be introduced incrementally and not copied verbatim before checking existing public APIs.

### 4.1 Identity and authentication

```python
class ExternalIdentity(BaseModel):
    provider_id: str
    issuer: str
    subject: str
    email: str | None = None          # display/contact attribute, never identity key
    display_name: str | None = None
    claims: dict[str, object] = {}

class AuthenticatedPrincipal(BaseModel):
    user_id: str
    tenant_id: str
    session_id: str
    auth_method: str
    authenticated_at: datetime
    assurance_level: str

class IdentityProvider(Protocol):
    async def build_authorization_url(self, transaction: AuthTransaction) -> str: ...
    async def exchange_callback(self, code: str, transaction: AuthTransaction) -> ExternalIdentity: ...
```

Provider Adapter verifies protocol-specific signatures/tokens and returns a normalized, verified identity. It does not create local roles or permissions.

### 4.2 Authorization

```python
class AuthorizationRequest(BaseModel):
    subject: Subject
    action: str                        # e.g. tool:execute
    resource: Resource
    context: dict[str, object] = {}    # run, agent, data class, network, etc.

class AuthorizationDecision(BaseModel):
    outcome: Literal["allow", "deny", "require_approval"]
    reason_code: str
    policy_version: str
    matched_grant_ids: list[str] = []
    obligations: list[Obligation] = []
    expires_at: datetime | None = None

class AuthorizationService(Protocol):
    async def authorize(self, request: AuthorizationRequest) -> AuthorizationDecision: ...
    async def build_run_snapshot(self, run: RunIdentity) -> RunAuthorizationSnapshot: ...
```

Requirements:

- `authorize` is pure with respect to policy semantics; repository reads are injected.
- Every resource carries `tenant_id`, stable type and stable ID.
- Subject contains the platform principal and effective tenant roles; never a raw unvalidated IdP group claim.
- Decision includes an internal reason code for audit/support; external responses must not reveal resource existence across tenants.
- `obligations` can require approval or parameter/data constraints; callers must enforce them, not just log them.

### 4.3 Run snapshot and Tool guard

```python
class RunAuthorizationSnapshot(BaseModel):
    principal_id: str
    tenant_id: str
    agent_id: str
    allowed_tool_ids: frozenset[str]
    allowed_actions: frozenset[tuple[str, str]]
    policy_version: str
    group_membership_version: str | None = None

class ToolInvocationContext(BaseModel):
    principal_id: str
    tenant_id: str
    agent_id: str
    run_id: str
    tool_id: str
    tool_version: str
    call_id: str
    approval_receipt_id: str | None = None
```

The snapshot filters candidate Tools and avoids repeated database loads during LLM planning. The Guard takes the context and validated arguments, reauthorizes against current policy with its own DB session, validates approval binding, and only then calls the underlying Tool. Never share one SQLAlchemy `AsyncSession` between parallel Tool invocations.

## 5. Authorization model and data schema

### 5.1 Existing schema reuse

Keep the current tables initially:

- `roles`, `permissions`, `user_roles`, `role_permissions`.
- `grants` with `tenant_id`, `principal_type`, `principal_id`, `resource_type`, `resource_id`, `action`, `effect`.
- `users`, `tenants`, `tools`, `agent_tools` and `audit_logs`.

The first mandatory code fix is to preserve `Grant.action` in loading and decisions. Current `load_grant_keys` returns only `(resource_type, resource_id, effect)`, and current framework check has no action-aware resource key. The migration must not silently reinterpret old grants.

### 5.2 Target schema additions

#### `identity_providers`

```text
id, tenant_id, provider_key, provider_type, issuer, client_id,
secret_ref, discovery_url, scopes, capabilities, config_json,
status, created_by, created_at, updated_at
```

- Unique `(tenant_id, provider_key)` and an issuer/provider uniqueness constraint appropriate to product behavior.
- `secret_ref` points to a secret manager or deployment secret; do not store plaintext client secret in ordinary JSON.
- `discovery_url` must be admin-controlled and protected against SSRF: HTTPS only, validated issuer/host, no arbitrary redirects/private IPs.

#### `external_identities`

```text
id, tenant_id, provider_id, issuer, subject, user_id,
email_snapshot, display_name_snapshot, linked_at, last_login_at, status
UNIQUE(provider_id, issuer, subject)
```

Email is a mutable profile field. Database uniqueness prevents one external identity from being linked to two users.

#### `auth_transactions`

```text
id, provider_id, state_hash, nonce_hash, pkce_verifier_encrypted,
redirect_uri, expires_at, consumed_at, browser_binding_hash
```

Short-lived, single-use login transaction; store in a transactional DB or a suitably protected short-TTL store. Persist hashes where verification permits; never log raw authorization codes or tokens.

#### `auth_sessions` (or equivalent revocable session store)

```text
id, user_id, tenant_id, refresh_token_hash, auth_method,
created_at, expires_at, revoked_at, rotated_from_session_id,
last_seen_at, assurance_level
```

Platform access JWT is short-lived and carries only stable identifiers/session ID. Refresh token rotation and revocation enable account disable, identity unlink and IdP offboarding to take effect. Existing long-lived JWT behavior can remain during migration.

#### `external_groups` and `group_role_mappings`

```text
external_groups(id, tenant_id, provider_id, external_key, display_name, status)
group_role_mappings(id, tenant_id, provider_id, external_group_id, role_id,
                    sync_mode, created_by, created_at)
```

Map stable external group identifiers to local role IDs. Unknown or removed groups grant nothing. If group membership is cached, persist sync version/time and a bounded stale-membership SLA.

#### `grants` migration

Preserve `action` and add only fields needed by concrete policy:

```text
action                  # normalized action key, e.g. tool:execute
condition_json          # constrained schema, not executable expression
expires_at
created_by
updated_at
```

Add validated check constraints/enums for `principal_type`, `effect`, resource type and action namespace. For manageable uniqueness, add a unique constraint over principal/resource/action/effect after detecting and resolving legacy duplicates. Keep `tenant_id` in every resource lookup and grant query.

#### Tool policy metadata

Keep authorization separate from `Tool.config` secrets. Add a validated non-secret policy/manifest document or normalized fields:

```text
tool_id, risk_level, side_effect_class, default_approval,
allowed_parameter_policy, policy_version, active
```

Do not use the LLM-facing `manifest.permission` as the sole ACL. It describes tool capability/risk; user grants describe authorization.

## 6. Decision algorithm

Authorization Service evaluates normalized action and resource against one explicit evaluation context:

```text
1. Reject invalid/disabled principal, tenant or session.
2. Reject if request tenant != resource tenant.
3. Enforce platform hard-deny constraints (inactive resource, disabled Tool, forbidden risk).
4. Resolve direct and role-derived grants scoped to this tenant.
5. If any matching deny applies, return deny.
6. Require the functional permission code for the action.
7. Require explicit resource/action allow; no match means deny.
8. Evaluate constrained conditions and return deny when they do not match.
9. If approval/obligation required and no valid bound receipt exists, return require_approval.
10. Return allow with policy version and matched policy IDs.
```

For `tool:execute`, the effective authorization is the intersection of:

```text
principal has run:execute
AND principal has tool:execute
AND explicit (user or role, tool_id, execute) allow
AND no applicable deny
AND Agent is active and bound to this exact Tool
AND Tool is active and its risk policy permits the call
AND required approval is valid for this run/call/argument digest/policy version
```

Admin and break-glass are represented as explicit policy subjects/permissions, not a bypass before the hard-deny and obligation checks.

### 6.1 Permission and grant evaluation examples

| Functional permission | Resource grant | Outcome |
|---|---|---|
| missing `tool:execute` | role has Tool execute allow | deny |
| present | no Tool grant | deny |
| present | role allow, user deny | deny |
| present | user allow, role deny | deny (deny wins) |
| present | allow, approval required but absent | require approval |
| present | allow, exact approval receipt valid | allow |
| present | allow on same Tool name but different `tool_id` | deny |

## 7. Login and authorization sequences

### 7.1 Third-party login

```text
Browser      Auth API       Provider Adapter      External IdP       DB
   |             |                 |                   |              |
   | /authorize  |                 |                   |              |
   |------------>| create tx state/nonce/PKCE                         |
   |             |---------------- create tx ------------------------->|
   |<------------| redirect URL     |                   |              |
   |--------------------------------------------------->| authorize    |
   |<---------------------------------------------------| callback code|
   | callback(code,state)            |                   |              |
   |------------>| consume tx once  |                   |              |
   |             |---------------->| exchange + verify  |              |
   |             |                 |<------------------>|              |
   |             |<----------------| verified issuer+subject          |
   |             | lookup external_identity -------------------------->|
   |             | check tenant/user/session policy                    |
   |             | create/link only under explicit enrollment policy   |
   |             | issue platform session ---------------------------->|
   |<------------| short-lived platform access + refresh/session cookie|
```

The callback must consume the transaction exactly once and use strict redirect allowlisting. If no identity mapping exists and self-enrollment is disabled, return a generic enrollment error; do not create an unassigned user. Client-side tenant input is never authoritative.

### 7.2 One Tool call

```text
Run API -> RunService -> AuthZ snapshot -> Authorized Plugin Registry -> Runtime
                                                |                    |
                                                | filter schema      | LLM returns call
                                                |<-------------------|
                                                |                    v
                                               Tool Guard <- Runtime invoke
                                                   |
                                           fresh AuthZ check
                                                   |
                                      validate arguments/approval
                                                   |
                                      execute Capability/local Tool
                                                   |
                                      Audit decision + outcome
```

The final invocation check is mandatory even if the Tool was omitted/filtered at planning time: a model can return fabricated calls, saved checkpoints can outlive policy changes, and other call paths may invoke plugins.

## 8. Tool authorization integration with current Runtime

### 8.1 Run composition sequence

Target `RunService` responsibilities:

1. Verify the Run's stored tenant/owner/Agent and `run:execute` permission.
2. Load active Agent and its explicit plugin references within tenant scope.
3. Load Tool metadata using stable tool IDs; validate Capability provider ownership and active state.
4. Build `RunAuthorizationSnapshot`.
5. Filter unauthorized plugins before building `AgentDefinition.plugins`, so `registry.to_openai_schema()` exposes only authorized tools.
6. Wrap each executable Tool with a host `AuthorizedTool` guard carrying principal, tenant, Agent, run and policy context.
7. Inject only a snapshot-based, synchronous checker into current `RuntimeDeps` for framework prechecks and HITL signaling.
8. Store snapshot/policy version and composition hash on the Run for replay and audit.

### 8.2 Guarded invocation

The guard must:

1. Parse/validate args against the Tool manifest.
2. Open a dedicated `AsyncSession` from the configured session factory; it must not reuse a session concurrently shared by the runtime.
3. Reload active user/session, current roles/permissions/grants, Agent binding and Tool status.
4. Evaluate current policy and approval receipt.
5. Write an authorization audit/outbox entry according to risk policy.
6. Invoke underlying local or Capability client only after allow.
7. Record result metadata after completion; secrets and sensitive parameters are redacted.

The wrapper returns/rethrows errors according to the framework's established Tool error contract; it must never convert auth service errors to a success-shaped empty result. Capability adapter currently catches broad execution exceptions and turns them into failed `ToolResult`; the authorization guard must distinguish denied, approval-required and dependency-unavailable outcomes before reaching that transport adapter.

### 8.3 Multi-call execution

The Runtime may execute multiple calls concurrently. Each guarded Tool call has its own DB session and audit event. For a batch:

- Preauthorize every call before invoking any.
- If any call is denied or requires approval, invoke none of the batch.
- Bind approvals to the exact set of calls and canonical argument digests; replaying the checkpoint with changed args must be rejected.
- Concurrency limits and idempotency keys are separate from authorization; external side effects need their own idempotency behavior.

## 9. Provider adapter architecture

```text
IdentityProvider protocol
  ├─ OidcProvider (discovery/JWKS/Authorization Code + PKCE)
  ├─ OAuthProvider (vendor-specific code exchange/profile verification)
  ├─ SamlProvider (enterprise assertion validation)
  └─ DirectoryProvider protocol
       ├─ ScimDirectoryProvider
       ├─ WeComDirectoryProvider
       ├─ DingTalkDirectoryProvider
       └─ ByteDance/Alibaba enterprise directory adapters as required
```

Provider implementation outputs only normalized records:

```text
VerifiedIdentity(issuer, subject, profile)
DirectoryUser(external_id, active, attributes_redacted)
DirectoryGroup(external_id, display_name)
GroupMembership(external_user_id, external_group_id)
```

Protocol-specific packages should not import `smartagent.iam` or write `user_roles` directly. They call `IdentityLinkService` / `GroupRoleSyncService`, which validate tenant binding, allowed mappings, role protection and audit.

### 9.1 Provider registry

Use an explicit application registry/factory, not dynamic import from DB:

```python
providers.register("oidc", OidcProviderFactory(...))
providers.register("wechat", WechatOAuthFactory(...))
```

Persisted `provider_type` selects only a compiled-in factory. Provider config is schema-validated and versioned. A tenant admin may configure an allowed provider instance but cannot register executable code or arbitrary callback URLs.

## 10. API contracts

### 10.1 User login API

```text
GET  /v1/auth/providers
POST /v1/auth/{provider_key}/authorize
GET  /v1/auth/{provider_key}/callback
POST /v1/auth/refresh
POST /v1/auth/logout
POST /v1/auth/identities/{provider_key}/link
DELETE /v1/auth/identities/{identity_id}
```

Browser flows should prefer secure, HttpOnly, SameSite cookies for refresh/session material; access token handling follows the Console's threat model. Native clients use Authorization Code + PKCE. Avoid returning Provider access/refresh tokens to the browser.

### 10.2 Administrative APIs

```text
POST/GET/PATCH/DELETE /v1/admin/identity-providers
POST                   /v1/admin/identity-providers/{id}/test
GET/POST/DELETE        /v1/admin/users/{user_id}/identities
POST                   /v1/admin/provisioning/{provider_id}/sync
GET/POST/DELETE        /v1/admin/group-role-mappings
GET/POST/PATCH/DELETE  /v1/admin/roles
GET/POST/DELETE        /v1/admin/roles/{role_id}/permissions
GET/POST/DELETE        /v1/admin/tools/{tool_id}/grants
POST                   /v1/admin/authorization/simulate
```

All admin endpoints require function permission and tenant-bound resource authorization. `simulate` is advisory and must not be used as an execution permit.

### 10.3 Error model

Use stable machine codes:

| Code | HTTP | Meaning |
|---|---:|---|
| `UNAUTHENTICATED` | 401 | No valid platform principal/session |
| `ENROLLMENT_REQUIRED` | 403 or generic 404 flow | Valid external identity but not allowed into tenant |
| `AUTHORIZATION_DENIED` | 403 | Authenticated but action/resource not authorized |
| `APPROVAL_REQUIRED` | 409 | Action needs a pending human approval |
| `IDENTITY_LINK_CONFLICT` | 409 | External identity already linked |
| `PROVIDER_UNAVAILABLE` | 503 | Provider metadata/token endpoint unavailable |
| `AUTHORIZATION_UNAVAILABLE` | 503 | Policy state cannot be safely evaluated |
| `INVALID_AUTH_TRANSACTION` | 400 | Expired, replayed or mismatched state/nonce |

External error messages must not disclose whether an account/resource exists in another tenant. Detailed reason and policy IDs go to protected audit/support logs.

## 11. Cache, revocation and consistency

- Short-lived access token contains `user_id`, `tenant_id`, `session_id`, issuer/audience/expiry; it does not carry authoritative roles.
- Authorization snapshots are scoped to one Run and versioned. They are useful for deterministic Run setup but not sufficient for long-running side-effect authorization.
- Tool Guard live-checks current grants and active state before side effects.
- Role/grant/session/provider/group mapping mutation increments a tenant or policy version and invalidates cache.
- Group sync cannot be the only revocation path: provider sync latency and outage must have a documented max-staleness policy. For high-risk actions, stale group membership fails closed or requires an online verification.
- Never share authorization cache entries across tenant, principal, action or resource key.

## 12. Auditing and transactional behavior

Authorization produces a typed `AuthorizationAuditEvent`:

```text
event_id, occurred_at, tenant_id, principal_id, auth_method,
action, resource_type, resource_id, outcome, reason_code,
policy_version, matched_grant_ids, run_id, agent_id, tool_call_id,
provider_id, trace_id, redacted_metadata
```

For high-risk Tool calls, use a transactional outbox or equivalent durable pre-execution decision record:

1. Persist `authorization.allowed`/approval receipt before invoking the external side effect.
2. If durable audit cannot be recorded, do not invoke the Tool.
3. Persist completion/failure afterward with an idempotency/correlation ID.

For low-risk reads, policy may allow best-effort audit if product requirements permit, but this is an explicit per-action policy—not a global silent catch. Current `write_audit` is best-effort; retain it only for actions whose declared policy allows that behavior, and add tests for database failure.

## 13. Migration and compatibility plan

### Phase 0 — Baseline and action-aware grants

1. Add tests documenting current RBAC/Grant semantics and all `check_permission` call sites.
2. Introduce canonical action names and a parser/validator. The current API accepts only `execute`, the action currently enforced by the runtime.
3. Update grant repository to return structured Grants including `action`, `effect`, `tenant_id`, principal and optional expiry.
4. Add new `AuthorizationRequest`/`Decision` API in PlatformAgent while retaining `PermissionManager.check` as a compatibility adapter.
5. Migrate legacy grants to an explicit wildcard action to preserve their pre-migration resource-wide behavior; migrate local database Tool IDs where the mapping is unambiguous and retain a name fallback for unmapped resources.

### Phase 1 — Tool guard and exact grants

1. Add stable `tool_id` metadata through plugin loading, including Capability tools.
2. Build authorized plugin registry from run snapshot; filter Tool schemas by principal + exact Tool grant.
3. Add `AuthorizedTool` wrapper and live authorization immediately before side effects.
4. Add `tool:discover`, `tool:read`, `tool:execute`, `tool:manage`, `tool:manage-grants` permissions.
5. Make the `run:execute` endpoint, direct invoke, resume and child run share the same service.
6. Preserve role/admin compatibility only through an explicit legacy policy version; publish a migration path to explicit role grants.

### Phase 2 — OIDC and identity linking

1. Provider, auth transaction and external identity tables plus generic OIDC Authorization Code + PKCE are implemented in PlatformAgent migration `0008`.
2. Tenant admins can configure an OIDC issuer; `OIDC_ALLOWED_HOSTS` restricts the issuer and discovery/token/JWKS endpoint hosts.
3. OIDC identities are linked only after an authenticated existing user starts the link flow. Login never auto-links by email and never creates a local user; unlinked identities are denied.
4. Local password login remains available. Revocable refresh sessions and session-wide revocation are not implemented; existing access JWTs expire according to `JWT_EXPIRE_SECONDS`.

### Phase 3 — Role assignment and group provisioning

1. Implement group-role mapping preview/simulation.
2. Start with SCIM where enterprise IdP supports it; vendor directory adapters are separate deliverables.
3. Add scheduled reconciliation and explicit stale-membership behavior.
4. Require review for mapping high-privilege groups.

### Phase 4 — Broader resource ACL and policy obligations

Add Knowledge Base, Document, Memory, Agent, Skill, Evaluation and tenant configuration resources using the same action/resource contract. Add constrained conditions, parameter policies and break-glass only when supported by a concrete use case.

## 14. Test architecture

### Unit tests (pure policy)

- default deny, deny-overrides, allow requires action match.
- exact resource IDs and tenant matching.
- approval-required outcomes and policy obligations.
- admin cannot bypass hard deny or required approval.
- group mapping only creates configured tenant role assignments.

### Repository/service tests

- Grant loader preserves action and tenant.
- user/role grant union and deny precedence.
- duplicate grant constraints; expired grant handling.
- identity unique key `(provider_id, issuer, subject)`.
- identity unlink and session revocation.
- group sync removes stale mapped role assignment without touching manually assigned roles.

### API/provider tests

- state/nonce/PKCE mismatch, expired/replayed transaction, wrong issuer/audience/signature.
- account email collision does not auto-link.
- enrollment denied for unknown external identity.
- tenant discovery and callback host allowlist.
- provider outage returns explicit `PROVIDER_UNAVAILABLE`.

### Runtime integration tests

- unauthorized Tool not present in LLM schema.
- fabricated Tool call is denied by invocation guard.
- Agent binding without user grant is denied.
- Grant revoked after Run snapshot but before Tool invoke is denied.
- policy DB unavailable prevents a sensitive Tool side effect.
- parallel Tool invocations use isolated DB sessions.
- resumed checkpoint reauthorizes with current grants and invalidates stale approval after argument/policy change.
- child Agent receives only delegated Tool grants.
- audit failure follows configured risk class.

### Contract tests

- each Provider Adapter returns the same normalized identity model.
- each Tool Guard preserves the BaseTool/Plugin result and error contract.
- tests run without real provider accounts, PostgreSQL, or external services using fakes; PostgreSQL integration tests verify constraints and query tenant filters.

## 15. Operational rollout and observability

Metrics and structured logs should include bounded labels only:

- `auth.login.success/failure` by provider key and reason class (not subject/email).
- `authz.decision` by action/resource type/outcome/policy version.
- `authz.tool_schema_filtered` count.
- `authz.live_check.latency/error`.
- `identity.sync.lag` and membership version.
- `audit.outbox.pending/oldest_age/failure`.

Do not put user ID, email, token, Tool arguments or document content into metric labels. Alerts should detect sudden deny spikes, failed group sync, stale membership and audit outbox backlog.

Rollout order:

1. Deploy decision logging in shadow mode for existing runs; compare old and new decisions, without granting more access.
2. Enable Tool filtering for internal admin/test tenants.
3. Enable exact Tool grants for one pilot tenant; retain explicit migration allowlist for existing Agents.
4. Enable live Guard for all external side-effecting Tools.
5. Pilot OIDC with invitation-only enrollment.
6. Add a specific vendor/directory adapter only after a pilot validates its protocol, required scopes and offboarding semantics.

Shadow mode must never be treated as an authorization control. Final mode is server-side enforcement.

## 16. Delivery definition

The permission system is ready for project integration only when:

- An administrator can configure an identity Provider and safely map an external identity to the correct tenant user.
- A user can receive roles from local assignment or an explicitly configured external group mapping.
- A role can be granted permission to a particular Tool resource and action without granting other Tools.
- An Agent cannot expose or execute a Tool beyond both its binding and the caller's grants.
- Authorization is rechecked at the side-effect boundary, including resume and subagent execution.
- Cross-tenant tests, revocation tests, approval-binding tests and audit-failure tests pass.
- Operators can explain a decision from reason code, policy version and matched grant IDs without logging secrets.
