# PlatformAgent 可组合能力模块化架构设计

> 状态：架构提案，尚未实现。本文描述 PlatformAgent 如何把权限、审计、知识库等平台能力解耦成可组合模块，供不同项目植入。
> 当前代码事实以[业务层详细设计](./业务层详细设计.md)为准；本文中的模块清单和接口是目标设计，不代表已具备对应实现。

## 1. 目标与边界

目标不是把每个 Python 包都做成独立微服务，也不是允许客户上传代码动态扩展平台，而是：

1. 通用运行时和平台核心保持稳定。
2. 领域能力通过明确契约接入，可以单独启用、替换实现或组合。
3. 不同项目使用不同的能力配置、领域包和 UI/API 面，不复制 Agent Runtime。
4. 租户隔离、授权和审计作为平台安全底线，不因关闭某个可选模块而绕过。
5. 已有业务逐步迁移到模块边界，避免一次性重写。

本文中的“植入”指应用装配时启用一组受信任的能力模块，不是把任意模块代码注入运行中的进程。

## 2. 当前基线

当前仓库已具备以下基础：

- **Ouroboros 2.0.0**：业务无关的 Agent Runtime、Plugin 协议和 `ouroboros.ports`。
- **PlatformAgent 0.3.0**：多租户、JWT/RBAC/Grant、Run/Step 持久化、审计、个人长期记忆、评测、实验、成本及运行装配。
- **Capability Registry 0.3.0**：通过 HTTP 管理和同步外部 MCP/API Tool。
- **业务知识库**：尚未实现。Knowledge/Retriever 已有框架协议，平台级文档摄取、检索、来源证据和知识授权仍是设计/规划。

因此，架构演进应先抽取现有 IAM、审计、运行装配的边界，再新增 Knowledge 模块；不应把它们误当成已经存在的通用模块系统。

## 3. 目标架构

```text
垂直应用 / 客户项目
┌───────────────────────────────────────────────────────────────┐
│ Domain Pack：医疗信息助手 / 法务资料助手 / 客服助手 / 自定义   │
│ 提示词、流程、输出 Schema、知识范围、工具白名单、评测集       │
└──────────────────────────┬────────────────────────────────────┘
                           │ 声明需要的能力和配置
┌──────────────────────────▼────────────────────────────────────┐
│ PlatformAgent Composition / Module Host                       │
│ 配置校验、依赖解析、模块装配、能力目录、健康检查、请求上下文   │
├──────────────────────┬────────────────────────────────────────┤
│ 必需的安全与运行核心 │ 可选/可替换的能力模块                   │
│ Tenant / Identity    │ Knowledge / Memory / Tools              │
│ Authorization        │ Audit Sink / HITL / Evaluation           │
│ Run / Event / Config │ Observability / Cost / Sandbox           │
└───────────┬──────────┴────────────────────┬───────────────────┘
            │ Ports / Adapters               │
┌───────────▼─────────────┐      ┌──────────▼────────────────────┐
│ Ouroboros AgentRuntime  │      │ PostgreSQL / Redis / ACR       │
│ run / resume            │      │ Capability Registry（HTTP）    │
└─────────────────────────┘      │ 外部模型、存储、业务系统       │
                                 └───────────────────────────────┘
```

### 3.1 三个稳定层次

| 层 | 职责 | 变更原则 |
|---|---|---|
| Runtime Kernel（Ouroboros） | Agent 循环、Plugin/Tool 执行、框架端口 | 保持业务无关；只有通用执行契约才进入框架 |
| Platform Core（PlatformAgent） | 租户、身份、请求/运行上下文、授权入口、运行持久化、装配、事件/配置 | 作为所有方案共用的宿主；核心安全不依赖可选模块 |
| Capability Modules + Domain Packs | 知识、工具、审核、评测等能力，以及行业/项目配置 | 可组合、可替换；领域规则不回流到 Runtime Kernel |

Capability Registry 是外部工具目录和执行服务，不等于 PlatformAgent 的通用 Module Host。早期模块可在 PlatformAgent 进程内按 Python 包边界部署；仅在需要独立扩缩容、隔离或独立运维时再拆服务。

## 4. 模块分类：不是所有能力都能“随意关闭”

### 4.1 平台必需核心

- **Tenant Context**：为每次请求和运行确定租户，不接受由模型或客户端任意覆盖。
- **Identity Provider**：验证调用身份。单机/开发环境可配置简化实现，生产配置必须显式选择身份来源。
- **Authorization**：对 API、数据、知识、工具和运行动作做服务端授权；默认拒绝、显式允许。
- **Run / Transaction Core**：记录运行状态、租户、发起者、版本与关联事件。
- **Module Host**：校验模块配置和依赖，构建一次运行所需的依赖集合。

核心安全能力可以替换后端实现，但不能因为某项目未启用 UI 模块就绕过授权。

### 4.2 可选或可替换的平台能力

| 能力模块 | 职责 | 可替换点/依赖 |
|---|---|---|
| Audit | 记录身份、授权决策、数据访问、工具调用、管理变更和运行结果 | Sink 可为 PostgreSQL、外部 SIEM；敏感模式要求持久化审计能力就绪 |
| Knowledge | 文档导入、版本、切片、索引、检索、来源证据 | Embedding、向量/文本存储、解析器可替换；检索必须带授权范围 |
| Memory | 会话工作记忆和用户长期记忆 | Redis、PostgreSQL/pgvector 等适配器；与业务知识库分开授权和生命周期 |
| Tool Catalog / Executor | 平台 Tool、MCP/API Tool 的发现和受控调用 | 本地 Tool Registry 或 Capability Registry HTTP 适配器 |
| Approval / HITL | 高风险动作暂停、审批、恢复及审批记录 | 不同项目可有不同审批人解析和通知通道 |
| Evaluation | Golden Set、Judge、回归评测与发布门禁 | 评测集、Judge 和阈值按领域配置 |
| Observability | Trace、指标、结构化日志、告警 | OpenTelemetry、Prometheus 或托管服务 |
| Cost / Model Routing | 模型路由、配额和成本归因 | 模型目录、价格表和预算策略可按租户替换 |
| Sandbox | 不可信代码/工具的隔离执行 | 本地禁用或外部隔离 Worker；不可降级成普通宿主进程执行 |

模块“可选”表示项目可以不使用该业务能力，不表示可以跳过其安全前置条件。例如使用私有知识库时，Knowledge 必须依赖 Authorization；否则知识模块不得启动或提供数据。

## 5. 模块契约与注册

### 5.1 模块清单

每个受信任模块提供静态清单，至少描述：

```yaml
id: platform.knowledge.pgvector
version: 1.0.0
provides: [knowledge.search, knowledge.ingest]
requires: [platform.tenant-context, platform.authorization, platform.audit]
optional_dependencies: [platform.embedding]
config_schema: KnowledgeModuleConfig
data_scopes: [knowledge.read, knowledge.manage]
health_check: required
migrations: owned-by-module
```

这是目标格式示例，不是现有可直接加载的配置。模块只能从应用构建时注册的可信目录中启用；不支持从管理 API 上传 Python 代码、任意 import 路径或执行未签名插件。

### 5.2 运行时统一上下文

各模块通过显式类型接收由 Platform Core 创建的上下文，而不是自行读取全局变量：

```text
RequestContext
  tenant_id
  principal_id / actor_type
  request_id / trace_id
  locale

RunContext
  RequestContext
  run_id / session_id / parent_run_id
  domain_pack_id + version
  granted_scopes
  deadline / cancellation token
  data_classification
```

`tenant_id`、身份和授权范围只能由宿主认证/授权流程产生。子 Agent 只继承明确委派的范围，不能自动获得父运行的全部凭据或上下文。

### 5.3 契约类别

模块通过可测试的 Protocol/Port 或服务 API 暴露能力，尽量不共享 ORM Model：

- `AuthorizationPort.authorize(subject, action, resource) -> Decision`
- `AuditPort.append(AuditEvent) -> receipt`
- `KnowledgePort.search(scope, query, filters) -> EvidenceSet`
- `ToolCatalogPort.list_allowed(scope) -> ToolManifest[]`
- `ApprovalPort.request(ApprovalRequest) -> ApprovalState`
- `EvaluationPort.evaluate(profile, candidate) -> EvaluationReport`

上面是接口方向的示意签名，最终 Python 类型需在实现阶段统一。模块间不得绕过端口直接查询别的模块私有表。

## 6. 权限与审计的安全设计

第三方登录、企业组到角色映射、Tool 资源级授权和现有代码迁移细节见[权限与第三方身份集成设计](./权限与第三方身份集成设计.md)。

### 6.1 权限分层

至少区分四类检查，不能只在 Agent 执行 Tool 时做一次权限校验：

1. **入口权限**：谁能调用 API、创建/修改 Agent、管理用户和模块配置。
2. **资源权限**：谁能读取哪些知识库、文档、记忆、运行记录和评测集。
3. **执行权限**：当前 Agent/Run 可以调用哪些 Tool、使用哪些参数范围。
4. **动作审批**：写入、外发、删除、付款、诊疗/法律等高影响动作是否需要人工确认。

决策规则建议采用 `deny > require_approval > allow`，未配置规则或授权服务不可用时默认拒绝敏感操作。必须把授权范围落实到实际数据查询（例如 `tenant_id + allowed_knowledge_base_ids`），不能只在 API 返回前过滤。

### 6.2 审计事件

审计事件建议统一字段：

```text
event_id, occurred_at, tenant_id, actor, action, resource_type, resource_id,
decision, run_id, trace_id, module_id, policy_version, metadata_redacted
```

- 授权拒绝、审批、数据导入/删除、知识检索访问、Tool 调用和配置变更都要有对应事件。
- 不在审计日志中默认保存完整提示词、文档正文、API 密钥或个人敏感信息；按字段分类和脱敏。
- 审计写入失败必须有明确策略：对合规/高风险操作应 fail closed 或进入持久化 outbox 后再执行；普通遥测允许降级。不能统一采用“尽力写入后静默吞错”。
- 既有 `audit_logs` 和 `write_audit` 可先作为 PostgreSQL Audit Adapter；当前实现有 best-effort 行为，迁移到新契约时需明确并分级调整失败语义，避免误称为强一致审计。

## 7. Knowledge 与 Memory 解耦

Knowledge 和 Memory 的业务含义不同，必须是两个可独立装配的模块：

- **Knowledge** 是组织/租户拥有、可管理版本、来源和权限的事实资料；回答需返回证据引用。
- **Memory** 是对话中的短期状态或用户长期偏好/事实，按用户、会话和保留期限管理。

两者不能共用未经区分的表、授权规则或删除策略。Knowledge 检索至少需要：

```text
tenant scope
∩ caller's knowledge grants
∩ Agent/Domain Pack allowlist
∩ document status/version policy
```

检索返回 `EvidenceSet`，包含 chunk/document/version/source、命中理由、权限范围和置信信息。上层回答应能引用证据；没有足够证据时明确不确定。检索结果和文档正文都视为不可信输入，不能当作系统指令执行。

首个实现可复用现有 PostgreSQL + pgvector，并按已写的[知识图谱与知识检索设计](./知识图谱与知识检索设计.md)逐步交付；模块接口不应把平台固定绑定到某一种向量数据库。

## 8. 能力组合与配置

### 8.1 Composition Profile

一个部署或租户使用一个经校验的 Profile，声明启用模块、版本、依赖和策略：

```yaml
profile: support-assistant
modules:
  identity: platform.jwt
  authorization: platform.rbac-grants
  audit: platform.audit.postgres
  knowledge: platform.knowledge.pgvector
  memory: platform.memory.redis-pgvector
  tools: capability.registry-http
  approval: platform.approval.manual
  evaluation: platform.evaluation.golden-set
domain_pack: customer-support@1.2.0
```

Profile 仅是设计示例。配置需要由管理员/部署系统管理；普通 Agent 提示词和模型输出不能增删模块。

### 8.2 启动时校验

Module Host 在应用启动或 Profile 发布时完成：

1. 校验模块 ID、版本和配置 Schema。
2. 验证依赖闭包、版本兼容和模块唯一性，检测循环依赖。
3. 校验强制安全能力是否存在；例如 `knowledge` 必须有 `authorization` 和审计策略。
4. 验证密钥引用存在但不回显秘密；校验数据库迁移状态和模块健康检查。
5. 生成不可变的有效 Composition Snapshot，Run 记录 profile/module/domain pack 版本。

任一必需条件失败，应阻止相关 Profile 启用并报告具体错误，不能静默退化到无权限、无审计或空知识库运行。

### 8.3 典型组合

| 方案 | 组合示例 |
|---|---|
| 内部知识问答 | Platform Core + JWT/RBAC + Audit + Knowledge + Evaluation |
| 客服回复草稿 | 上述组合 + Tool Catalog + Memory + 可选人工审核 |
| 法务资料助手 | Core + 强审计 + 授权 Knowledge + 来源引用 + 专业审核 + 法域评测 |
| 医疗信息整理 | Core + 最小化敏感数据 + 授权 Knowledge + 来源证据 + 医护审核 + 紧急升级规则 |
| 无知识库流程 Agent | Core + Tool Catalog + Approval；不启用 Knowledge/长期 Memory |

## 9. Domain Pack：领域差异作为配置和资产包

Domain Pack 不复制模块实现，负责组合各模块并定义领域规则，建议包括：

```text
domain-pack/
  manifest.yaml             pack ID/version/required modules
  instructions/              系统级约束、语气和范围
  workflows/                 有边界的业务流程定义
  schemas/                   输入/输出结构与验证规则
  policies/                  工具白名单、拒答条件、审批阈值
  knowledge/                  允许挂载的知识库引用（不内嵌生产密钥）
  ui/                         可选的导航/表单/字段配置
  evals/                      Golden Set、风险测试和发布门槛
```

医疗、法律的专业结论、审批规则和知识内容必须由具备资质的业务方维护和审查。Domain Pack 不能覆盖平台强制安全策略，不能直接授予更高权限，也不能取消租户隔离。

## 10. 数据、部署与 API 组合

- 早期所有模块可运行在 PlatformAgent 单体服务中，模块边界用包、Protocol、依赖注入和独立 service 实现。
- 共享 PostgreSQL 可以是首期部署选择，但表/迁移归属明确；跨模块访问走契约，不直接依赖其他模块 ORM。
- Redis 作为可选缓存/工作记忆后端；失效时根据能力安全等级明确定义降级策略。
- Capability Registry 继续经 HTTP 接入，网络超时和鉴权失败必须向上显式报错。
- API 路由可以按模块注册，但 OpenAPI、权限依赖、错误格式和租户上下文由 Platform Core 统一。
- Console 根据后端返回的能力清单显示功能；前端隐藏按钮不构成授权控制。
- 在隔离、部署独立性、资源伸缩或合规需求出现前，不按每个能力拆微服务。

## 11. 渐进实施路线

### 阶段 0：契约清点与基线测试

- 为当前 IAM、审计、插件装配、记忆和 Run 生命周期补齐接口级测试。
- 记录当前权限决策、审计失败和多租户查询的真实行为。
- 固化当前 API 行为和数据库 schema，定义迁移兼容要求。

### 阶段 1：建立 Module Host，但不改变功能

- 创建应用级 Composition/Module Host，只注册当前已实现的 IAM、Audit、Memory、Tool Catalog 等适配器。
- 从 `run_service.py` 提取明确的 `RunComposition`/依赖装配边界。
- 用依赖注入替代跨模块直接构造；先保留现有业务 API 和数据表。
- 启动校验依赖、配置和健康状态；为每次 Run 固化有效模块版本。

### 阶段 2：抽取安全契约

- 为身份、授权和审计定义稳定接口与事件模型。
- 将当前 `PermissionManager`、FastAPI RBAC 和 `AuditingPermissionChecker` 逐步包入 Adapter。
- 统一 API、知识资源、Tool 与 Run 的授权资源模型。
- 按操作风险区分审计持久化保证，逐步迁移 best-effort 路径。

### 阶段 3：交付 Knowledge 模块

- 按知识库设计实现知识库/文档/版本/片段/摄取作业与来源证据。
- 所有检索以租户、调用者授权、Agent allowlist 的交集为硬约束。
- 提供 Knowledge Adapter 注入 Ouroboros `RuntimeDeps` 的路径。
- 与个人长期 Memory 分表、分 API、分生命周期。

### 阶段 4：领域包与发布门禁

- 增加 Domain Pack 版本、校验、发布和回滚。
- 将工具 allowlist、知识库范围、输出 Schema、审批策略和评测集绑定到版本。
- 发布前运行领域回归测试；高风险领域还需人工专业审批。
- Console 展示当前配置来源和版本，运行记录可追溯。

### 阶段 5：按真实项目抽离可替换实现

- 先从至少两个不同业务项目的复用结果中识别稳定契约。
- 对确有需求的持久化、Embedding、Audit Sink、Identity Provider 增加替换 Adapter。
- 仅在出现独立扩缩容/隔离要求后抽服务；不要为抽象而抽象。

## 12. 验收标准

1. 同一 Platform Core 能运行至少两个不同 Composition Profile，而不复制 Run Service/Agent Runtime。
2. Profile 缺少必需授权或审计依赖时，发布失败且错误可定位。
3. 自动化测试证明跨租户不可读取 Run、Memory、Knowledge、Tool 配置和审计记录。
4. Knowledge 的搜索结果不能超出 caller grant、Agent allowlist 和文档有效版本范围。
5. 每次 Run 可还原触发它的模块、Domain Pack、策略和知识版本。
6. 替换一个 Adapter 不要求改 Ouroboros 核心，也不导致其他模块导入其私有 ORM。
7. Agent 提示词/LLM 输出无法启用模块、提升权限、修改模块配置或绕过审批。
8. 模块故障遵循显式 fail-open/fail-closed 分类；没有成功形状的静默空结果。

## 13. 明确不做

- 不把租户、HTTP、SQLAlchemy 或行业逻辑放进 Ouroboros。
- 不把 RBAC/租户隔离做成“默认关闭”的可选插件。
- 不把所有业务功能都实现成 Ouroboros `Plugin`：Module 是宿主级能力，Tool/Skill Plugin 是 Agent 可调用能力，两者生命周期和权限范围不同。
- 不允许用户在线上传任意 Python 插件、模块代码或没有签名的 Domain Pack。
- 不要求每个模块独立数据库、容器或微服务。
- 不把业务知识库与对话 Memory 混为一谈。
- 不宣称医疗/法律方案可取代专业人员判断或审核。
