# PlatformAgent 权限与第三方身份集成设计

> 状态：OIDC 通用登录与本地账号显式绑定、Tool `execute` Grant 已部分实现；SAML、厂商专用接入和组织/组同步仍为设计提案。
> 目标：支持 Google、Apple、阿里云身份服务、微信/企业微信、钉钉、字节系等身份来源，并以平台内部角色、权限和资源授权统一控制 API、Agent、知识库及单个 Tool。
> 软件组件、接口、数据库迁移、运行时接线和测试细节见[权限系统软件架构与详细设计](./权限系统软件架构与详细设计.md)。

## 1. 设计结论

必须把“谁登录了”和“登录后可以做什么”分开：

- **认证（Authentication）**：第三方证明外部身份；PlatformAgent 将外部身份稳定映射到本地用户和租户。
- **授权（Authorization）**：PlatformAgent 自己的角色、权限、资源 Grant 和策略决定可访问范围。第三方登录成功不等于获得管理员权限。

建议采用：

1. 面向用户登录，提供 OIDC/OAuth 适配器；对企业 IdP 增加 SAML 2.0 适配器。
2. 企业用户/组织成员同步，通过标准 SCIM 优先；没有 SCIM 时实现各厂商通讯录/组织 API Adapter。
3. 把外部用户组映射为**租户内的平台角色**，而不是把外部 token 里的任意 role/group 原样作为权限。
4. 使用 RBAC 管理功能权限，使用资源级 Grant 管理某个 Agent、Knowledge Base、Tool 实例等对象权限。
5. 对每一次 Tool 调用，先从模型可见的 Tool Schema 中排除无权工具，再在服务端执行前再次授权；Agent 绑定 Tool 不代表发起者有权调用。
6. 默认拒绝；跨租户拒绝；显式 deny 优先；需要审批的动作不能因用户有普通 execute 权限而跳过审批。

## 2. 当前实现与缺口

### 2.1 已有基础

当前 PlatformAgent 已有：

- `User`、`Tenant`、`Role`、`Permission`、`UserRole`、`RolePermission`。
- `Grant` 支持 `principal_type=user|role`、资源类型、资源 ID、`action` 和 `effect`。
- 业务端 `PermissionManager` 加载角色权限和 Grant；框架 `PermissionContext` 供执行时授权检查。
- 用户 JWT 不内嵌角色，HTTP 请求会从数据库重新解析用户和角色。
- FastAPI 侧 JWT/密码登录入口及 `require_permission`。
- 通用 OIDC Authorization Code + PKCE；租户管理员可配置 Provider，外部身份仅能由已认证的本地用户主动绑定，不按邮箱自动合并或创建账号。
- OIDC `state`/`nonce`/PKCE、单次有效事务、浏览器绑定 Cookie、ID Token issuer/audience/signature/nonce 校验；客户端密钥使用 Fernet 加密后存储。
- OIDC Provider 与 identity link 仍映射到 PlatformAgent 本地用户/租户；第三方声明不会自动授予角色或 Tool 权限。

### 2.2 需要修正/扩展的地方

- 目前 `User` 只有本地用户名/密码，没有独立的外部身份绑定模型和 Provider 配置。
- 当前 Grant 装载成 `(resource_type, resource_id, effect)` 三元组时没有保留数据库中的 `Grant.action`。因此它不能完整表达“同一 Tool 上 read 与 execute 不同授权”。
- 框架 `check_permission` 处理资源 Grant 时，动作/资源权限语义有限；需升级为显式 `subject + action + resource + context -> decision` 决策，而不能简单丢弃 action。
- Tool Manifest 上的 `permission` / `requires_approval` 是静态风险描述，不等于某个用户或角色对此 Tool 的授权。
- Agent 配置绑定 Tool 只表示 Agent 具备该候选能力，不应被解释为每位 Agent 调用者都获得 Tool 权限。

所以现有权限属于可演进的 RBAC/Grant 基础，不应宣传为已支持多 IdP、外部组织同步或完整 Tool 级 ACL。

## 3. 目标架构

```text
Google / Apple / 阿里云 IdP / 微信 / 企业微信 / 钉钉 / 字节系 / 企业 SAML IdP
                              │
                 Provider Adapter（协议/厂商差异）
                              │ 标准化身份 assertion
                              ▼
             External Identity Linker（issuer + subject）
                              │
                   本地 User + Tenant
                              │
     External Group/SCIM Sync ─┴─► Group-to-Role Mapping
                              │
                              ▼
              Authorization Service（平台权威）
        RBAC permission + user/role resource grants + policies
                  │                         │
              API/data access          Agent Tool execution
                                            │
                             pre-filter schema + invoke-time check
```

Provider Adapter 只负责验证登录响应、获取标准身份声明，以及可选的用户/组同步；不能自行决定平台权限。Authorization Service 不依赖特定身份厂商。

## 4. 第三方身份 Provider 设计

### 4.0 当前已交付的 OIDC 范围

首期实现的是通用 OIDC，不代表已接入表格中的全部厂商产品。管理员先为租户配置支持 OIDC 的 IdP，并在部署环境设置 `OIDC_ENCRYPTION_KEY`、`OIDC_ALLOWED_HOSTS` 和 `OIDC_PUBLIC_BASE_URL`。IdP 回调地址固定为 `{OIDC_PUBLIC_BASE_URL}/v1/auth/oidc/callback`。允许列表需覆盖该 IdP 的 issuer、授权、token 和 JWKS endpoint 主机。

本地用户先通过现有密码登录，再调用 `POST /v1/auth/oidc/{provider_id}/link` 获取授权 URL 并完成绑定。之后用户访问 `GET /v1/auth/oidc/{provider_id}/authorize` 登录。未绑定身份明确拒绝；不会按相同邮箱自动合并或自助创建用户。用户停用后，本地 JWT 鉴权仍会拒绝访问。当前没有 SCIM/通讯录同步、外部组映射或 JWT 主动撤销。

### 4.1 Provider 能力类型

Provider 注册时声明能力，不假设每个厂商都支持相同功能：

| 能力 | 含义 | 典型用途 |
|---|---|---|
| `login` | 浏览器或客户端完成用户认证 | Google、Apple、微信、企业微信、钉钉等 |
| `oidc` | 标准 OIDC Authorization Code 登录 | 支持 OIDC 的企业/公共身份服务 |
| `saml` | 企业 SAML 2.0 登录 | 企业已有统一身份平台 |
| `profile` | 获取基础用户资料 | 登录后补充展示名 |
| `group_claims` | 在可信断言中携带组织/组信息 | 只有经过验证的企业 IdP 可使用 |
| `directory_sync` | 同步用户、部门和组成员 | SCIM 或厂商通讯录 API |
| `provisioning` | 用户停用/离职状态同步 | SCIM 或厂商通讯录 API |

首选实现顺序：OIDC 标准适配器 → SAML 2.0 企业适配器 → 具有明确客户需求的国内厂商 Adapter。对支持标准协议的“阿里云身份”或企业 IdP 优先按标准 OIDC/SAML/SCIM 对接；厂商自有 OAuth、通讯录和组织 API 再单独实现适配器。不得仅因产品名相似就假设协议、字段或组同步能力一致。

### 4.2 Provider 能力矩阵（规划）

| Provider 类别 | 登录接入 | 组织/角色信息来源 | 注意事项 |
|---|---|---|---|
| Google | OIDC/OAuth 登录 Adapter | Workspace 场景由受信任组声明或 Directory/SCIM 同步提供 | 个人 Google 登录通常不等于企业组织成员身份 |
| Apple | Sign in with Apple Adapter | 通常需平台邀请/管理员分配角色 | 邮箱可能是 relay 地址；用 `issuer + subject` 绑定，不用邮箱做主键 |
| 阿里云 | 支持标准协议的企业身份服务优先 OIDC/SAML；具体企业目录 API 单独 Adapter | IdP 组声明或目录/SCIM 同步 | 不把云 RAM 控制台用户自动当成业务租户成员 |
| 微信 | 微信 OAuth 登录 Adapter | 通常由应用邀请/用户绑定/管理员分配 | 不应假设个人微信 OAuth 提供企业部门和组 |
| 企业微信 | 企业微信登录 Adapter | 企业 ID/成员 ID、通讯录部门/标签 API 或可用标准目录协议 | 必须校验企业归属；成员离职/禁用需同步撤权 |
| 钉钉 | 钉钉登录 Adapter | 企业内部用户/部门/角色 API 或标准目录协议 | 校验 Corp/Tenant 绑定和成员状态 |
| 字节系企业身份 | 按具体产品提供的 OAuth/OIDC/组织 API 建 Adapter | 组织成员/部门 API 或标准目录协议 | 先确定具体产品及授权范围，不把不同产品能力混作一个协议 |

这是一张适配规划表，不承诺所有厂商在任何账号类型下都提供组织同步能力。产品上线前需按具体产品文档和企业租户验证 scopes、审核要求、回调限制及用户停用事件。

### 4.3 Identity Link 与安全规则

外部身份唯一键使用 `(provider_id, issuer, subject)`；禁止使用 email 作为身份主键。

登录/绑定必须满足：

- Authorization Code + PKCE；严格校验 `state`、`nonce`、签名、issuer、audience、过期时间和回调 URI。
- 服务端保存 client secret、证书和 refresh token；加密存储且日志脱敏。浏览器不持有 Provider client secret。
- 第一次第三方登录只能通过已允许的租户入口、管理员邀请或明示的自助注册策略加入租户。
- 同邮箱用户不能自动合并本地账号；合并/绑定需要已有账号重新认证或租户管理员批准，并写审计事件。
- 一个外部身份不能被静默绑定到多个本地用户；解绑前需确认有其他有效登录方式或管理员恢复路径。
- 外部身份 token 仅用于完成认证/读取获准的用户资料，不作为 PlatformAgent API bearer token。登录成功后由平台签发自己的短期 access token / 可撤销 session。
- 用户停用、企业成员离职、Provider 解绑或租户禁用时，撤销相关 session；组同步失败不得自动扩大授权。

### 4.4 租户发现与账号入组

多个租户可各自配置相同 Provider；租户归属由租户登录入口、已验证的企业 ID、邀请或管理员绑定决定，不从客户端任意传入的 `tenant_id`、邮箱后缀或未经验证的 claim 推断。

对于公开 OAuth（个人 Google/Apple/微信）：

- 默认不自动创建可访问业务数据的账号。
- 可配置邀请制，接受邀请后才成为租户成员。
- 新成员角色使用明确的最小权限模板；禁止默认映射 admin。

对于企业 IdP：

- Provider 与一个或多个租户建立管理员确认的绑定。
- 外部 subject 映射本地用户；外部组经 allowlist 映射为平台 role ID。
- 未映射的组不授予权限；未知组不自动创建高权限角色。

## 5. 用户、组、角色与权限模型

### 5.1 逻辑数据模型

保留现有角色权限表并增补/规范化：

```text
users
  id, tenant_id, username, status, ...

identity_providers
  id, tenant_id, provider_type, issuer, client_id, encrypted_secret_ref,
  capabilities, config, status, created_at

external_identities
  id, tenant_id, provider_id, issuer, subject, user_id,
  email_snapshot, profile_snapshot_redacted, linked_at, last_login_at
  UNIQUE(provider_id, issuer, subject)

external_groups
  id, provider_id, external_group_key, display_name, status

group_role_mappings
  id, tenant_id, provider_id, external_group_key, role_id, sync_policy

roles / permissions / user_roles / role_permissions
  平台内角色与功能权限；Role 必须归属 tenant

resource_grants
  tenant_id, principal_type(user|role), principal_id,
  resource_type, resource_id, action, effect, condition, expires_at, created_by
```

`identity_providers` 的敏感配置不应以明文 JSON 保存。`resource_grants` 可迁移现有 `grants` 并增加条件/过期等能力；具体拆分前先检查现有 migration 和索引。

### 5.2 RBAC 与资源级授权职责

- **RBAC permission code**：回答“能否进行某类管理操作”，例如 `agent:create`、`tool:manage-grants`、`knowledge:manage`。
- **Role assignment**：回答用户具备哪些功能角色；用户可有多个租户内角色。
- **Resource Grant**：回答用户/角色是否能对特定资源执行某动作，例如 `tool.execute` on `tool_123`。
- **Policy/condition**：表达时间、网络、数据分类或参数限制等属性规则；第一版只引入确实需要的有限条件，不做任意表达式执行器。

角色是权限集合，不是“某个用户的身份标签”。建议系统角色模板包括 Tenant Owner、Security Admin、Agent Builder、Operator、Auditor、Knowledge Curator、Viewer；租户管理员可从模板复制并定制，但系统保护权限不能被普通租户管理员授予。

### 5.3 外部组映射

外部组映射是“外部组 → 本地角色”，不应是“外部组字符串 → 任意 permission code”：

```text
Google Workspace group: finance-readers
    → tenant role: finance_viewer
    → permission codes: knowledge:read
    → grants: knowledge_base=kb_finance, action=read
```

映射由租户管理员配置并审计；同步时只更新映射范围内的成员角色。未映射组没有权限。高权限角色需二次确认，不能仅凭可变的组显示名映射，使用稳定 group ID。

## 6. 单个 Tool 的授权模型

### 6.1 资源和动作

每个 Tool 必须拥有稳定的租户内 `tool_id`，不能以可改名的 Tool 名称或模型提供的函数名作为授权主键。外部工具的资源身份至少关联来源：

```text
Tool resource:
  tenant_id
  tool_id
  source = builtin | platform | capability
  provider_id / external_tool_id (when applicable)
  version or manifest_hash
```

动作建议分为：

| Action | 含义 |
|---|---|
| `tool:discover` | 能否看到 Tool 的名称和基本描述 |
| `tool:read` | 能否读取 Tool 配置/详情（不返回密钥） |
| `tool:execute` | 能否调用 Tool |
| `tool:manage` | 能否创建、修改、启停 Tool |
| `tool:manage-grants` | 能否给用户/角色授权 Tool |

再结合 Tool 风险等级和参数策略：`read`、`write`、`external_send`、`destructive` 等不是角色名称，而是动作风险元数据；高风险动作可以强制审批、限制参数或禁止 Agent 自动执行。

### 6.2 有效授权计算

一个 Tool 调用仅当以下条件全部满足才可执行：

```text
tenant matches
AND tool is active
AND Agent is active and bound to this exact tool
AND principal has tool:execute permission
AND user/one-of-role has explicit grant for (tool_id, execute)
AND no applicable deny grant
AND tool risk policy allows the operation
AND required approval has been granted for this exact run/action
```

如果产品要支持“角色拥有租户内所有普通只读 Tool”的便捷策略，应以显式的、受限作用域的 wildcard policy 实现，默认不启用；高风险 Tool 仍须精确授权。不得把“已绑定 Agent”当作通用授权，也不默认让任何有 `run:execute` 的人调用所有 Tool。

### 6.3 执行链路

1. 构造不可伪造的 `AuthorizationContext`：tenant、principal、roles、agent、run、domain pack、来源。
2. 加载 Agent 已绑定且 active 的候选 Tool。
3. 对每个 Tool 做 `tool:discover` / `tool:execute` 检查，只把允许的 schema 交给 LLM。拒绝事件可按策略审计。
4. LLM 返回 Tool Call 后，不信任 schema 过滤结果；在执行器中以当前 DB/策略版本再次检查 tenant、Agent 绑定、角色/Grant、风险和审批。
5. 参数经 Tool schema 校验及参数策略过滤/验证；不能只依赖 LLM 生成合法参数。
6. 执行前记录授权决策；敏感动作需在实际外部副作用之前完成审批。
7. 记录 Tool 结果、调用身份、资源 ID、策略版本、脱敏后的参数摘要和耗时；失败需可观测。

直接 API、后台 job、子 Agent 和人工 resume 必须走同一套授权语义。子 Agent 使用显式委派的 principal/scopes，不能因系统内部调用而绕开检查。审批应绑定 run、tool、参数摘要和策略版本，参数变化后原审批失效。

## 7. 统一决策语义

建议决策返回结构，而非布尔值：

```text
Decision:
  outcome: allow | deny | require_approval
  reason_code
  matched_policy_ids[]
  policy_version
  obligations[]       # e.g. mask fields, require approval, max rows
  expires_at
```

执行顺序：

1. 身份有效且用户/租户 active，否则 deny。
2. 租户与资源一致，否则 deny（对外可返回 404 以免泄露资源存在）。
3. 检查全局/资源 deny；任何适用 deny 优先。
4. 检查功能权限和资源 allow；缺少显式授权则 deny。
5. 检查审批和义务；需审批时返回 `require_approval`。
6. 只有所有强制条件满足才 allow。

默认拒绝、租户不可变、权限服务/策略状态不可用时敏感动作失败关闭。权限缓存需要短 TTL，并在角色、Grant、组成员或账户停用发生变化时失效；不能依赖长寿命 JWT 中的角色快照。

## 8. API 与管理界面建议

初步 API 分组（路径仅示意）：

```text
/auth/providers                       用户可见的登录 Provider
/auth/{provider}/authorize            发起登录
/auth/{provider}/callback             校验回调并签发平台会话
/admin/identity-providers              配置企业 IdP
/admin/users/{id}/identities           管理外部身份绑定
/admin/groups / group-role-mappings   组同步和角色映射
/admin/roles / permissions             角色、功能权限
/tools/{tool_id}/grants                单个 Tool 的授权管理
/agents/{agent_id}/tool-access         Agent 候选 Tool 与访问策略预览
/authorization/check                  管理员调试/解释决策（不可作为最终执行闸门）
```

Tool 管理页需要区分“Agent 绑定了这个 Tool”和“哪些用户/角色能执行这个 Tool”，并展示来源、风险等级、所需动作、授权对象、审批要求和最近授权事件。普通用户不应看到其无权发现的 Tool 详情或敏感配置。

## 9. 与现有代码的演进关系

1. 为 `Grant.action` 增加完整语义和测试；修复 `load_grant_keys` 不保留 action 的问题。
2. 扩展 `PermissionContext` 为明确的 subject/resource/action 授权上下文；保留 `check_permission` 的兼容包装，避免同时重写所有调用。
3. 将 `PermissionManager` 作为第一版 Authorization Service；让 HTTP 路由、数据访问、Ouroboros Tool 执行共用同一政策核心。
4. 为现有 User 增加 external identity link，不改变现有用户名/密码登录；分阶段允许每租户开启 Provider。
5. 先实现 OIDC 标准 Adapter 和 identity mapping；按有客户需求再加 SAML、SCIM、微信/企业微信/钉钉/字节系/厂商目录 Adapter。
6. 给 Grant 增加 `tool` 精确授权、拒绝、过期和审批测试；随后覆盖 Knowledge Base / Document / Agent / Skill 等资源。
7. 逐步把既有 admin bypass 改成不可变的系统保护权限清单；租户可自定义业务角色，但不得自授跨租户或系统级权限。
8. 把当前 best-effort audit 路径按操作风险分级；授权配置、身份绑定、审批和高风险 Tool 操作需要可靠审计。

避免一次大迁移：每阶段保留旧 JWT 会话、现有 API 错误格式和已有角色数据；迁移脚本需可重复验证并提供回滚窗口。

## 10. 威胁与测试要求

必须覆盖：

- 同一邮箱但不同 Provider/subject 不会自动合并账号。
- 伪造 tenant、外部 group claim、未验证 issuer/audience、过期/重放登录响应均拒绝。
- Provider A 的身份不能访问 Provider B/另一租户的数据。
- 用户有 Agent `run:execute` 但没有单 Tool grant 时，该工具 schema 不暴露且调用端二次检查拒绝。
- Agent 被绑定 Tool 但调用者无权时拒绝；LLM 直接伪造未暴露 Tool Call 仍拒绝。
- user deny 覆盖 role allow；跨租户 grant 不生效；过期 grant 立即/按声明缓存期限失效。
- Tool 删除/替换/重绑定不能通过复用名称或旧 external ID 继承错误授权。
- 高风险 Tool 参数被修改后旧审批不能复用。
- 组成员移除、用户停用、身份解绑后 session 与授权缓存按 SLA 失效。
- 审计不记录 token、client secret、完整敏感参数；审计写失败符合当前动作的 fail-closed 策略。

## 11. 分阶段实施建议

### Phase 1：统一工具授权（先做）

- 不新增第三方登录前，先补全当前 Grant.action 和 Tool `execute` 决策。
- 在 Tool Schema 暴露前筛选授权，并在 invoke 前强制重查。
- 支持租户管理员给单个用户/角色授予单个 Tool 的 `discover/read/execute/manage`。
- 增加风险标签、审批绑定与审计；默认拒绝未授权 Tool。

### Phase 2：OIDC 登录与账号链接

- 建立 Provider 配置和外部身份表。
- 先实现标准 OIDC Authorization Code + PKCE，覆盖支持 OIDC 的企业/公共 IdP。
- 增加邀请入租户、身份绑定确认、撤销会话和 Provider 管理 API。
- 仅通过管理员 allowlist 的 claims 映射组，不自动授予高权限。

### Phase 3：企业目录和角色映射

- 先接标准 SCIM；再按真实客户需求逐一实现企业微信、钉钉、字节系、阿里云企业身份等组织目录 Adapter。
- 处理成员停用、组移除、同步失败与定期 reconciliation。
- 组映射使用稳定外部 group ID，增加预览/模拟授权与审计。

### Phase 4：SAML、条件策略和更细授权

- 按企业客户需求增加 SAML 2.0、多因素/设备姿态要求和有限 ABAC 条件。
- 扩大资源对象授权到知识库、文档、评测集、实验等。
- 建立权限解释、批量审查、冲突检测和导出审计能力。

## 12. 非目标与安全边界

- 不把 Google、Apple、微信等 OAuth 登录的用户自动视为某企业组织成员。
- 不将第三方账号的 Admin/Owner 字符串直接变为平台管理员。
- 不把 Provider access token 当平台 API token，也不把 OAuth scope 当业务权限。
- 不用邮箱作为稳定用户主键，不自动合并同邮箱身份。
- 不只依赖 React/Console 隐藏按钮；所有 API 和 Tool invoke 服务端鉴权。
- 不因为权限服务、审计或 Provider 同步暂时失败而放宽授权。
- 不允许 Agent prompt 或 LLM 决定自己的 Tool 权限。
- 不假设各厂商的登录、组织、用户禁用和组同步能力一致；每个 Adapter 都要有能力声明和独立验收。
