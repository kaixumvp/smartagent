# PlatformAgent 业务层详细设计

> 本文记录当前代码结构与运行时接线约束；完整启动配置见[后端 README](../../application/platformagent/backend/README.md)。
> 规划中但尚未实现的能力不应视为当前 API。

## 1. 系统边界

PlatformAgent 负责“以谁的身份、使用哪些权限和能力执行 Agent、如何持久化并向用户呈现结果”。
Agent 思考循环属于 [Ouroboros 框架](../ouroboros/README.md)，框架不反向依赖业务层。

```text
Console ──HTTP/SSE──► api ─► services ─► adapters ──ports──► ouroboros
                         │       │             │
                         ├───────┴──────► db / iam
                         │
                         └──内部 HTTP + 共享密钥──► Capability Registry
```

依赖原则：`api → services → adapters → ouroboros`。API 层处理 HTTP、认证和响应；services 编排事务和
框架运行；adapters 实现宿主端口。`db/`、`iam/` 提供共享持久化和授权能力。Capability 只通过 HTTP 集成，
不共享 Python 包或数据库。

## 2. 主要模块

| 目录/模块 | 职责 |
|---|---|
| `smartagent/main.py` | FastAPI 应用、中间件、15 个显式注册的路由组、异常格式、Scalar 与 health |
| `smartagent/api/` | schemas、JWT 安全、租户上下文、限流、SSE 序列化及 HTTP 路由 |
| `smartagent/services/run_service.py` | 从 Agent/租户状态装配 `AgentDefinition`、`RuntimeDeps`，运行/恢复并汇总结果 |
| `smartagent/services/evaluation_service.py` | 异步评测任务；任务当前在 API 进程内运行 |
| `smartagent/services/experiment_service.py` | 实验变体的确定性粘性分流 |
| `smartagent/adapters/` | RunRecorder、DbCheckpointer、DbSubagentRunner、pgvector 记忆、插件装配、Judge、成本及 Capability HTTP 适配 |
| `smartagent/iam/` | RBAC、Grant 与框架 `PermissionContext` 的组装 |
| `smartagent/db/` | SQLAlchemy ORM、异步 session；PostgreSQL 是可审计数据的持久化来源 |

核心持久化模型包含 Agent、Skill、Tool、Run、RunStep、IAM/Grant、审计、向量记忆、Golden Set、Evaluation、
Experiment 等。具体 schema 与迁移以 `backend/src/smartagent/db/` 和 `backend/alembic/` 为准。

## 3. 一次运行的调用与持久化

1. `api/routes/runs.py` 验证身份、`tenant_id`、权限和 Agent 状态，并创建 Run 记录。
2. `RunService` 根据 Agent 配置加载插件，将租户权限与当前 run 的模型网关、记忆、事件接收器及 checkpoint
   适配器装入 `RuntimeDeps`。
3. `AgentRuntime.run(...)` 或 `.resume(...)` 执行 Plan → Decide → Execute → Observe。
4. `RunRecorder` 将 step / terminal 状态写入 PostgreSQL，再向 SSE 消费者发布事件。
5. Run 完成后，业务服务汇总 token、model、cost、结果、记忆写回和审计数据。

`runs` / `run_steps` 是运行历史和审计的真相源；Redis Working Brain 是带 TTL 的会话缓存。

## 4. 必须遵守的集成约束

1. **工作记忆写入顺序**：当前用户消息必须先写入 Working Brain，再读取历史并传入 runtime；否则后续轮次可能丢失当前输入。
2. **记忆召回仅执行一次**：业务当前在宿主侧召回长期 pgvector 记忆并留空 `RuntimeDeps.long_term_memory`，
   避免 runtime 再次召回导致重复注入。Knowledge fallback 未接通。
3. **HITL 恢复执行**：checkpoint 保存的是暂停时应再次执行的节点状态；审批后 `resume` 会重跑该 execute 节点，
   因而工具操作需遵守预期的幂等边界。
4. **步骤序号**：每次 runtime 调用会从头产生 step 序号；恢复运行时 `RunRecorder` 必须偏移序号以维持单调顺序。
5. **模型与成本账本**：仅 Agent 未固定模型时才进入 per-run 路由；每个 run 持有独立成本账本，不能依赖共享路由器上的
   `last_model` 归因并发请求。
6. **数据库会话并发**：并发子 Agent 不得共享同一个 SQLAlchemy `AsyncSession`；每个 child run 创建独立会话。

## 5. 已实现与未实现边界

已实现：多租户 JWT/RBAC/Grant、Agent/Tool/Skill CRUD、Run 同步与 SSE、HITL approve/reject、
checkpoint、子 Agent、Redis 工作记忆、pgvector 长期记忆、Golden Set/Judge、反馈、A/B 实验、成本归因、
Capability API/MCP Tools HTTP 集成。

未实现或后续规划：平台 Knowledge/RAG 摄取与检索、租户文档业务知识图谱（0.4.0 规划；区别于个人对话 Memory Graph）、
用户主动 pause/cancel 控制 API、
Console DAG/时间线/Playground、进程外评测队列、完整 OTel/Prometheus 部署及 Kubernetes。路线图见
[业务层版本规划](./版本规划.md)。
