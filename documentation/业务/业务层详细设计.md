# 业务层详细设计（smartagent-app）

> 本文档基于 `application/src/smartagent/` 的**实际代码**重写，描述业务层当前的职责、目录、API、持久化、适配器与跨层调用链。
> 业务层回答：**「跑哪个 Agent、以什么身份、用什么权限、结果存到哪、如何对外暴露」**。它依赖并实现 Agent 框架层（`application/ouroboros/`，包名 `ouroboros`）的端口。

| 契约面 | 业务侧落点 | 状态 |
|--------|-----------|------|
| `AgentRuntime.run/resume` | `services/run_service.py` | ✅ |
| `ports.EventSink` | `adapters/run_recorder.py` | ✅ |
| `ports.Checkpointer` | `adapters/db_checkpointer.py`（`runs.checkpoint`） | ✅ |
| `ports.SubagentRunner` | `adapters/subagent_runner.py` | ✅ |

| `ports.Knowledge` | — | ⏳ V0.3 |

### 接线时必须尊重的四个框架契约细节

这四条都是「按直觉写就会静默出错」的地方，实现散落在 `services/run_service.py` 与 `adapters/run_recorder.py` 的注释里：

1. **`_initial_state` 不会把 task 追加进 history**（`runtime.py:205`）：`history` 非空时被原样使用。因此当前用户消息必须**先写入 Working Brain、再读 history**，否则第二轮起用户输入丢出 LLM 上下文。
2. **`_recall_context` 会自行召回**（`runtime.py:395`）：同时传 `memory_context=` 和 `deps.long_term_memory` 会双份注入。业务层选择宿主侧召回并留空 `deps.long_term_memory`（保住测试缝、让 `memory_recall_top_k` 生效；代价是 Knowledge 兜底暂不启用）。
3. **暂停时刻意不落 checkpoint**（`runtime.py:291`）：最后快照是 post-decide、`_next_node == "execute"`，`resume` 正好重跑被卡住的那一步。
4. **框架每次 `run()`/`resume()` 都把 step `seq` 从 1 重新计数**：而 `run_steps.seq` 表示整个 run 的时间线位置，故 `resume` 时 `RunRecorder` 需按已有步数做 `seq_offset`，否则续跑步骤与暂停前撞号、`ORDER BY seq` 乱序。

5. **分级路由若直接用框架 `TieredRouter` 会静默失效**（V1.1）：`AgentRuntime` 把 `definition.model` 传给每个节点（`runtime.py:249`），而 `TieredRouter` 只在调用方 model 为假值时才选层（`cost.py:89`）。因此 `build_definition` 对未配 `config.model` 的 Agent 产出**空串**，由业务侧 `RunScopedRoutingGateway` 决策——空串同时也是「该 Agent 未锁定模型」的信号，配了模型的 Agent 仍然锁定。

6. **框架 `TieredRouter` 不能做成本归因**（V1.1）：`last_model` 是共享单例上的普通属性（`cost.py:86`），并发评测必然串号。成本账本必须挂在**每次运行独立**的网关实例上。

> 另：`ouroboros.events.sse` 已废弃（import 即告警），SSE 序列化由宿主 `api/sse.py` 负责。

## 1. 定位与职责边界

### 1.1 职责（做）

| 职责 | 说明 | 落点 |
|------|------|------|
| HTTP 暴露 | FastAPI 路由、请求/响应模型（Pydantic）、异常处理、中间件、Scalar 文档 | `api/`、`main.py` |
| 身份与访问 | JWT 签发/校验、密码哈希、当前用户依赖、功能权限依赖、RBAC + Grant 授权 | `api/security.py`、`iam/` |
| 资源管理 | Agent / Tool / Skill / Role / Grant 的 CRUD 与持久化 | `api/routes/` |
| 运行编排 | 创建 Run、HITL 审批、子 Agent 调度、SSE 流式输出 | `api/routes/runs.py`（HTTP）+ `services/run_service.py`（编排） |
| 端口实现（Adapters） | 实现框架层 `LongTermMemory` / `EventSink` / `Checkpointer` / `SubagentRunner` / `PermissionChecker`、插件装配 | `adapters/` |
| 持久化 | `runs`/`run_steps`/`runs.checkpoint` 落库、长期记忆 pgvector 落库 | `db/`、`adapters/{run_recorder,db_checkpointer,pgvector_memory}.py` |
| 审计 | 登录、越权拦截、审批决策写 `audit_logs` | `adapters/audit.py` |

### 1.2 不职责（由框架层 `ouroboros` 负责）

- 不做 Agent 主循环（Plan/Decide/Execute/Observe，框架层 `core/runtime.py` 的 `AgentRuntime`）
- 不做插件协议与技能/工具的**执行**逻辑（框架层 `plugins/`、`skills/`、`tools/`）
- 不做记忆机制（固化/召回/去重，框架层 `memory/`：`WorkingBrain`、`Consolidator`、`MemoryManager`）
- 不做授权决策纯逻辑（框架层 `ports.py` 的 `check_permission`）

## 3. 分层与依赖

```
api（routes/schemas/security/middleware/sse）
  ├──► services（编排）──────┬─────► ouroboros（框架层 AgentRuntime）
  │                          └─────► adapters（端口实现）──► ouroboros（ports）
  ├──► iam（RBAC/Grant 数据加载）
  └──► db（models/session）────────► PostgreSQL / pgvector
```

- `api` 负责 HTTP 语义与鉴权；`services` 负责编排（装配框架入参、回写运行结果）；`adapters` 负责「业务数据 ↔ 框架端口」的转换；`iam` 负责「DB 授权数据 → `PermissionContext`」。
- 依赖方向单向：`api → services → adapters`。`adapters` 不反向 import `services`（子 Agent 的编排逻辑通过构造期注入的 `child_runner` 回调传入，避免环）。
- `db` 被 `api`、`iam`、`adapters` 共同使用，不被框架层 import。
- 业务层整体可 import 框架层；框架层禁止反向 import 业务层。

## 4. 领域与持久化

### 4.1 数据模型（15 表，`db/models.py`）

| 分组 | 表 | 备注 |
|------|-----|------|
| 租户/身份 | `tenants` `users` `roles` `permissions` `user_roles` `role_permissions` | 6 表；`users`/`roles` 有 `(tenant_id, name)` 唯一约束 |
| 授权 | `grants` | `principal_type`（user/role）× `resource_type`（tool/skill/agent/knowledge）× `action` × `effect` |
| 业务实体 | `agents` `tools` `agent_tools` `skills` | 4 表；`skills` 多版本 + `is_latest` |
| 运行记录 | `runs`（`parent_run_id` 子 Agent 树）`run_steps` | 2 表；`runs.approvals` 已批准高危资源、`runs.checkpoint` 运行状态快照、`runs.pending_approvals` 待审批资源（后两列由 Alembic 0003 引入） |
| 记忆 | `vector_memories`（`embedding vector(1536)` + HNSW 余弦索引） | 1 表 |
| 审计 | `audit_logs` | 1 表（登录/越权/审批/暂停均已接线） |
| 评测（V1.1） | `golden_sets` `golden_cases` `evaluations` `evaluation_results` `feedbacks` | 5 表；Alembic 0004 |
| 实验（V1.1） | `agent_experiments`（**权重冻结**）`experiment_assignments` | 2 表；Alembic 0004 |

**V1.1 对存量表的扩展**（Alembic 0004）：

- `agents` + `is_latest`：建立「同一逻辑 Agent 的多个版本」，A/B 才有对比对象。索引策略是**非唯一** `(tenant_id,name,version)` + **部分唯一** `(tenant_id,name) WHERE is_latest`——不给 `(name,version)` 加唯一约束是为了不迁移改动存量数据（该表历史上无此约束，可能已有重复）；版本唯一性由路由侧 409 尽力保证，而 A/B 真正依赖的「至多一个 latest」由部分唯一索引硬保证。
- `runs` + `model`/`experiment_id`/`variant`/`evaluation_id`。`evaluation_id` 的作用是让重启清理能**精确圈定评测产生的 run**——否则笼统地把 `awaiting_human` 判失败会误杀正在等人工审批的正常 HITL 运行。

- 主键应用侧生成：`{prefix}_{uuid4().hex}`（`agent_`/`tool_`/`skill_`/`role_`/`grant_`/`run_`/`step_`/`mem_` 等）。
- `VectorMemory` 的 embedding 维度常量 `VECTOR_DIM = 1536`，须与 `config.embedding_dimension` 一致。
- `Agent` 通过 `agent_tools` 关联表维护 `tools` 关系（`lazy="selectin"`）；但 V0.2 的插件装配走 `Agent.config.plugins`（§5.1），`agent_tools` 表为 V0.1 遗留。

### 4.2 决策点：domain 薄层

- **现状**：ORM 模型即领域实体，`api`/`adapters`/`iam` 直接操作 ORM 对象，无独立 `domain/` 层。
- **演进**：后续如需纯业务实体 + repository，可再引入 `domain/`；当前保持少一层映射。

## 5. 适配器（Adapters）—— 实现框架层端口

### 5.1 `db_plugin_loader.py`（装配插件）

**职责**：把 `agents.config.plugins` 的引用解析为框架层 `Plugin` 对象，装配成 `PluginRegistry`。

```
extract_plugins(agent_config) -> list[{"type","ref","config"}]
    config.plugins 存在 → 直接用；否则把 config.tools（V0.1 遗留）归一化为 type=tool

PluginLoader(tool_registry, skill_manager)
  .load_for_agent(db, tenant_id, agent_config) -> PluginRegistry
      type=tool  → 内置 tool_registry 命中，或 DB tools 表（builtin/mcp/http）
      type=skill → DB skills 表（按 name + version 或 is_latest 命中）→ skill_manager.build
      type=model/knowledge/memory/node → 预留，暂忽略
```

- 工具装配分三态：内置（进程内 `ToolRegistry`）→ MCP（`McpTool`）→ HTTP（拉取 OpenAPI spec，`_resolve_operation` 按 `operation_id`/`path+method` 定位操作，`HttpOpenApiTool`）。
- `parse_ref` 解析 `kind:name@version` 格式（框架层 `plugins/manifest.py`）。

### 5.2 `pgvector_memory.py`（长期记忆）

**职责**：实现框架层 `LongTermMemory` 端口（`ports.py`），pgvector 写入/召回。类名 `VectorMemoryStore`。

```
VectorMemoryStore(embedder)
  .add(db, *, tenant_id, user_id, session_id, content, importance, confidence) -> id
      content → embedder.embed → VectorMemory(embedding) → db.add + commit
  .recall(db, tenant_id, user_id, query, top_k) -> list[MemoryEntry]
      query → embed → embedding.cosine_distance SQL 排序 → top-k → 转 MemoryEntry(similarity=1-distance)
```

- 读侧不 select embedding 列，相似度由 `cosine_distance` 在 SQL 端计算，避免 asyncpg 的 vector 类型注册。
- 框架层 `Consolidator` 只依赖 `LongTermMemory` 协议，不感知 pgvector。

### 5.3 `run_recorder.py`（运行时间线落库，实现 `EventSink`）

```
RunRecorder(db, run_id, *, queue=None, seq_offset=0)
  step.completed        → 插入 run_steps（seq = 事件 seq + seq_offset）
  run.completed/failed  → 更新 runs 终态 + finished_at，清空 pending_approvals
  run.awaiting_human    → 落 pending_approvals，并把刚写入的那一步改判 awaiting_human
  有 queue 时           → 持久化之后再投递事件（SSE 客户端不会看到未落库的步骤）
```

- 作用域是**单个 run**：每个子 Agent 必须绑定各自的 Recorder，否则子步骤会记到父 run 上。
- 这是 `run_steps` 的**唯一写入路径**，不要再从 `RunResult.steps` 落一遍。
- `seq_offset` 见 §0 契约细节 4；`step.completed` 事件不带 status，故暂停步骤靠紧随其后的 `run.awaiting_human` 回改。

### 5.4 `db_checkpointer.py`（运行快照，实现 `Checkpointer`）

`save`/`load`/`delete` 落在 `runs.checkpoint`。走 ORM `db.get(Run, id)`（identity map 命中，近乎零成本）。**保存时深拷贝**是必需而非防御：框架全程复用同一个 state dict 就地修改，直接赋值会让 SQLAlchemy 认为属性无净变化而不发 UPDATE，且后续修改会篡改已保存的快照。

### 5.5 `subagent_runner.py`（子 Agent 调度，实现 `SubagentRunner`）

解析 `agent_ref` → 租户校验 → 深度守卫 → 建 `parent_run_id` 子 Run → 委托注入的 `child_runner` 执行 → 渲染回父 Agent 的字符串。

**每个子 run 使用独立 session**：框架 `execute` 节点会 `asyncio.gather` 并行执行同一轮的多个工具调用，两个 agent-skill 并发即并发操作同一个 `AsyncSession`，而它并非并发安全。

### 5.6 `audit.py`（审计留痕）

`write_audit(...)` best-effort 写 `audit_logs`（失败自行 rollback，绝不影响主流程）。
`AuditingPermissionChecker` 包一层 `PermissionChecker`，缓冲每次非 ALLOW 决策，run 结束后由 `RunService` 批量落库——框架 `execute` 同步调用 `check()`、没有 db/租户上下文，而 `get_permission_manager()` 是进程级单例扛不了请求级状态。

### 5.7 `cost_gateway.py` / `llm_judge.py`（V1.1）

- `RunScopedRoutingGateway`：**每次运行**构造一个。`chosen = 传入 model（Agent 锁定）→ 分级路由 → 部署默认`，并把 `(model, usage)` 记进私有账本供 `run.cost`/`run.model` 归因。不用框架 `TieredRouter` 的两条理由见 §0 契约 5、6。
- `LlmJudge`：实现 `ports.Judge`，提示词要求纯 JSON 裁决，容忍代码围栏与前后文；解析失败或网关异常时**降级为「非空即通过」并在 `reason` 标注 `[degraded]`**——评测不能因一条无法解析的回复整体失败，但也不能把降级结果伪装成真实评分。

### 5.8 `iam/`（授权数据加载，非 adapters 目录）

**职责**：把 RBAC/Grant 数据加载为框架层 `PermissionContext`，并暴露 `check()`。

```
PermissionManager.build_context(db, principal) -> PermissionContext
    ├── rbac.load_user_role_ids / load_user_role_names / load_permission_codes
    └── grants.load_grant_keys -> {(resource_type, resource_id, effect)}

PermissionManager.check(ctx, action, ...) -> PermissionDecision
    └── 直接转发框架层 ouorobos.ports.check_permission(...)   # 纯决策逻辑在框架层
```

- 纯决策逻辑（admin 绕过 → deny-wins → 功能权限 → grant 要求 → 高危审批）在框架层 `ports.check_permission`，业务层只负责 `build_context()` 与数据加载。

### 6.1 静态依赖（进程级，`@lru_cache`）

### 6.3 鉴权依赖（`api/security.py`）

- `get_current_user(request, db)` → `Principal`：`auth_enabled=False` 时返回系统 admin；否则校验 `Authorization: Bearer`，JWT 解析 `sub`/`tenant_id`，DB 校验用户存在且 `tenant_id` 匹配且 `status=active`，加载角色名。
- `get_permission_context(principal, db)` → `PermissionContext`：`get_permission_manager().build_context(db, principal)`。
- `require_permission(code)`：依赖工厂，校验 `ctx.is_admin or code in ctx.permission_codes`，否则 403。
- `require_admin(principal)`：校验 `principal.is_admin`，否则 403。

## 8. 安全设计

| 面 | 措施 |
|----|------|
| 认证 | JWT（HS256），`sub`/`tenant_id`/`scope`/`exp`；角色不进 token、每次请求解析。**HS256 密钥需 ≥32 字节**（RFC 7518 §3.2），默认占位串只有 23 字节，PyJWT 会告警 |
| 密码 | PBKDF2-HMAC-SHA256（200k 迭代，自描述串 `pbkdf2_sha256$iters$salt$dk`），常量时间比较 |
| 身份源 | **本地账号库**（`users` 表即真相源，自签 JWT），无自助注册；账号由 `user:manage` 持有者在租户内创建。目标架构的 OIDC/OAuth2（`技术方案设计.md:189`）留待后续，届时本地库可保留作破窗账号 |
| 密码轮换 | 自助 `POST /auth/change-password`（校验当前密码）+ 管理员 `POST /users/{id}/password`（重置）。引导管理员密码取自 `BOOTSTRAP_ADMIN_PASSWORD`，不再硬编码进仓库 |
| 防自锁 | 禁止禁用自己的账号——无第二个管理员时不可恢复 |
| 授权 | 功能权限（`require_permission`）+ 资源级 Grant（框架 `check_permission` 运行时决策） |
| 多租户 | 查询按 `tenant_id` 过滤；跨租户资源返回 404 |
| 限流 | Redis 令牌桶（Lua），按 `rl:{tenant}:{sub}` 维度，fallback 到 client host |
| 审计 | `audit_logs` 表已建，业务代码**尚未接线**（待办） |

## 9. 跨层时序：一次 Run

```
客户端 POST /v1/agents/{id}/runs
   │
   ├─ api/routes/runs.py create_run（薄层）
   │    1. get_current_user → Principal
   │    2. get_permission_context → PermissionContext
   │    3. require_permission("run:execute")（拒绝时写 audit_logs）
   │    4. 加载 Agent（tenant 校验）
   │    5. 构造 RunService（内部：AuditingPermissionChecker / DbSubagentRunner / PluginLoader）
   │    6. service.load_registry → PluginRegistry
   │    7. 建 Run 记录（status=running，带 trace_id）
   │    8. stream=false → service.start；stream=true → StreamingResponse(_stream_run)
   │
   ├─ services/run_service.py start
   │    9.  memory.write(user 消息) → memory.get_history()    ← 顺序不可颠倒，见 §0 契约 1
   │    10. memory.recall → memory_context                     ← 不设 deps.long_term_memory，见 §0 契约 2
   │    11. AgentRuntime.run(
   │           AgentDefinition(model, system_prompt, plugins, runtime, agent_id),
   │           task, RunContext, RuntimeDeps(llm, permission_checker, checkpointer,
   │                                          event_sink=RunRecorder, subagent_runner, id_gen))
   │        → 每个节点：RunRecorder 落 run_steps（+ SSE 扇出）、DbCheckpointer 存快照
   │        → RunResult(status, result, steps, token_usage, pending_approvals)
   │
   └─ services/run_service.py finalize
       12. 兜底回写 runs 终态 + token_usage（终态字段主要由 RunRecorder 写）
       13. 非暂停时：写 assistant 消息 + memory.consolidate（best-effort，异常吞掉）
       14. flush 缓冲的授权决策 → audit_logs
       15. 返回 RunOut（同步）/ SSE 流（run.started → step.completed* → run.completed|failed|awaiting_human）
```

**子 Agent 调度**：`DbSubagentRunner` 校验深度与租户一致性 → **开独立 session** → 建 `parent_run_id` 子 Run → 回调 `RunService._run_child`（装配子 registry/definition/deps，绑定子 Recorder 与子 Checkpointer）→ 递归执行 → 渲染字符串回父 Agent。
> `PluginLoader ↔ SubagentRunner` 的循环依赖，由「把 `RunService._run_child` 绑定方法注入 `DbSubagentRunner`」自然打破——方法体在调用时才读 `self._loader`，而那一定发生在 `__init__` 完成之后。V0.2 早期用的 `loader_holder` 字典因此不再需要。

**HITL 审批（mid-run，`POST /runs/{id}/actions`）**：

```
run 执行到 execute 节点 → check_permission 返回 REQUIRE_APPROVAL
   → 框架发 run.awaiting_human（不落 checkpoint，最后快照停在 post-decide/_next=execute）
   → RunRecorder 落 runs.pending_approvals + 该步改判 awaiting_human
   → 响应 status=awaiting_human + pending_approvals
人工 approve
   → 累积 runs.approvals；仍有剩余高危资源则继续 awaiting_human
   → 否则 AgentRuntime.resume(definition, run_id, approvals, deps)
      从 runs.checkpoint 恢复，只重跑被卡住的 execute（RunRecorder 带 seq_offset 续号）
   → 同一 run 跑到 completed，checkpoint 清空
reject → status=canceled + audit_logs
```

> **授权语义前提**（框架 `ports.check_permission`）：admin 主体直接 ALLOW，**永不触发审批**；非 admin 还必须对该资源有 `allow` grant，否则是 DENY 而非 REQUIRE_APPROVAL。`auth_enabled=false` 的开发态返回 admin 主体，同样不会触发审批。

### 10.1 V1.1 评测任务的生命周期

```
POST /v1/evaluations → 建 evaluations 行(queued) → asyncio.create_task → 立即 202 返回
   │
   ├─ 任务持强引用于模块级 set（裸 create_task 可能被 GC 掉）
   ├─ 自开 session：请求的 db 在响应发出后即关闭
   ├─ PermissionContext 用新 session 重建（评测会真调工具，旧授权快照可能失真）
   └─ 每 case 独立 session + Semaphore 限并发（AsyncSession 非并发安全）
        每 case 建真实 runs 行（evaluation_id 标记）→ RunService.start → Judge 评分 → 逐 case 提交
   ▼
GET /v1/evaluations/{id} 轮询 → completed + total/passed/failed/avg_score/cost
```

**局限（记入技术债）**：任务在进程内，重启即中断。`lifespan` 启动时扫描并把滞留任务判失败（可用 `eval_sweep_on_startup` 关闭——它会连库，不该阻塞启动）。进程外调度归 V1.0。

> 评测运行**不回写长期记忆**（`RunService(memory_write_back=False)`）：它是合成流量，混进长期记忆会污染真实用户的召回。
