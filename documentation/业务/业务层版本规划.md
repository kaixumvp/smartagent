# 业务层版本规划（smartagent-app）

> 本文档是**业务层**（`application/src/smartagent/`）的版本计划，与平台级《版本规划.md》对齐，但只聚焦业务层自身的交付节奏。
> 业务层跟随平台版本号（V0.1 / V0.2 / V0.3 / V1.0 / V1.1）；由于业务层依赖框架层 `ouroboros`，当框架层 API 演进时，业务层的首要任务是**跟上契约、不脱节**。

### 收口过程中修掉的三个缺陷

1. **阻断级失配**：`runs.py` 引用已删除的 `ouroboros.core.graph`（`build_graph`/`run_agent`），app 无法 import、两个测试模块 collect error。已改接 `AgentRuntime`。
2. **model 传参不一致**：`_execute_now` 传 `Settings` 对象、`create_run`/`_stream_run` 传 `settings.llm_model` 字符串，且都未读 `agent.config.model`。已统一到 `RunService.build_definition`。
3. **step `seq` 撞号**：框架每次 `run()`/`resume()` 都把 `seq` 从 1 重新计数，续跑步骤与暂停前撞号导致 `ORDER BY seq` 时间线乱序。`RunRecorder` 增加 `seq_offset` 修正。

此外顺带修复了一个既有隐患：框架 `execute` 节点并行调用多个工具时，多个子 Agent 会并发操作同一个 `AsyncSession`（非并发安全），现改为每个子 run 独立 session。

| 版本 | 主题 | 业务层核心交付 | 状态 |

| V0.2 | 能力 | 多租户 + JWT + RBAC/Grant + Skill/Tool 注册 + 长期记忆起步 + 插件装配 + HITL mid-run 审批 + 子 Agent + 审计 | ✅ 已完成 |

| 项 | 落点 |
|----|------|

| Alembic 0004 | 7 张新表 + `agents.is_latest` + `runs` 四列 + 4 个权限码（幂等种子） |

**为什么能跳过 V0.3/V1.0**：框架层已经是 v1.1，`evaluation/`、`llm/{cost,routing,replay}.py`、`ports.Judge` 全部就位，业务层缺的只是存储、端点与装配；平台文档也把评测排在最后是因为「评测依赖真实运行数据」，而 V0.2 收口后 `runs`/`run_steps` 已是真相源。

**已知代价**：平台 V1.1 验收标准「成本较 V1.0 下降（有量化目标）」**无法验证**——V1.0 的可观测基线不存在。本版把「成本计价落库」纳入实施，至少让成本数据从这一版起是真的（此前 `runs.cost` 恒为 0）。

**实施中发现并修掉的三个缺陷**：

1. **分级路由接上去也不会生效**（阻断级，会静默失效）：`AgentRuntime` 把 `definition.model` 传给每个节点（`runtime.py:249`），而框架 `TieredRouter` 只在 model 为假值时才选层（`cost.py:89`），V0.2 的 `build_definition` 又保证 model 恒非空。三者叠加，路由永不触发。改为 `build_definition` 对未配模型的 Agent 产出空串 + 业务侧 `RunScopedRoutingGateway`。
2. **框架 `TieredRouter` 无法做成本归因**：`last_model` 是共享单例属性（`cost.py:86`），并发评测必然串号。改为每次运行独立的网关实例持有成本账本。
3. **启动阻塞在数据库往返**：`lifespan` 里的评测清理会同步连 Postgres，数据库不可用时拖慢启动（测试从 0.23s 涨到 36.88s）。改为可配置开关 `eval_sweep_on_startup`。

**验收**：
- ✅ 质量劣化可阻断发布：Golden Set + LLM-as-Judge 给出 `passed/failed/avg_score`，可作为发布门禁
- ✅ 同一 `(experiment, subject)` 恒定分到同一变体，权重 90/10 分布落在容差内
- ✅ `runs.cost`/`runs.model` 与价表精确吻合（`tests/test_cost.py` 端到端驱动真实 run 验证）
- ⚠️ 「成本较 V1.0 下降」无基线可比，见上

## 五、关键原则（业务层特有）

1. **契约先行**：业务层只能调用框架层 `ports.py` 的协议与 `core/runtime.py` 的公开入口，不 import 框架层内部实现；框架层每次 API 演进，业务层第一优先事项是**对齐契约、保证可运行**。
2. **每版可验证**：每版以「能跑通的最小闭环 + 明确验收项」收口，不留半成品。
3. **持久化是真相源**：`runs`/`run_steps` 是结果追溯的真相源，Redis Working Brain 是易失缓存；业务层负责把框架事件可靠落库。
4. **多租户是红线**：所有查询 `WHERE tenant_id = current`，跨租户一律 404，宁可重复过滤不留裸查询。
5. **适配器收敛**：与框架端口一一对应（`EventSink`/`SubagentRunner`/`LongTermMemory`/`PermissionChecker`/`Checkpointer`/`Knowledge`），业务逻辑尽量不散落在路由层。
6. **不提前设计**：`domain` 薄层、独立 repository、插件市场等在证据不足前不引入。
